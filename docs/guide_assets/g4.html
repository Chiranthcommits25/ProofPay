MODULE 6THE BACKEND AND THE SHIPMENT API

The backend is small, deliberately: one Express service, five routes, one JSON file, one validation layer. Its job is to be the off-chain system of record for physical progress, so that the oracle has something independent to read. It never touches the escrow, never holds keys, and never decides a settlement.

6.1 Node, Express and the shape of a REST API

Node.js runs JavaScript outside the browser, with a single-threaded event loop: I/O is asynchronous, so waiting for a file read does not block other requests. Express is a thin HTTP framework on top of Node: you register routes, and middleware functions run in order. This project uses Express 4.21.2 with only two extra dependencies, cors and dotenv.

// backend/src/app.js (structure)
const app = express();
app.use(cors({ origin: config.corsOrigin }));
app.use(express.json({ limit: '32kb' }));          // reject oversized bodies early
app.use('/api/shipments', createShipmentRouter({ shipmentService, config }));
app.use((req, res) => res.status(404).json({ error: 'NOT_FOUND' }));
app.use((error, req, res, next) => { /* ApiError → status, else 500 */ });

REST means resources are addressed by URLs and verbs describe the intent: GET reads, POST creates, PATCH partially updates. The API's verbs are not decoration; each maps to a different service method and a different validation path.

Table 6.1: The complete shipment API, as implemented
EndpointHandlerBehaviour and status codes

6.2 Middleware, validation and the five-layer write path

Middleware is a function that runs before the handler. requireMutationAccess is the security middleware: it compares a shared secret header against configuration and returns 401 when it is absent or wrong. It exists because the API is intentionally reachable on localhost by the browser, but only the seller client and the scheduler should be able to change a status.

Validation lives in lib/validation.js, not in the route. normalizeCreateShipment checks the order ID is 32 bytes of hex, the tracking ID is non-empty and conforms to the expected pattern, the carrier is a string, and the seller address is a valid 20-byte hex address; it lowercases addresses so comparisons with chain data are reliable. normalizeStatusUpdate rejects unknown statuses. Rejecting bad input at the edge means every later layer can assume clean data — but each later layer still validates, because a service can be called from somewhere else tomorrow.

6.3 Registering a shipment: the real sequence

  1. Seller opens Incoming Escrows, selects a funded order, and enters a tracking ID such as PPD-MACBOOK-001.
  2. The React app sends POST /api/shipments with the order ID, tracking ID, carrier label, its own address and a description, plus the mutation secret header.
  3. register() normalises the body, then calls assertNoDuplicates: no existing shipment with that tracking ID, none for that order.
  4. It then calls chainVerifier.verifyEscrow(orderId), a read-only RPC call to getEscrow.
  5. Three chain-level facts are enforced: the escrow exists (404 if not), its status is 1 = Funded (409 if released/refunded), and its seller equals the registered seller address (409 SELLER_MISMATCH).
  6. The duplicate checks run again — after the async RPC — to close the window in which two concurrent requests could both pass.
  7. Finally the record is built with status: "CREATED", simulated: true, timestamps from an injectable clock, and the first event in its history.

Step 5 is the answer to "what stops a seller from registering a shipment for an order that does not exist?". The backend refuses, and even if it did not, the CRE workflow independently checks the escrow's status before reporting, and the receiver checks again before paying. Three layers, same fact.

6.4 State transitions, and why the API is strict

// backend/src/services/shipmentService.js
export const SHIPMENT_TRANSITIONS = Object.freeze({
  CREATED:    Object.freeze(['SHIPPED']),
  SHIPPED:    Object.freeze(['IN_TRANSIT']),
  IN_TRANSIT: Object.freeze(['DELIVERED', 'LOST']),
  DELIVERED:  Object.freeze(['RETURNED']),   // simulation-only return path
  LOST:       Object.freeze([]),
  RETURNED:   Object.freeze([]),
});
Table 6.2: The shipment lifecycle as enforced by the API
StatusAllowed nextMeaning for the oracle
CREATEDSHIPPEDRegistered, not dispatched. CRE reports nothing; the escrow stays funded.
SHIPPEDIN_TRANSITIn the network. Still no settlement.
IN_TRANSITDELIVERED or LOSTThe decision point. CRE now produces a report, and the escrow is still funded, so it is eligible.
DELIVEREDRETURNED (simulation only)CRE maps DELIVERED to RELEASE. If the escrow is already released, a later RETURNED produces no automatic action — the workflow routes it to manual review.
LOSTnoneCRE maps LOST to REFUND; the escrow becomes Refunded and terminal.
RETURNEDnoneManual review only. No automatic report is generated, because a return after delivery is a dispute, not a courier fact.

The transition table is validated inside the store's serialised updater. That detail matters: if the check happened before the async write, two concurrent PATCH requests could both read IN_TRANSIT and both apply DELIVERED and LOST, producing two contradictory events. Serialising the check and the write makes the transition atomic at the application level.

6.5 Persistence: one file, written carefully

shipmentStore.js keeps the collection in memory and mirrors it to backend/data/shipments.json. Writes go to a temporary file and are then renamed over the target, so a crash mid-write cannot leave a truncated JSON document. Writes are serialised through a promise chain, so concurrent requests queue rather than interleave. Reads are served from memory, which is why the CRE HTTP call is cheap.

This is not production storage, and the guide says so plainly: no indexing, no transactions across entities, no replication, no access control at rest. For a teaching project whose subject is the oracle pipeline, a single atomic file is the right trade — it makes the data source inspectable with cat, which is exactly what a viva needs.

6.6 Why seller registration is separate from escrow creation

They are different facts recorded by different parties on different systems. The escrow records a financial obligation: this buyer has locked this amount for this seller. The shipment record describes physical fulfilment: this parcel with this tracking number is moving. If registration were part of createEscrow, the buyer would have to know a tracking number that does not exist yet, and the escrow contract would have to store a string, paying permanent storage costs for data that changes six times.

Separating them also creates the cross-check that makes the oracle meaningful: the backend verifies that the order is funded and that the seller matches before accepting a shipment. Neither system can lie alone; the chain supplies the financial fact, the API supplies the physical fact, and CRE is the component that joins them.

Interview checkpoint — Module 6

Q. "Why not put shipment status on chain?" A. Cost, mutability and privacy. Six status updates per order would cost gas each time, and a mis-scan would be permanent. Keeping it off chain means it can be corrected, while the money stays on chain where corrections are unnecessary.

Q. "Who can fake a shipment?" A. Anyone holding the API's mutation secret, which is server-side only. But a fake status cannot move money unless the escrow is funded and unspent, and the settlement itself is limited to one payout per order by the receiver and the escrow.

MODULE 7CHAINLINK, ORACLES AND CRE FROM ZERO

This is the module that turns you from someone who used Chainlink into someone who can explain why it is necessary. Read it slowly.

7.1 The oracle problem, stated simply and then precisely

A smart contract is a sealed room: it can compute, it can read its own storage, and it can call other contracts, but it cannot look outside the blockchain. It has no network access, no clock beyond the block timestamp, and no way to ask "did the parcel arrive?". This is not an oversight; it is what makes consensus possible. Every node must compute the same answer, so every input must already be on chain.

Therefore any fact about the real world has to be carried in by a transaction. The carrier is called an oracle. The oracle problem is: how do you get a trustworthy external fact into a system that cannot verify it, without reintroducing a single point of trust?

Table 7.1: Off-chain facts versus on-chain facts in ProofPay
FactWhere it livesWhy there
Buyer locked 3,499 pUSD for seller SOn chain (escrow storage)It is the money. Must be tamper-proof and verifiable by both parties.
Shipment PPD-MACBOOK-001 is DELIVEREDOff chain (Express API)It changes often, comes from an external process, and must be correctable.
Report says DELIVERED at 12:55:31ZOn chain (via receiver)It is the evidence that justified moving money; it must be permanent.
Courier's internal scan historyOff chainVoluminous, private, and irrelevant to the contract beyond the status.

7.2 What Chainlink is, and which parts this project actually uses

Chainlink is a network of independent node operators that deliver external data and computation to blockchains. A node runs software that can fetch APIs, sign results and submit transactions. A DON (decentralised oracle network) is a group of nodes that must agree on a result before it is reported, which removes the single-reporter assumption. Consensus in that context means the nodes independently fetch and compare, and only an agreed answer is accepted.

Table 7.2: Chainlink products, and whether ProofPay uses them
ProductWhat it doesStatus in this project
Price FeedsPublishes market prices (ETH/USD, etc.) on chain.Not used. ProofPay has no price dependency; amounts are denominated in pUSD.
Automation (Keepers)Runs a contract function when a condition is met.Not used. The scheduling here is a local cron inside the CRE workflow and the demo scheduler script.
FunctionsServerless JavaScript that returns a value on chain.Not used. Its model is a request/response callback; ProofPay needs a multi-step workflow with its own decision logic.
VRF / CCIPVerifiable randomness / cross-chain messaging.Not used.

Why CRE rather than a price feed? Because the task is not "read a number someone else publishes"; it is "fetch my own API, check my own contract, apply my own rule, and produce a report my contract can verify". CRE is the product that supports arbitrary workflow logic with both HTTP and EVM capabilities, which is exactly the shape of the problem.

7.4 main.ts, stage by stage, with the real code

The workflow is one handler. Read the following in the order it executes; each block is quoted from chainlink/cre/shipment-workflow/main.ts.

Stage 1 — configuration and the decision table

export type Config = {
  shipmentApiBaseUrl: string; shipmentApiPath: string; rpcUrl: string; chainId: number;
  escrowContractAddress: string; receiverContractAddress: string;
  forwarderAddress: string; dryRun: boolean;
};
const ESCROW_STATUS_FUNDED = 1;

Configuration is supplied per target by config.staging.json, validated by zod in config.ts. The staging file sets the API base to http://localhost:5001, the chain ID to 31337, the escrow and receiver addresses to the deployed ones, the forwarder to the zero address, and dryRun: true. config.production.json exists and was left untouched.

function shouldSettle(shipment: { status: string }): SettlementDecision {
  switch (shipment.status) {
    case "DELIVERED": return { action: "RELEASE", outcome: "DELIVERED", reason: "..." };
    case "LOST":      return { action: "REFUND",  outcome: "LOST",      reason: "..." };
    case "IN_TRANSIT":
    case "SHIPPED":   return { action: "NONE",    reason: "payment remains locked" };
    case "RETURNED":  return { action: "MANUAL_REVIEW", reason: "requires manual review" };
    case "CREATED":   return { action: "NONE",    reason: "not ready for settlement" };
    default:          return { action: "NONE",    reason: `Unknown shipment status: ${shipment.status}` };
  }
}

This function is the project's entire settlement policy, and it lives in exactly one place. The bridge has no copy of it. If an interviewer asks "where is the decision made?", point here.

Stage 2 — fetch the shipment list over HTTP, with consensus aggregation

const httpClient = new HTTPClient();
const responseBody = httpClient
  .sendRequest(runtime, fetchShipments, consensusIdenticalAggregation<string>())(runtime.config)
  .result();

const fetchShipments = (sendRequester: HTTPSendRequester, config: Config): string => {
  const url = `${config.shipmentApiBaseUrl}${config.shipmentApiPath}`;
  const response = sendRequester.sendRequest({ url, method: "GET" }).result();
  if (!ok(response)) throw new Error(`HTTP request failed with status: ${response.statusCode}`);
  return text(response);
};

Three things to notice. The request is wrapped in consensusIdenticalAggregation<string>(), which in a DON deployment means every node fetches and the results must be byte-identical before the workflow continues — that is how a single lying node is outvoted. In the local simulator there is one node, so the consensus wrapper is exercised but proves nothing; say that honestly. Second, failures throw, and the handler catches them and returns an error string, so a dead API results in "HTTP error" and zero settlements rather than a partial run. Third, the body is treated as untrusted text and parsed defensively:

let shipments: any[] = [];
if (Array.isArray(parsed)) shipments = parsed;
else if (parsed && typeof parsed === "object" && "shipments" in parsed && Array.isArray(parsed.shipments))
  shipments = parsed.shipments;
else return "No shipments";

Stage 3 — read the escrow on chain before believing the shipment

const network = getNetwork({ chainFamily: "evm", chainSelectorName: "ethereum-testnet-sepolia", isTestnet: true });
const evmClient = new EVMClient(network.chainSelector.selector);

const callData = encodeFunctionData({ abi: ESCROW_ABI, functionName: "getEscrow", args: [orderIdBytes32] });
const callMsg = encodeCallMsg({ from: zeroAddress, to: config.escrowContractAddress, data: callData });
const evmResp = evmClient.callContract(runtime, { call: callMsg, blockNumber: LAST_FINALIZED_BLOCK_NUMBER }).result();
const escrow = decodeFunctionResult({ abi: ESCROW_ABI, functionName: "getEscrow", data: bytesToHex(evmResp.data) });
if (escrow.status !== ESCROW_STATUS_FUNDED) { runtime.log("Escrow not funded..."); continue; }

This is the cross-check that makes the design sound: the API claims a shipment status, the chain proves whether money is still held. Both must agree before a report exists. LAST_FINALIZED_BLOCK_NUMBER is used rather than "latest" so the read is from a settled block, not a tip that could be reorganised.

The chain-selector limitation, stated exactly

getNetwork is called with ethereum-testnet-sepolia because the installed SDK (1.23.0) exposes no chain selector for a local Hardhat node on chain ID 31337. The EVM read therefore does not point at Hardhat through that abstraction. This is precisely why the local execution bridge exists, and why this project must never be described as having executed a CRE write against Hardhat. CRE's read is performed against the configured RPC in the local workflow path used here, and the write path is disabled entirely.

Stage 4 — build and generate the report

const observedAt = shipment.updatedAt || shipment.createdAt || "2026-11-01T00:00:00.000Z";
const trackingIdHash = keccak256(toHex(shipment.trackingId));
const reportPayload = createReportPayload(shipment.orderId, decision.outcome, shipment.trackingId, observedAt);
const reportRequest = prepareReportRequest(reportPayload);
const report = runtime.report(reportRequest).result();

createReportPayload does the ABI encoding:

const orderIdBytes32 = (orderIdHex.padEnd(66, "0").slice(0, 66)) as Hex;
const trackingIdHash = keccak256(toHex(trackingId));
return encodeAbiParameters(parseAbiParameters("bytes32, string, bytes32, string"),
  [orderIdBytes32, outcome, trackingIdHash, observedAt]);
Table 7.4: The four report fields, and why each exists
FieldTypeWhy it is in the report
orderIdbytes32Identifies which escrow to pay. The receiver decodes it and passes it to the escrow.
outcomestring"DELIVERED" or "LOST". The receiver accepts only these two and maps them to the two settlement calls.

Stage 5 — extract the exact bytes, and prove they are the right bytes

The SDK prefixes a 109-byte metadata header to the encoded body. The receiver decodes the body only, so sending the raw report would corrupt the first field. The workflow therefore tries both candidates and accepts the one that decodes to the expected order and outcome:

const creRawReportHex = bytesToHex(report.rawReport());
const bodyBytes = report.body();
if (bodyBytes && isExpectedAbiPayload(bodyBytes, orderIdBytes32, outcome))
  return { payloadHex: bytesToHex(bodyBytes), payloadSource: "body", creRawReportHex };
if (isExpectedAbiPayload(report.rawReport(), orderIdBytes32, outcome))
  return { payloadHex: creRawReportHex, payloadSource: "rawReport", creRawReportHex };
return { payloadHex: creRawReportHex, payloadSource: "unverified", creRawReportHex };

In every observed run the source was body, the payload was 256 bytes, the raw report 365 bytes, and 365 − 256 = 109 exactly matches REPORT_METADATA_HEADER_LENGTH. That arithmetic is the cleanest evidence that the header was stripped correctly, and it is the kind of detail that makes an interviewer believe you built the thing.

Stage 6 — emit the structured records, then honour dry-run

runtime.log(`${REPORT_LOG_PREFIX}${JSON.stringify({
  type: "report", orderId, outcome: decision.outcome, trackingId: shipment.trackingId,
  observedAt, metadata: "0x", report: payloadHex })}`);

runtime.log(`${REPORT_LOG_PREFIX}${JSON.stringify({
  type: "meta", orderId, action: decision.action, trackingIdHash, reportSource: payloadSource,
  reportDecodesToReceiverAbi: payloadSource !== "unverified", creRawReportLength,
  creMetadataHeaderLength: REPORT_METADATA_HEADER_LENGTH, creRawReportHash,
  receiver: config.receiverContractAddress, escrow: config.escrowContractAddress,
  creDryRun: config.dryRun })}`);

if (config.dryRun) { runtime.log("DRY RUN: ... CRE write skipped"); continue; }

The sequencing is the single most important repair in the project's history. In the original code the dryRun check came before runtime.report, so with dry-run enabled — the safe setting — no report object was ever produced and nothing could be captured. Moving generation above the branch is what made the entire local pipeline possible: the report exists in both modes, and only its on-chain destination is conditional.

The two log lines exist because the CRE runtime truncates user log lines at roughly one kilobyte. The payload alone is 512 hex characters, so provenance is emitted separately and the bridge rejoins the two records by order ID. That constraint, and the workaround, is a good story about reading your tools' limits instead of fighting them.

Interview checkpoint — Module 7

Q. "Why hash the tracking ID?" A. Two reasons: the hash ties the settlement to a specific courier record as evidence, and it avoids publishing the tracking number on a public ledger, which would leak shipping details. The receiver stores it only as part of the report ID.

Q. "Does consensus aggregation prove your oracle is decentralised?" A. No. The code is written for it, but in this deployment the simulator runs one node, so no independent agreement happens. Real decentralisation requires the workflow deployed to a DON with multiple operators, which was out of scope.

MODULE 14 · PART BINTERVIEW AND VIVA BANK: LEVELS 4–5

14.4 Level 4 — advanced technical

Q66. Walk me through CRE report generation.

Short: encode the four fields, wrap in prepareReportRequest, call runtime.report(...).result(), then extract the body. Reasoning: the SDK adds a metadata header the receiver must not see. Instance: 256-byte payload, 365-byte raw report, source reported as body.

Q67. How exactly is the report encoded?

Short: abi.encode(bytes32, string, bytes32, string) — the order ID word, then a dynamic string, then a word, then a dynamic string. Reasoning: dynamic types use offsets, which is why the fixed part is four 32-byte words and the strings trail behind. Instance: the receiver uses one abi.decode with the same signature.

Q68. Why 109 bytes, and why does it matter?

Short: that is REPORT_METADATA_HEADER_LENGTH, the SDK's provenance prefix; the receiver decodes only the body. Reasoning: passing the raw report would shift every field by 109 bytes and fail to decode. Instance: 365 − 256 = 109, which is the arithmetic proof the strip was correct.

Q69. How does replay protection actually work?

Short: the receiver hashes the whole report and refuses a hash it has seen. Reasoning: identical bytes always produce the same digest, so a replay is detectable without storing the report. Instance: keccak256(abi.encodePacked(orderId, outcome, trackingIdHash, observedAt, metadata)).

Q70. Why do you need a second mapping for duplicate settlements?

Short: because a different report on a settled order produces a different report ID. Reasoning: without orderSettled, changing the timestamp would bypass replay protection. Instance: the escrow's Funded check would still block payment, but the receiver would waste gas and emit a misleading attempt.

Q71. Why can't the CRE SDK target local Hardhat?

Short: the installed SDK has no chain selector for chain ID 31337. Reasoning: selectors are an allow-list of supported networks, and local dev chains are not in it. Instance: the code calls getNetwork with a Sepolia selector because that is what compiles and runs; this is exactly why the bridge exists and why no CRE write is claimed.

Q72. Simulation versus DON deployment — what is the real difference?

Short: simulation runs your workflow in the CLI on one machine; deployment registers it with a DON where multiple operators execute it and agree. Reasoning: consensus, availability and signing authority all change. Instance: locally dryRun is true and a bridge relays; on a DON the workflow would write the report itself.

Q73. What exactly would you change for a DON deployment?

Short: deploy the workflow, flip dryRun to false, expose the API over HTTPS, set the receiver's forwarder, remove the owner fallback, delete the bridge. Reasoning: each change moves one responsibility from the local machine to the network. Instance: the escrow needs no change at all, because its oracle is already the receiver.

Q74. How does the receiver communicate with the escrow?

Short: it holds an immutable IEscrowSettlement reference and calls confirmDelivery or confirmFailure. Reasoning: because the receiver is the escrow's oracle, those calls satisfy onlyOracle without any EOA having that power. Instance: the escrow sees msg.sender = receiver.

Q75. What happens if report submission fails?

Short: the bridge reports the failure, decodes the revert, exits non-zero and records nothing. Reasoning: no state file entry means the submission is not falsely considered done; no retry means no duplicate risk. Instance: the operator fixes the cause (funding, wiring, authorisation) and runs again deliberately.

Q76. What if the transaction reverts after gas was spent?

Short: all state changes are undone; only gas is consumed. Reasoning: the EVM is atomic across the whole call tree. Instance: a reverted processReport leaves the escrow Funded and the mappings untouched, so a corrected retry is safe.

Q77. How would this scale to production?

Short: deploy the contracts to a public chain, run the workflow on a DON, replace the JSON store with a database, index events for the UI, use a KMS-backed signer for any manual path. Reasoning: each change addresses a specific local shortcut, not the architecture. Instance: the contract interfaces and the report format stay identical.

Q78. Where does the gas go in a settlement?

Short: mostly the token transfer, the two mapping writes, the escrow state write and the events. Reasoning: storage writes dominate; logs are cheaper. Instance: ~122,000 gas for processReport versus ~71,000 for a direct confirmDelivery; the ~51,000 difference is the policy layer's price.

Q79. Why terminal states instead of a reversible flag?

Short: because reversibility is the property an attacker needs. Reasoning: a reversible payout invites governance capture and makes balances non-final. Instance: the escrow's enum has no path back to Funded, and there is no admin rescue.

Q80. No upgradeability — is that a strength or a flaw?

Short: both, and you should say both. Reasoning: strength: no proxy admin can rewrite the rules; flaw: a bug is permanent and migration means a new deployment and manual fund movement. Instance: the project mitigates with a small surface, audited primitives and 31 tests rather than an upgrade path.

Q81. How would you add a second payment token?

Short: make the escrow's token per-order rather than immutable, or deploy one escrow per token. Reasoning: the immutable token is a deliberate simplification; multi-token support means storing the token address in the Escrow struct and validating it against a registry. Instance: the receiver would not change, because the escrow still owns payouts.

Q82. How would partial refunds work?

Short: a new settlement function that splits the amount and a report outcome that carries a basis-points field. Reasoning: the current payload has no room for an amount, and adding one changes the receiver's ABI. Instance: this is future work, listed in the report, not implemented.

Q83. What if the user switches accounts mid-checkout?

Short: accountsChanged re-runs applyAddress, the address changes, and the pending transaction is signed by the new account. Reasoning: the wallet is the authority, so the UI must follow it rather than cache an address. Instance: that is why useWallet exposes a refresh and subscribes to events.

Q84. Two orders for the same seller — any interference?

Short: none: state is keyed by order ID, and settlements are independent. Reasoning: the escrow mapping is per order, so one release cannot affect another. Instance: a test named "settles multiple escrows independently" pins exactly this.

Q85. How do you test the oracle without a real courier?

Short: with a deterministic simulated API and a scheduler that advances statuses. Reasoning: the oracle's job is to read a source, not to trust it, so a fake source exercises the same code path. Instance: the workflow's logs show it processing real records from the Express API, including skip and error branches.

Q86. What does idempotency mean in this system?

Short: running the pipeline twice has the same effect as running it once. Reasoning: settlement is the only irreversible effect, so it must be exactly-once, while report generation is safely repeatable. Instance: CRE may emit the same report again; the receiver and bridge both refuse it.

Q87. How would an auditor verify a settlement afterwards?

Short: take the transaction hash, read the receipt, decode ReportProcessed for the report ID and outcome, read getEscrow for the final state, and check token balances. Reasoning: the chain is self-describing; nothing depends on the app. Instance: that is precisely what the verification script produced for blocks 24, 29 and 30.

Q88. Why uint64 for timestamps?

Short: to pack two timestamps with an address and an enum into fewer storage slots. Reasoning: storage is charged per slot, so smaller types reduce gas when they share a slot. Instance: createdAt and settledAt are both uint64 and will not overflow for billions of years.

Q89. Why does the receiver take a metadata parameter that is always 0x?

Short: because the CRE/Chainlink receiver interface requires it, and the local path passes empty bytes. Reasoning: keeping the signature identical means a DON can call onReport without code changes. Instance: metadata still contributes to the report ID, so two otherwise identical reports with different metadata are distinct.

Q90. What happens to the allowance after settlement?

Short: it was already consumed at funding; settlement uses transfer from the escrow's own balance, not an allowance. Reasoning: the escrow owns the tokens, so it needs no permission to move them. Instance: after a purchase the buyer's allowance to the escrow returns to zero for that amount.

14.5 Level 5 — the challenging questions

Q91. Why should I trust the courier API?

Short: you should not trust it blindly — you should bound what a lie can achieve. Reasoning: a false status can cause a wrong settlement, but only for a funded, unsettled order, only once, and only through an authorised report. Instance: the design mitigations are the on-chain funding re-check, replay protection, and the audit trail that records which report justified the payout. A production system would add a real carrier's signed webhooks or multiple independent sources.

Q92. What if the seller manipulates shipment status?

Short: they can make a parcel look delivered, but they cannot make money appear. Reasoning: settlement requires a funded escrow and a valid report, and the seller cannot call the escrow or the receiver. Instance: the worst case is early release on an order the buyer actually funded — a fraud that leaves a permanent, attributable on-chain record rather than an untraceable one.

Q93. The courier says DELIVERED but the buyer never received the parcel. What then?

Short: this is the system's hardest case, and the honest answer is that it is a dispute, not a bug. Reasoning: the oracle reports what the data source says; a wrong data source yields a wrong but valid settlement. Instance: mitigation today is the manual-review path and off-chain recourse; the report lists arbitration and multi-source verification as future work. Never claim the design solves physical fraud.

Q94. What stops a seller from generating a false delivery report?

Short: the report is not produced by the seller — it is produced by CRE from the API record, and accepted only from an authorised caller. Reasoning: the seller's leverage is limited to the API's write access, which is protected by a server-side secret and validated transitions. Instance: even a forged API record still needs a funded escrow and passes the receiver's single-settlement checks.

Q95. What if Chainlink returns incorrect information?

Short: the report would be wrong, and the contracts cannot detect that — they can only enforce authorisation and uniqueness. Reasoning: an oracle is a trust boundary; a DON reduces the chance of error or collusion but does not eliminate it. Instance: locally, one simulator runs the workflow, so the trust is even more concentrated; that is stated explicitly rather than glossed.

Q96. What if the bridge is compromised?

Short: it could suppress reports or submit a forged one, and the receiver would accept the forgery because the caller is authorised. Reasoning: authority is by address, not by content signature. Instance: the damage is bounded to one payout per funded order, and every submission is recorded on chain. A DON removes the bridge entirely, which is the real fix.

Q97. What if an admin key is stolen?

Short: the thief can reconfigure the oracle, mint pUSD, and settle through the manual path — but cannot directly drain escrowed funds to an arbitrary address. Reasoning: there is no sweep function; the escrow only pays the recorded buyer or seller. Instance: the mitigations are owner separation, event logging of every configuration change, and the recommendation of a multisig in production.

Q98. Why is a local execution bridge needed at all?

Short: because the SDK cannot address Hardhat and no DON was available, yet the settlement still had to be demonstrated for real. Reasoning: the alternative was either no on-chain settlement or a fake UI claim; the bridge keeps CRE as the decision-maker and produces real transactions. Instance: three verified settlements exist because of it.

Q99. Is your system actually decentralised?

Short: no — the custody and rules are on chain, but the oracle path is centralised in this deployment. Reasoning: one simulator, one bridge machine, one authorised account, one simulated data source. Instance: the honest phrasing is "trust-minimised custody with a centralised oracle, architected for a DON". Claiming more would be false and easily challenged.

Q100. Why didn't you deploy the workflow on the DON?

Short: access to a deployed DON was not available in this environment, and the SDK lacks a local chain selector. Reasoning: both are external constraints, not design choices. Instance: the workflow was still written to DON conventions — consensus aggregation, report interface, forwarder role — so deployment is a configuration change rather than a rewrite.

Q101. How is this different from traditional escrow?

Short: custody and rules are code, decisions are evidenced, and settlement is automatic. Reasoning: a traditional agent holds money and a human judges delivery; here no one holds the money and the judgement is a report you can audit. Instance: the buyer can verify the escrowed balance and the settlement transaction without asking anyone.

Q102. What would happen if Hardhat were restarted?

Short: every deployment, balance and escrow disappears; the addresses are reusable only after redeploying. Reasoning: the chain is in memory. Instance: the recovery order is redeploy → authorise → mint → re-register shipments; the bridge's preflight reports exactly which step is missing.

Q103. What happens if the API becomes unavailable?

Short: CRE logs an HTTP error and settles nothing; the system fails safe. Reasoning: no data means no decision, which is preferable to guessing. Instance: escrows remain Funded and can be settled later or manually, so availability affects liveness, not safety.

Q104. What if a shipment is returned after delivery?

Short: if it was already released, nothing automatic happens; if it is still funded, CRE routes RETURNED to manual review and emits no settlement report. Reasoning: a return after delivery is a dispute about facts, not a courier status. Instance: shouldSettle returns MANUAL_REVIEW, and the receiver would reject such an outcome anyway.

Q105. What is the single biggest limitation?

Short: the trust boundary at the oracle: a simulated data source and a single local relay. Reasoning: every other component is either enforced by code or verified by tests; this one rests on operational honesty. Instance: the contracts bound the consequences to one payout per funded order, which is why the limitation is survivable but must be stated first, not last.

14.6 Rapid fire

Q106. msg.sender versus tx.origin?

Short: msg.sender is the immediate caller; tx.origin is the EOA that started the chain. Reasoning: authorising on tx.origin enables phishing through an intermediate contract. Instance: ProofPay uses msg.sender everywhere, which is why the escrow sees the receiver as its caller.

Q107. Why not approve an unlimited allowance?

Short: because the approved spender could take everything at any time. Reasoning: least privilege; an exact approval limits blast radius to one order. Instance: ProofPay approves the order amount and the allowance is consumed at funding.

Q108. What is front-running, and are you exposed?

Short: observing a pending transaction and submitting one that profits from it. Reasoning: on a public mempool, transaction content and ordering are visible. Instance: ProofPay's settlement is keyed to a specific order and payee, so there is no price to manipulate; on a local chain there is no mempool race at all.

Q109. Calldata, memory and storage — one line each?

Short: calldata is immutable function input, memory is temporary working space, storage is permanent chain state. Instance: the report arrives as calldata, is decoded into memory, and only the two booleans and the escrow struct reach storage.

Q110. Why is the escrow's mapping private?

Short: because a getter that reverts on unknown orders is a better API than one returning a zeroed struct. Reasoning: silent zero values are a classic source of bugs. Instance: getEscrow reverts with EscrowNotFound.

Q111. Why does the report ID include the metadata?

Short: so two reports that differ only in provenance are treated as distinct. Reasoning: the metadata is part of what the caller asserted. Instance: locally metadata is 0x, so it contributes nothing, but the interface stays DON-compatible.

Q112. What if two reports arrive with identical fields in the same second?

Short: the second is rejected — identical bytes give an identical report ID. Reasoning: the tick is part of the report only if the source's timestamp is; identical timestamps mean a true duplicate. Instance: that is the behaviour you want; a genuine second settlement attempt must fail.

Q113. What if the bridge's state file is deleted?

Short: replay protection moves entirely to the chain, which already covers it. Reasoning: the state file is a convenience for idempotent local runs, not the security boundary. Instance: a resubmission would revert with ReportAlreadyProcessed or OrderAlreadySettled.

Q114. What if two bridges run at once?

Short: the lock file prevents it; if forced, the chain prevents a double payout. Reasoning: both would compute the same report ID and only one transaction could succeed. Instance: the observed runs show one submission per order and one block of advancement.

Q115. What if CRE emits MANUAL_REVIEW as a settlement?

Short: the bridge refuses it and the receiver would revert with UnsupportedOutcome. Reasoning: the system only has two payouts, and neither means "a human should look at this". Instance: shouldSettle never produces an outcome for RETURNED, so this is belt and braces.

Q116. Why is the seller's address checked in the backend as well as the escrow?

Short: defence in depth and better errors. Reasoning: the escrow check would only fail at settlement, long after the mistake. Instance: SELLER_MISMATCH is returned at registration time.

Q117. What is the role of block.timestamp in your design?

Short: recording when an escrow was created and settled. Reasoning: it is consensus-agreed and monotonic enough for audit timestamps, but miners can nudge it slightly, so it must never gate security. Instance: no authorisation or amount logic depends on it.

Q118. Why not store the tracking ID on chain?

Short: cost and privacy. Reasoning: arbitrary-length strings cost storage and leak parcel identity. Instance: the hash gives evidence without exposure, and the receiver only needs it for the report ID.

Q119. How do you know the frontend is not lying?

Short: because it reads the chain rather than trusting a server, and every displayed value can be re-derived with an independent RPC call. Reasoning: the UI could still be malicious, but it cannot fabricate a balance that the chain disagrees with. Instance: the verification script reproduces the dashboard's numbers from getEscrow and balanceOf.

Q120. What is the point of the EscrowCreated event if the UI re-reads state?

Short: discovery and indexing. Reasoning: there is no enumerable list of mapping keys on chain, so an event is the only efficient way to learn which IDs exist. Instance: useEscrows filters logs on the event topic and the escrow address.

Q121. Why does the receiver use a self-call for the funding check?

Short: so a missing escrow becomes EscrowNotFound instead of a raw revert from the external call. Reasoning: typed errors are easier to test and to explain. Instance: try this._checkEscrowFunded(orderId) ... catch { revert EscrowNotFound(orderId); }.

Q122. Why does the bridge read the escrow again if CRE already did?

Short: because time passed and state can change between the simulation and the submission. Reasoning: the read is a preflight, not a second decision; it prevents wasting gas on an order that closed. Instance: the dry-run log prints the seller and the 100 pUSD amount from that read.

Q123. What would you do differently if you started again?

Short: design the report export before the first settlement, and keep the bridge's validation and the contract's checks generated from one schema. Reasoning: the dry-run ordering bug cost real time and was only visible once exports were attempted. Instance: a shared report schema would also have made the report ID derivation impossible to drift.

Q124. Which part of this project are you proudest of, technically?

Short: the demonstration that both outcomes can be executed and independently verified, with the decision provably outside the relay. Reasoning: the interesting engineering is the boundary design, not the contracts. Instance: the allowlist run where CRE reported two shipments and exactly one transaction resulted.

Q125. If I gave you one week, what would you add?

Short: a Sepolia deployment with a verified receiver and a DON-hosted workflow, plus one real carrier sandbox integration. Reasoning: those three changes convert the honest local caveats into production-relevant evidence. Instance: the escrow and receiver need no redesign; only addresses, configuration and the removal of the bridge.

15.1 Resume entry

15.2 The 30-second introduction

"ProofPay is a blockchain payment-protection system for high-value online purchases. The buyer locks pUSD in a smart-contract escrow, a Chainlink CRE workflow reads the courier's shipment record and the escrow state, decides whether the delivery condition is met, and produces a signed-off report; a receiver contract enforces authorisation and replay protection and tells the escrow to pay the seller or refund the buyer. I built the three contracts, the CRE workflow, the local relay and the React front end, and verified both settlement paths on a local Hardhat chain."

15.3 The two-minute version

Structure it as problem, design, evidence, limitation. Problem: in high-value e-commerce, whoever acts first carries the risk, and existing protections replace that risk with an institution you cannot audit. Design: custody moves into a contract with no withdrawal path; the delivery fact comes from an off-chain API read by CRE rather than asserted by an administrator; the report carries order, outcome, tracking hash and timestamp; the receiver accepts it only from an authorised caller, only once, and only while the order is funded. Evidence: 31 contract tests and 17 API tests pass, and three settlements executed with receipts at blocks 24, 29 and 30 — a release, a refund and a second release, each moving exactly 100 pUSD and each advancing the chain by one block. Limitation: the workflow runs in the official CRE simulator with dry-run enabled and a local bridge relays the report, so this is real workflow execution, not DON consensus; and the courier is simulated.

15.4 The five-minute architecture answer

Walk the four layers and name one artefact per layer. Presentation: React reads chain state through MetaMask; the checkout sequences approve then createEscrow, waiting for each receipt. Contracts: the token, the escrow (Funded, Released, Refunded, oracle-only settlement), and the receiver (authorise, decode, de-duplicate, route). Oracle: CRE fetches the API, reads getEscrow at a finalised block, applies shouldSettle, encodes a four-field report, and logs structured records. Relay: the bridge validates those records, re-derives the report ID, checks the allowlist and funding, submits processReport from an unlocked account, and records the receipt. Then say what each layer cannot do — that is what makes the answer senior rather than descriptive.

15.6 Explaining your contribution honestly

You used AI coding agents on this repository. That is normal in 2026 and it is not a weakness, but the way you describe it determines whether it sounds like authorship or delegation. Say what you decided, not what you typed: "I chose to keep the decision in CRE and make the bridge policy-free, which is why the bridge has no copy of shouldSettle. Then demonstrate understanding of a detail only an author would know — the dry-run/report ordering fix, the 109-byte header, the allowlist run where two reports produced one transaction.

Three sentences never to say

"It is deployed on Chainlink's decentralised network." "It is production-ready and audited." "The courier integration works with real carriers." Each is false, and each invites a question that ends the interview badly. The accurate versions are stronger because they show judgement.

13.2 ProofPayUSD.sol

Purpose. Define the unit of account. Architecture. Two OpenZeppelin bases and three members: constructor, decimals, mint. Interactions. Called by the escrow (transferFrom, transfer) and by the admin (mint); read by the frontend and the evidence scripts. Flow. Deploy → mint to admin → transfer to buyer/seller → approve escrow → escrow pulls funds → escrow pays out.

Two details to be able to defend: decimals are explicit even though 18 is the default, and mint is the only privileged function. There is no burn, pause, blacklist or fee, so the escrow's "exact amount arrives" assumption always holds.

13.3 ProofPayEscrow.sol

Purpose. Hold money and release it exactly once, to exactly one party, on the oracle's instruction. Architecture. One enum, one struct, one mapping, an immutable token, a mutable oracle, five external functions and two private helpers. Interactions. Reads the token; is called by buyers (fund) and by the receiver (settle); read by the frontend and by CRE.

13.4 ProofPayCREReceiver.sol

Purpose. Turn an authorised report into exactly one settlement call. Architecture. Immutable escrow reference, two configurable authorised callers, two boolean mappings, two entry points that share one internal routine, and an ERC-165 advertisement. Interactions. Called by the forwarder (a DON) or the manual oracle (local/admin); calls the escrow's two settlement functions.

// The essential shape, in five lines:
decoded = abi.decode(report, (bytes32, string, bytes32, string));
reportId = keccak256(abi.encodePacked(orderId, outcome, trackingIdHash, observedAt, metadata));
require(!processedReports[reportId] && !orderSettled[orderId]);
require(escrowIsFunded(orderId));
outcome == "DELIVERED" ? escrow.confirmDelivery(orderId) : escrow.confirmFailure(orderId);

Flow, in words. Receive bytes → decode → build report ID → reject replay → reject duplicate order → verify funding via a self-call (so a missing escrow becomes a typed error) → hash the outcome string and branch → mark both mappings → emit two events. Anything unexpected reverts, and a revert changes nothing.

13.5 chainlink/cre/shipment-workflow/main.ts

Purpose. Fetch shipments, verify escrows, decide, and produce a report — and nothing else. Architecture. One cron handler; a pure decision function; an HTTP fetch helper; an ABI-encoding helper; a payload-extraction helper; two structured log emissions. Interactions. Calls the Express API over HTTP, the escrow over EVM, and writes to stdout for the bridge.

// Execution order inside onCronTrigger:
1. runtime.config                       → typed staging configuration
2. HTTPClient.sendRequest(consensusIdenticalAggregation)  → shipments JSON
3. JSON.parse with array-or-{shipments} tolerance
4. for each shipment:
     shouldSettle(status) → NONE / MANUAL_REVIEW ? log & continue
     encodeFunctionData(getEscrow) → EVMClient.callContract(LAST_FINALIZED_BLOCK_NUMBER)
     decodeFunctionResult → status !== 1 ? log & continue
     createReportPayload → prepareReportRequest → runtime.report
     extractAbiPayload → verify slice decodes to (orderId, outcome)
     log PROOFPAY_REPORT_V1 {type:"report"} and {type:"meta"}
     if (config.dryRun) { log "DRY RUN"; continue; }
     evmClient.writeReport(...)         // unreachable in this deployment

The two subtleties that mark this as real work rather than a tutorial: report generation is deliberately above the dryRun branch, and the payload extraction verifies which slice actually decodes rather than assuming a fixed 109-byte offset.

13.6 chainlink/cre/shipment-workflow/local-runner.ts

Purpose. Relay CRE's report to the receiver, safely and exactly once. Architecture. Roughly 1,180 lines in nine sections: constants and ABIs; configuration; logging and retry helpers; simulation spawner and line consumer; validation; state and locking; chain context and preflight; escrow reads and transaction preparation; the main loop and summary. Interactions. Spawns the CRE CLI, reads the HTTP-served chain through viem, and sends one transaction per eligible report.

13.7 chainlink/cre/shipment-workflow/courier-scheduler.ts

Purpose. Advance demo shipments on a timeline and optionally run CRE + bridge afterwards. Architecture. Config loader; nextStatus; due-checking with per-shipment delays; patchStatus; runBridge; a lock; a tick loop with idle-log suppression. Interactions. PATCHes the Express API; spawns the bridge. It never calls a contract.

The two functions to know: nextStatus(status, trackingId) which encodes the timeline and the -LOST convention, and tick(config) which filters due shipments, applies updates sequentially, and runs the bridge only if something changed.

13.8 The shipment service (backend)

Purpose. Be the authoritative off-chain record with strict transitions. Architecture. Router → service → store, with validation and errors as libraries. Interactions. The router is called by React and the scheduler; the service calls escrowChain.verifyEscrow over RPC; the store writes JSON.

router.post('/', mutationAccess, asyncHandler(async (req, res) => {
  const shipment = await shipmentService.register(req.body);
  res.status(201).location(`/api/shipments/${shipment.trackingId}`).json(shipment);
}));

// service.register():
normalizeCreateShipment(body) → assertNoDuplicates → verifyEscrow(orderId)
→ 404 ESCROW_NOT_FOUND | 409 ESCROW_NOT_FUNDED | 409 SELLER_MISMATCH
→ assertNoDuplicates again → build record with status CREATED + first event → store.add

Notice the deliberate double duplicate check around the async RPC call, and that the record's first event is created together with the record — there is no window in which a shipment exists without history.

13.9 The checkout page

Purpose. Turn a product selection into a funded escrow with as few failure modes as possible. Architecture. Controlled form state; validation in handleSubmit; transaction sequencing delegated to useEscrowActions; presentation only otherwise. Interactions. Reads token balance and allowance; sends approve then createEscrow; calls onCreated to trigger re-reads.

const busy = tx.phase === 'approving' || tx.phase === 'approved' || tx.phase === 'creating';
// validation before any wallet prompt:
if (!isValidAddress(sellerAddress)) next.seller = 'Enter a 0x address with 40 hex characters.';
else if (sellerAddress.toLowerCase() === ZERO_ADDRESS) next.seller = 'The zero address cannot receive funds.';
else if (sellerAddress.toLowerCase() === (wallet.address ?? '').toLowerCase())
  next.seller = 'The seller cannot be your own wallet.';
if (parsed.error) next.amount = parsed.error;

That block is worth quoting in an interview: it shows the UI enforcing the same invariants as the contract, before spending the user's time on a doomed signature. The contract still enforces them; the UI just fails fast.

13.10 The oracle panel (admin)

Purpose. Prove the wiring and allow a manual, receiver-mediated settlement. Architecture. Two useEffect reads (escrow.oracle() and receiver.manualOracle()), derived booleans receiverAuthorized and walletAuthorized, and a submit path that encodes a report client-side. Interactions. Reads through EIP-1193 eth_call; writes processReport from the connected account.

const receiverAuthorized = receiverDeployed && escrowOracleState?.toLowerCase() === addr.toLowerCase();
const walletAuthorized  = wallet.address?.toLowerCase() === receiverManualOracle?.toLowerCase();
// Both must be true before the panel offers "Confirm delivery" / "Confirm failure".

This panel is the manual counterpart to the automated pipeline, and it is genuinely useful: it is how the receiver path was validated before CRE existed, and it remains the diagnostic tool when the automated path misbehaves.

13.11 lib/receiver.ts

Purpose. Build a receiver call without any framework magic. Architecture. A minimal ABI (two entries), an environment reader, a mode flag, and one encoder. Interactions. Used by the oracle panel; mirrors the CRE payload exactly.

The important line is the zero tracking hash: the manual path has no tracking record, so it passes 0x0…0. The report ID remains unique because the order and timestamp differ. If asked why the manual path is weaker, this is the evidence: no tracking hash means no link to a courier record, which is precisely what the automated path provides.

Interview checkpoint — Module 13

Q. "Which file would you open first to understand the system?" A. ProofPayEscrow.sol, because it defines what money does; then ProofPayCREReceiver.sol for who may trigger it; then main.ts for how the decision is produced. The frontend and backend are consumers of those three.

MODULE 8THE LOCAL EXECUTION BRIDGE

This is the component that makes the local demonstration possible, and the one most likely to be misunderstood in an interview. Learn its boundaries before its code: the bridge carries a decision, it never makes one.

8.1 Why a bridge exists at all

A CRE workflow's normal on-chain write path is evmClient.writeReport(...), which targets a chain selected by a CRE chain selector. The installed SDK (1.23.0) has no selector for a local Hardhat node on chain ID 31337. Two consequences follow: the workflow cannot deliver a report to the local escrow by itself, and no DON was available to deploy to anyway.

So the workflow runs in the official CLI simulator with dryRun: true, producing a real report but no transaction. Something must carry that report the last metre. That something is local-runner.ts, a Node/Bun script that runs the simulator, parses its structured output, validates everything it can, and submits the exact bytes through processReport.

What this architecture is, and is not

It is: genuine CRE workflow execution (real HTTP fetch, real EVM read, real decision, real ABI encoding) plus a local relay.

It is not: a Chainlink DON, decentralised consensus, or DON-signed delivery. One machine runs the simulation and one unlocked local account submits. Anyone who says this is "oracle decentralisation" is wrong, and the receiver's checks — not the bridge — are what protect the funds.

8.3 Preflight: the part that saves you from yourself

const chainId = await withRetry("chain id", () => publicClient.getChainId());
if (chainId !== config.expectedChainId) failures.push(`Chain ID ${chainId} is not ${config.expectedChainId}.`);

const receiverCode = await publicClient.getCode({ address: config.receiver });
if (!receiverCode || receiverCode === "0x") failures.push(`No bytecode at receiver ${config.receiver}.`);

const unlocked = (await walletClient.getAddresses()).map(getAddress);
if (!unlocked.some(a => a.toLowerCase() === config.admin.toLowerCase()))
  failures.push(`Admin ${config.admin} is not an unlocked RPC account.`);

const manualOracle = await publicClient.readContract({ address: config.receiver, abi: RECEIVER_ABI, functionName: "manualOracle" });
if (getAddress(manualOracle).toLowerCase() !== config.admin.toLowerCase())
  failures.push(`receiver.manualOracle() is ${manualOracle}, but the bridge signer is ${config.admin}.`);

const oracle = await publicClient.readContract({ address: config.escrow, abi: ESCROW_ABI, functionName: "oracle" });
if (getAddress(oracle).toLowerCase() !== config.receiver.toLowerCase())
  failures.push(`escrow.oracle() is ${oracle}, expected the receiver.`);

Every one of those six checks corresponds to a real failure mode: wrong network, wrong addresses after a redeploy, an account MetaMask switched, a receiver whose manual oracle was rotated, an escrow still pointing at the admin EOA, and an empty gas balance. The observed output prints each line with "ok" or "MISMATCH", so a failing preflight tells you which fact is wrong without any further debugging. In the dry-run shown in the report, the block read chainId 31337 ok, receiver code 3583 bytes ok, escrow code 3274 bytes ok, admin unlocked ok (rpc accounts: 20), receiver.oracle … ok (== signer), escrow.oracle … ok (== receiver).

8.4 Validation: the bridge repeats the contract's checks, in TypeScript

if (!ORDER_ID_PATTERN.test(line.orderId)) problems.push("orderId is not a bytes32 hex string");
if (!SUPPORTED_OUTCOMES.includes(line.outcome))
  problems.push(`outcome "${line.outcome}" is not one of ${SUPPORTED_OUTCOMES.join(", ")}`);
if (meta.reportDecodesToReceiverAbi === false)
  problems.push("CRE reported that its bytes are not the receiver ABI payload");
if (meta.creDryRun === false)
  problems.push("CRE dryRun is false: CRE itself may submit reports. Refusing to bridge to avoid a duplicate settlement.");

const decoded = decodeAbiParameters(SETTLEMENT_REPORT_ABI, line.report);
if (decoded[0].toLowerCase() !== line.orderId.toLowerCase())
  problems.push("bytes decode to a different orderId than the line advertises");
if (decoded[1] !== line.outcome) problems.push("bytes decode to a different outcome");
if (decoded[2] === undefined || decoded[3] !== line.observedAt) problems.push("bytes decode to a different observedAt");

The creDryRun === false check is subtle and worth memorising: if someone flips CRE's own dry-run off, both CRE and the bridge could deliver the same report, and the second delivery would revert on replay. Rather than rely on that revert, the bridge refuses to run at all — a fail-closed design. The independent decode is the other notable choice: the bridge does not trust CRE's summary of what it produced; it decodes the bytes itself and requires them to agree with the advertised fields.

Report-ID recomputation mirrors the Solidity exactly:

const reportId = keccak256(encodePacked(
  ["bytes32", "string", "bytes32", "string", "bytes"],
  [line.orderId, line.outcome, decodedTrackingIdHash, decodedObservedAt, line.metadata]
));

Compare this with the receiver's keccak256(abi.encodePacked(orderId, outcome, trackingIdHash, observedAt, metadata)). Same fields, same order, same packing — so the two independently compute the same 32 bytes. If they diverged, the bridge's duplicate check would be useless and the contract's replay protection would still hold, but the logs would lie. Matching them is a correctness requirement, not a nicety.

8.5 Submission without a private key

const walletClient = createWalletClient({ account: config.admin, transport });
// Passing the account as an address makes viem use eth_sendTransaction,
// i.e. the Hardhat node's unlocked account. No key material is involved.
const hash = await walletClient.sendTransaction({ to: config.receiver, data: calldata });
const receipt = await publicClient.waitForTransactionReceipt({ hash });

This is the security highlight of the whole component: there is no CRE_ADMIN_PRIVATE_KEY anywhere, because the Hardhat node already holds the key and exposes the account as unlocked. A private key in an environment file would have been the most dangerous artefact in the repository; not having one removes a whole class of leak.

8.6 Idempotency, retries and state

The state file is a JSON document listing successful submissions. On startup the bridge loads it; before submitting it checks the report ID against it, and also against the chain's processedReports and orderSettled. On success it appends a record. On failure it does not retry: a reverted submission is reported, the cause is decoded from the revert data, and the process exits non-zero. Blind retries after an ambiguous failure are exactly how duplicate settlements happen, so the bridge refuses to guess.

8.7 What would change for a real DON deployment

  1. The workflow would be deployed to a DON with dryRun: false, and the shipment API would have to be publicly reachable over HTTPS with authentication, not localhost.
  2. The receiver's forwarder would be set to the DON's forwarder address, and the owner fallback branch in onlyAuthorized would be removed.
  3. The bridge would be deleted. writeReport would deliver the report; the receiver's replay and duplicate checks would remain the safety net.
  4. manualOracle would stay as a documented break-glass path with a multisig, or be removed.
  5. The EVM read would target a supported chain selector, and the escrow would be deployed on that same chain.
Interview checkpoint — Module 8

Q. "Isn't the bridge just re-implementing the oracle?" A. No: an oracle decides what the outside world says. The bridge never looks at a shipment; it reads CRE's output, refuses anything malformed, and submits. Remove the bridge and the decision still exists in CRE; remove CRE and the bridge has nothing to submit.

Q. "What stops the bridge from submitting a report twice?" A. Three things: its own state file, the receiver's processedReports, and its refusal to retry after any failure. The second is the only one that matters if the bridge's disk is wiped.

MODULE 9THE AUTOMATIC COURIER SCHEDULER

courier-scheduler.ts is the component that makes the demonstration self-driving. Its header comment states its limits better than any paraphrase: it pushes shipments through a timeline, then runs the existing CRE simulation and the existing bridge. It never decides a settlement, never touches the contracts, and never submits a transaction itself.

9.2 Status progression and the LOST convention

case "CREATED":    return "SHIPPED";
case "SHIPPED":    return "IN_TRANSIT";
case "IN_TRANSIT": return trackingId.toUpperCase().endsWith("-LOST") ? "LOST" : "DELIVERED";

The outcome of a shipment is decided by its tracking ID suffix: PPD-MACBOOK-001 ends in DELIVERED; PPD-DEMO-LOST ends in LOST. This is a courier fact generator, not a settlement rule, and the file says so. CRE still reads the resulting status and decides what it means.

9.3 One tick, in order

const due = shipments.filter(s => isDue(s, config));         // prefix + elapsed delay
if (due.length === 0) { logIdleOnce(`waiting:${waiting}`, ...); return 0; }

let updates = 0;
for (const shipment of due) {
  const target = nextStatus(shipment.status, shipment.trackingId);
  if (!target) continue;
  const updated = await patchStatus(config, shipment.trackingId, target);   // authenticated PATCH
  log(`[courier] ${shipment.trackingId}: ${shipment.status} -> ${updated.status}`);
  updates++;
}
if (updates > 0 && config.runBridge) {
  log(`[courier] ${updates} update(s); starting CRE workflow + local bridge`);
  await runBridge(config);
}

Three properties are worth naming. Updates are applied one at a time and awaited, so two shipments reaching a terminal state together cannot start two overlapping CRE executions. The bridge is started only after at least one successful update, so idle ticks cost nothing. And the bridge inherits LOCAL_BRIDGE_DRY_RUN, which defaults to true, so the scheduler cannot accidentally send money unless someone explicitly opted in.

A lock file (.courier-scheduler.lock) prevents two scheduler instances, using the same create-with-wx technique as the bridge and the same stale-pid recovery. The scheduler also logs its mode at startup: "DRY RUN - no transaction will be sent" versus "LIVE", plus the reminder that CRE's dry-run stays true and the bridge decides nothing.

9.4 The MacBook demonstration, step by step

  1. Buyer funds an escrow of 3,499 pUSD for the seller. The escrow exists and is Funded.
  2. Seller registers tracking ID PPD-MACBOOK-001 against that order. The API validates the escrow is funded and the seller matches, then stores status CREATED.
  3. Scheduler tick at t+10s: patches status to SHIPPED. An event is appended. The scheduler then starts CRE + bridge; CRE reports nothing yet because SHIPPED maps to NONE, and the bridge has no report to parse.
  4. Tick at t+20s: IN_TRANSIT. Same outcome: no report, escrow untouched.
  5. Tick at t+40s: DELIVERED, because the tracking ID does not end in -LOST. Now CRE's shouldSettle returns RELEASE, the escrow is still funded, and a 256-byte report is emitted.
  6. The scheduler's bridge run parses that report, validates it, and — if dry-run is off — submits processReport. The receiver checks authorisation, replay, duplicate and funding, calls confirmDelivery, and the seller receives 3,499 pUSD.
What was actually demonstrated

The three settlements executed on chain were 100 pUSD orders: 0x4d07…aaf3 (release, block 24), 0x0c34…1152 (refund, block 29) and 0xf694…c26434 (release, block 30). A 3,499 pUSD escrow was observed funded at block 32 but was not settled during the recorded work. So the MacBook narrative above describes the mechanism exactly as implemented, while the measured evidence comes from the 100 pUSD orders. Distinguishing the two is precisely the honesty an examiner rewards.

9.5 What changes for a LOST shipment

Only the final status. A tracking ID ending in -LOST transitions IN_TRANSIT → LOST, and from there everything is symmetric: CRE maps LOST to REFUND, the report carries outcome LOST, the receiver calls confirmFailure, and the escrow pays the buyer instead of the seller. The observed refund at block 29 did exactly this for 100 pUSD, with the buyer's balance rising from 4,007 to 4,107 and the seller's unchanged.

MODULE 10THE COMPLETE WALKTHROUGH: 3,499 pUSD FOR A MACBOOK

This module is the story you will tell in an interview. Each stage is given twice: first in plain English, as you would explain it to a non-technical friend, then technically, as you would defend it to an engineer.

Stage 1 — Purchase

Plain. The buyer chooses a MacBook, connects their wallet, and pays into a locked box that neither they nor the seller can open. The seller can see that the money exists but cannot touch it.

Technical. React generates a random 32-byte orderId, validates the seller address and the amount, then sends approve(escrow, 3499e18). After that receipt, it sends createEscrow(orderId, seller, 3499e18). The escrow validates six conditions, writes a Funded struct, pulls the tokens with safeTransferFrom, and emits EscrowCreated. Two receipts, two confirmations, 156k and 46k gas respectively. The buyer's balance drops by exactly 3,499 pUSD; the escrow's balance rises by the same amount.

Stage 2 — Seller registration

Plain. The seller says "I have shipped it, here is the tracking number". This goes into the courier's system, not the blockchain, because it will change several times.

Technical. POST /api/shipments with the mutation secret. The service normalises the input, rejects duplicates by tracking ID and by order, calls getEscrow over RPC, and requires status === 1 and escrow.seller === sellerAddress. It stores the record with status CREATED and the first event, and re-runs the duplicate check after the async call to close the race.

Stage 3 — Courier progress

Plain. Over the next minute the parcel moves: dispatched, in transit, delivered. Each step is recorded with a timestamp.

Technical. The scheduler polls GET /api/shipments, filters to PPD- records with elapsed delays, and sends authenticated PATCH requests. The service validates against SHIPMENT_TRANSITIONS inside the serialised store update and appends an event per change. A manual alternative exists in the admin dashboard's simulator; both paths hit the same endpoint and the same rules.

Stage 4 — CRE evaluation

Plain. An independent program reads the courier's record and the locked box, and decides whether the delivery condition is satisfied.

Technical. The cron-triggered workflow fetches GET /api/shipments through the HTTP capability with consensus aggregation, parses defensively, and for each terminal shipment encodes getEscrow and reads it through the EVM capability at the last finalised block. It skips anything not Funded, applies shouldSettle, and builds the four-field payload. The report is generated, the payload source is verified, and two structured log records are emitted.

Stage 5 — Local relay

Plain. Because the workflow cannot post to our local test chain directly, a small relay carries its signed-off decision the last step and submits it.

Technical. The bridge runs the simulation, parses only PROOFPAY_REPORT_V1: lines, joins report and meta by order ID, validates the outcome, decodes the bytes independently, recomputes the report ID, applies the allowlist, checks the escrow is still funded, and encodes processReport(0x, report). It sends the transaction from the unlocked admin account and waits for a successful receipt, then records the submission.

Stage 6 — Settlement

Plain. The receiver checks that the report is legitimate and unused, then tells the locked box to pay. Delivered means the seller is paid; lost means the buyer is refunded.

Technical. _processReport decodes, derives the report ID, checks processedReports, orderSettled and the funding self-call, then branches on the outcome hash. confirmDelivery writes Released and transfers to the seller; confirmFailure writes Refunded and transfers to the buyer. Both emit settlement events; the receiver marks both mappings and emits ReportProcessed and SettlementExecuted.

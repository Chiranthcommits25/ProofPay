Three habits make the material stick. First, read with the repository open. MODULE 1UNDERSTANDING THE INTERNET AND BLOCKCHAIN FROM ZERO

You cannot understand escrow until you understand what it means for a program to hold money, and you cannot understand that until you understand where programs live and who can change their data. This module builds those foundations in the order a newcomer needs them: the web first, then the ledger, then the transaction, then the machine that runs contracts, then the cryptography that makes any of it trustworthy.

1.1 How the internet works, and where ProofPay sits in it

Almost every interaction in ProofPay is one of two shapes: a request to a server, or a transaction to a blockchain. Both are messages; the difference is who is allowed to change the record afterwards.

A client is a program that asks for something: your browser, or inside it, the React application. A server is a program that answers: here, the Express service on port 5001, or the Hardhat node on port 8545. Between them travel requests and responses. In the browser-to-backend case the protocol is HTTP; in the browser-to-blockchain case it is JSON-RPC, which is HTTP with a fixed message format for chain operations.

Frontend means the code running inside your browser tab: React components, TypeScript, CSS, and an injected wallet provider. Backend means code running in a separate process that the browser cannot inspect or edit: the shipment API with its JSON file. The split matters because a frontend is under the user's control. Anything the frontend decides can be changed by a determined user with developer tools. That is exactly why ProofPay's rule, "the buyer's funds may only move when the delivery condition is satisfied", is enforced in Solidity and not in React.

An API (application programming interface) is an agreed set of addresses and message shapes for talking to a program. ProofPay's shipment API, for example, defines five endpoints. A database is durable storage. Big systems use PostgreSQL or MongoDB; this project deliberately uses a single JSON file at backend/data/shipments.json, written atomically, because the teaching goal is the oracle pipeline rather than database engineering.

JSON (JavaScript Object Notation) is the text format both sides agree on. A real shipment record from this project looks like this:

Authentication answers "who is allowed to do this?". ProofPay uses three different answers in three places, and confusing them is a classic interview mistake. The shipment API uses a shared secret header on mutating routes (requireMutationAccess), because only the seller client and the demo scheduler should write. The blockchain uses cryptographic signatures: a transaction is only valid if it is signed by the private key behind the sending address. MetaMask is where that signature happens. And the contracts use role checks (onlyOwner, onlyOracle, onlyAuthorized), which are authorisation rules layered on top of the signature.

1.2 What a blockchain is, and why it exists

Start with the problem rather than the definition. Suppose two strangers want to exchange money for goods over the internet. Somebody has to go first. If the buyer pays first, the seller may vanish. If the seller ships first, the buyer may never pay. The usual answer is an institution in the middle: a bank, a marketplace, an escrow agent. That works, but it means the rule that decides who wins a dispute lives in a private database, applied by staff, visible to nobody.

A blockchain is a distributed ledger: a database replicated across many independent computers (nodes), where every change is a signed transaction, changes are grouped into blocks, and blocks are chained together by cryptographic hashes so that altering an old block invalidates every block after it. Because many nodes hold copies and compare them, there is no single machine whose edit becomes truth. The interesting part is not "many copies"; it is that the copies agree on rules for what counts as a valid change, and that agreement (consensus) is what lets strangers rely on the record without trusting each other.

Hashing is the glue. A hash function takes any input and returns a fixed-length fingerprint: change one character and the fingerprint changes completely, but the same input always gives the same fingerprint. ProofPay uses Keccak-256, which returns 32 bytes. You will meet it in three places: block linkage (not your code), order IDs (32 random bytes, treated as an identifier), and report IDs (keccak256 of the order, outcome, tracking hash, timestamp and metadata). The report ID is what makes replay detectable: the same report hashes to the same 32 bytes, so the receiver can recognise it.

Digital signatures are the other half. A private key signs; anyone holding the matching public key can verify the signature but cannot produce a new one. An Ethereum address is derived from the public key, so "verify the signature, recover the signer's address, compare it with the sender field" is enough to prove who authorised a transaction. This is why nobody can move your pUSD by editing a request in the browser: without your key, there is no valid signature, and the node rejects the transaction before any contract runs.

Analogy, then the reality

Think of a blockchain as a shared notebook kept by a hundred people, where each page's first line is a fingerprint of the previous page. Tearing out a page changes every later fingerprint, so the forgery is visible to everyone holding a copy.

Technically: each block header commits to its parent's hash, so rewriting history requires redoing all subsequent proof-of-work or consensus participation, on the majority of the network, faster than honest nodes extend the chain. On the local Hardhat chain, this security property is absent by design — one machine mines instantly and you can restart it and erase everything. That is why this project never claims mainnet security.

Immutability, therefore, is not magic: it is the cost of rewriting history. Transparency is the consequence of replication: every participant can read every transaction. Decentralisation is the degree to which no single party can unilaterally decide what happens next. ProofPay gets strong immutability and transparency from the chain, but its oracle path is only partially decentralised, and the honest answer to "is this decentralised?" is discussed in Module 11 and rehearsed in Module 14.

1.3 How a blockchain transaction works

Here is the full path of one ProofPay action — a buyer funding a 3,499 pUSD escrow. Read it once as a story, then again as a checklist, because interviewers ask you to narrate exactly this.

  1. The user initiates an action. The buyer clicks "Fund escrow". React has already validated the form and knows the amount, the seller address and a freshly generated 32-byte order ID.
  2. The wallet prepares a transaction. The app calls eth_sendTransaction through the injected provider. MetaMask builds an unsigned transaction: from, to (the escrow contract), value (0, because pUSD is an ERC-20 not ETH), data (the encoded createEscrow call), gas parameters and the next nonce.
  3. The transaction is signed. MetaMask shows the details and asks for confirmation. On approval it signs the transaction hash with the buyer's private key. The key never leaves the extension.
  4. The transaction is broadcast. The signed bytes go to the RPC endpoint — here http://127.0.0.1:8545, the Hardhat node.
  5. A node validates it. The node checks the signature, the nonce, the balance for gas, the chain ID and the intrinsic gas; malformed or unauthorised transactions never reach a contract.
  6. It is included in a block. Hardhat mines it immediately. On a public chain this is where validators or miners compete; here it is deterministic.
  7. The contract executes. The EVM runs createEscrow: validations, struct write, then paymentToken.safeTransferFrom(buyer, escrow, 3,499e18), which calls the token contract, which checks the allowance and moves the balance.
  8. State changes. The escrow's storage now holds a Funded record; the token's balances are updated; events are queued.
  9. A receipt is returned. The app polls eth_getTransactionReceipt, sees status: 1, reads the logs, and refreshes the dashboard.

What happens when a transaction fails

Failure comes in three flavours, and telling them apart is an interview skill in itself. Rejected in the wallet: the user pressed cancel, so nothing was broadcast, no gas was spent, and the app should say "you rejected the request" rather than "transaction failed". Reverted during execution: the transaction was mined, gas was consumed, but the contract threw. In Solidity 0.8 a revert rolls back all state changes, which is why a failed settlement leaves the escrow untouched. The receipt shows status: 0, and modern tooling can decode the revert reason — ProofPay uses custom errors such as EscrowNotFunded(orderId) so the reason is precise and cheap. Never mined: the transaction sits in the mempool because the gas price is too low or a nonce gap exists; here it appears as "pending forever".

Common misconception

"A reverted transaction still transfers the tokens because the transfer happened before the revert." False. Reverts are atomic: the EVM discards every state change made by the whole call, including nested calls into the token contract. The only thing permanently consumed is gas, which is why a reverted settlement costs the sender fees but moves no pUSD.

1.4 Ethereum and the EVM

Ethereum is a network whose state is a key-value store maintained by thousands of nodes, plus a virtual machine that can modify that store according to code that users deploy. Solidity compiles to EVM bytecode; the bytecode is what actually runs. "EVM-compatible" networks (Polygon, Arbitrum, Base, BNB Chain, and your local Hardhat node) implement the same instruction set and RPC conventions, which is why the same contracts and the same frontend work on any of them — only the chain ID and addresses change.

There are two kinds of account, and ProofPay depends on both. An externally owned account (EOA) is controlled by a private key: the buyer, the seller, the admin. A contract account has code and storage and no key: the token, the escrow, the receiver. An EOA initiates transactions. A contract can only act when called, either by an EOA or by another contract — which is exactly how the receiver becomes the escrow's oracle: the admin calls the receiver, and the receiver calls confirmDelivery, so the escrow sees msg.sender = receiver, not the admin.

That is precisely why useEscrows uses logs to discover order IDs and then calls getEscrow to read the data: discovery is cheap and indexable; truth comes from storage.

1.5 Cryptographic foundations you will actually be asked about

Hashing. Keccak-256 maps any bytes to 32 bytes, deterministically and irreversibly. Properties that matter: the same input always yields the same output (so a report ID can be recomputed by anyone); a one-bit change scrambles the whole output (so tampering is detectable); and you cannot feasibly find two inputs with the same output (so an attacker cannot substitute a different report for the same ID). In this project, hashing appears in the block chain itself, in order IDs, in keccak256(toHex(trackingId)) inside the report, in report IDs, and in ABI function selectors.

Signatures. Ethereum uses ECDSA over secp256k1. A signature proves that the holder of a private key approved a specific 32-byte digest. The digest for a transaction covers the chain ID, nonce, gas, recipient, value and data, so a signature cannot be replayed on another chain or reused for a different call. When MetaMask shows you a scary-looking hex blob and asks you to confirm, that is the digest you are authorising.

Address derivation. Address = last 20 bytes of keccak256(publicKey) for an EOA. For a contract, the address is keccak256(rlp(sender, nonce))[12:] — which is why, on a fresh Hardhat node, deployments land at the familiar sequence 0x5FbD…, 0xe7f1… from the same account: same deployer, increasing nonce.

Why contracts cannot trust arbitrary external information. This is the seed of Module 7. A contract is deterministic: every node must compute the same result from the same inputs, or consensus breaks. If Solidity could perform an HTTP GET, two nodes could receive different responses (or none), and the chain would fork on the answer. Therefore external facts must be pushed into the chain by a transaction, and the only question that matters is who is allowed to push, and what evidence they attach. Everything in this project's oracle design — the receiver's authorisation, the report's provenance fields, the replay protection — exists because of that single constraint.

Interview checkpoint — Module 1

Q. "Why can't the escrow contract just call the courier's API when the parcel is delivered?" Model answer. Because execution must be deterministic and every node must agree on the same state transition; an HTTP call is non-deterministic and unavailable inside the EVM. So the fact has to arrive as part of a transaction, and something off chain must decide to send it. In ProofPay that something is a Chainlink CRE workflow, and the contract's protection is that it will only accept the report from an authorised caller, only once, and only while the order is still funded.

MetaMask is where most beginners' understanding collapses into "the wallet thing". This module fixes that. By the end you should be able to explain what MetaMask stores, what it refuses to store, what it does when a site calls it, and why ProofPay needs two separate confirmations to fund one escrow.

2.1 What MetaMask actually is

MetaMask is a browser extension that (a) holds encrypted private keys, (b) signs transactions and messages on your behalf, and (c) injects a JavaScript object into every page at window.ethereum so that websites can request those signatures. It is also a lightweight wallet UI and a network switcher.

What it stores: an encrypted vault containing your seed phrase and derived keys, your selected network and account, and a local transaction history. What it does not store: your cryptocurrency. The tokens and ETH are entries in the blockchain's state. If you delete the extension and reinstall it with the same seed phrase, your balance reappears instantly, because the balance never lived in the extension. This is the single most useful sentence for explaining wallets to a non-technical audience.

An address is your public identifier: 0x7099…79C8. Anyone can send to it; nobody can spend from it without the key. ProofPay displays addresses shortened for readability (0x7099…79c8) but always sends full 20-byte values to the chain, because a shortened address is not a valid address.

2.2 Private keys, seed phrases, importing versus connecting

A seed phrase (12 or 24 words) is the master secret. Every account in the wallet is derived from it by a deterministic process (BIP-39 for the mnemonic, BIP-32/BIP-44 for derivation paths). Importing an account means giving the wallet either the seed phrase or a raw private key so that it can control that account. Connecting a site means granting that site permission to see your address and ask for signatures — it never gives the site your key.

They exist only for local development. Never send real funds to them, never reuse them on a public network, and never paste them into a website. This guide deliberately contains no key material.

2.3 Accounts, networks, chain IDs and our local configuration

One wallet can hold many accounts (different addresses derived from the same seed) and can point at many networks (different chains). The chain ID is the crucial field: it is included in the signed transaction, so a transaction signed for chain 31337 cannot be replayed on Ethereum mainnet. 2.5 The real transaction lifecycle in ProofPay

Funding one escrow involves two transactions, and the reason is an ERC-20 design decision, not an accident. A contract cannot move tokens out of your wallet unless you have authorised it to. That authorisation is itself a state change on the token contract, so it needs its own transaction.

Table 2.4: Two transactions, one purchase
#TransactionWho executes whatWhat it means / what you see

Why not one transaction? Because the token contract is the only thing that may debit your balance, and it will only do so for an address you have approved. Combining them would require the token to trust an arbitrary caller, which would let any contract drain any wallet. The allowance indirection is the security feature; the extra click is its cost. (EIP-2612 permit and EIP-3009 transferWithAuthorization allow signature-based single-transaction flows for tokens that implement them; pUSD, built on OpenZeppelin's plain ERC-20, does not.)

Signing a message versus signing a transaction. A message signature (EIP-191/712) proves you control an address at a point in time; it changes no state and costs no gas. A transaction signature authorises a state change, is broadcast, costs gas and produces a receipt. ProofPay's flows are all transactions; the only message-ish interaction is the wallet connection itself.

3.1 What a smart contract is, precisely

A smart contract is a program deployed to a blockchain, where it receives an address, keeps its own storage, and can only be changed by sending it a transaction. Three properties distinguish it from a backend function:

  • Deterministic execution. Every node computes the same result from the same input. No randomness, no clock, no network, no filesystem. block.timestamp is the only time available, and it is the block's time, agreed by consensus.
  • Persistent, public state. Storage survives forever and anyone can read it. That is why ProofPay writes only the escrow's essentials and keeps product names, descriptions and tracking IDs off chain.
  • No owner override. Once deployed, the code cannot be patched. ProofPay's escrow deliberately has no pause, upgrade or sweep function; the only mutable configuration is the oracle address.

The practical consequence: a bug in a backend can be fixed in ten minutes; a bug in a contract that holds money is permanent. That asymmetry explains the project's conservatism — small functions, explicit checks, OpenZeppelin for anything standard, and 31 tests for 300 lines of Solidity.

3.3 ERC-20, from first principles

A token is not a special kind of coin; it is a row in a contract's storage. ERC-20 is a standard interface for such rows so that wallets, exchanges and other contracts can treat every token the same way. The standard requires six functions (totalSupply, balanceOf, transfer, allowance, approve, transferFrom) and two events (Transfer, Approval).

Why are approve and transferFrom separate? Because otherwise any contract you call could take everything you own. The allowance is a capability you grant deliberately, for a specific spender, up to a specific amount.   2. Buyer calls createEscrow(orderId, seller, 3499e18) on the escrow.
  3. Escrow calls pUSD.transferFrom(buyer, escrow, 3499e18).
  4. pUSD checks allowance[buyer][escrow] >= 3499e18 and balanceOf(buyer) >= 3499e18, moves the balance, decrements the allowance, emits Transfer.
  5. Escrow emits EscrowCreated and returns. The buyer's wallet is 3,499 pUSD lighter; the escrow contract is 3,499 pUSD heavier; nobody can spend it.

Why not send funds straight to the seller and refund from the seller if lost?

Because the seller would have to be trusted to return money. Escrow inverts the trust: the money sits in a contract that neither party controls, and the only question is who can prove the condition. That is also why the escrow has no owner-withdrawal path — an "emergency" admin function is exactly the backdoor users would criticise in an audit.

function _processReport(bytes calldata metadata, bytes calldata report) internal {

        abi.encodePacked(orderId, outcome, trackingIdHash, observedAt, metadata)
    );

    if (orderSettled[orderId]) revert OrderAlreadySettled(orderId);

    try this._checkEscrowFunded(orderId) returns (bool funded) {
        if (!funded) revert EscrowNotFunded(orderId);
    } catch { revert EscrowNotFound(orderId); }

    bytes32 outcomeHash = keccak256(bytes(outcome));
    if (outcomeHash == keccak256(bytes("DELIVERED"))) {
        escrow.confirmDelivery(orderId);
        processedReports[reportId] = true;
        orderSettled[orderId] = true;
        emit ReportProcessed(orderId, outcome, reportId);
        emit SettlementExecuted(orderId, true);

        processedReports[reportId] = true;
        orderSettled[orderId] = true;
        emit ReportProcessed(orderId, outcome, reportId);
        emit SettlementExecuted(orderId, false);
    } else {
        revert UnsupportedOutcome(outcome);
    }
}

Note what the receiver does not do: it does not verify a signature, because authorisation comes from the caller's address; it does not re-derive the outcome from anything, because the outcome is CRE's decision; and it does not know the seller or the amount, because the escrow owns those facts. It is a policy boundary, and keeping it narrow is what makes it reviewable.

3.7 Solidity security, using your own code as the case study

Reentrancy

Reentrancy is an attack where an external call lets the callee call back into your contract before your state is final. With a token that had a malicious hook, safeTransfer could re-enter confirmDelivery and pay twice. Two defences stop it here. ReentrancyGuard sets a storage flag so a nested call reverts with ReentrancyGuardReentrantCall. And the state is already terminal before the transfer, so even without the guard a second entry would hit EscrowNotFunded. The test suite includes a reentrant createEscrow case precisely to keep both defences honest.

SafeERC20

Some tokens return false instead of reverting on failure, and some return nothing at all. A plain transfer call that ignores the return value can therefore "succeed" without moving anything. SafeERC20 checks the return data and reverts if the call failed, so the escrow's accounting cannot drift from reality. pUSD itself behaves, but the escrow is written to survive a less cooperative asset.

6.2 Middleware, validation and the five-layer write path

Middleware is a function that runs before the handler. requireMutationAccess is the security middleware: it compares a shared secret header against configuration and returns 401 when it is absent or wrong. It exists because the API is intentionally reachable on localhost by the browser, but only the seller client and the scheduler should be able to change a status.

Validation lives in lib/validation.js, not in the route. normalizeCreateShipment checks the order ID is 32 bytes of hex, the tracking ID is non-empty and conforms to the expected pattern, the carrier is a string, and the seller address is a valid 20-byte hex address; it lowercases addresses so comparisons with chain data are reliable. normalizeStatusUpdate rejects unknown statuses. Rejecting bad input at the edge means every later layer can assume clean data — but each later layer still validates, because a service can be called from somewhere else tomorrow.

6.3 Registering a shipment: the real sequence

  1. Seller opens Incoming Escrows, selects a funded order, and enters a tracking ID such as PPD-MACBOOK-001.
  2. The React app sends POST /api/shipments with the order ID, tracking ID, carrier label, its own address and a description, plus the mutation secret header.
  3. register() normalises the body, then calls assertNoDuplicates: no existing shipment with that tracking ID, none for that order.
  4. It then calls chainVerifier.verifyEscrow(orderId), a read-only RPC call to getEscrow.
  5. Three chain-level facts are enforced: the escrow exists (404 if not), its status is 1 = Funded (409 if released/refunded), and its seller equals the registered seller address (409 SELLER_MISMATCH).
  6. The duplicate checks run again — after the async RPC — to close the window in which two concurrent requests could both pass.
  7. Finally the record is built with status: "CREATED", simulated: true, timestamps from an injectable clock, and the first event in its history.

Step 5 is the answer to "what stops a seller from registering a shipment for an order that does not exist?". The backend refuses, and even if it did not, the CRE workflow independently checks the escrow's status before reporting, and the receiver checks again before paying. Three layers, same fact.

6.5 Persistence: one file, written carefully

shipmentStore.js keeps the collection in memory and mirrors it to backend/data/shipments.json. Writes go to a temporary file and are then renamed over the target, so a crash mid-write cannot leave a truncated JSON document. Writes are serialised through a promise chain, so concurrent requests queue rather than interleave. Reads are served from memory, which is why the CRE HTTP call is cheap.

This is not production storage, and the guide says so plainly: no indexing, no transactions across entities, no replication, no access control at rest. For a teaching project whose subject is the oracle pipeline, a single atomic file is the right trade — it makes the data source inspectable with cat, which is exactly what a viva needs.

6.6 Why seller registration is separate from escrow creation

They are different facts recorded by different parties on different systems. The escrow records a financial obligation: this buyer has locked this amount for this seller. The shipment record describes physical fulfilment: this parcel with this tracking number is moving. If registration were part of createEscrow, the buyer would have to know a tracking number that does not exist yet, and the escrow contract would have to store a string, paying permanent storage costs for data that changes six times.

Separating them also creates the cross-check that makes the oracle meaningful: the backend verifies that the order is funded and that the seller matches before accepting a shipment. Neither system can lie alone; the chain supplies the financial fact, the API supplies the physical fact, and CRE is the component that joins them.

Interview checkpoint — Module 6

Q. "Why not put shipment status on chain?" A. Cost, mutability and privacy. Six status updates per order would cost gas each time, and a mis-scan would be permanent. Keeping it off chain means it can be corrected, while the money stays on chain where corrections are unnecessary.

Q. "Who can fake a shipment?" A. Anyone holding the API's mutation secret, which is server-side only. But a fake status cannot move money unless the escrow is funded and unspent, and the settlement itself is limited to one payout per order by the receiver and the escrow.

7.1 The oracle problem, stated simply and then precisely

A smart contract is a sealed room: it can compute, it can read its own storage, and it can call other contracts, but it cannot look outside the blockchain. It has no network access, no clock beyond the block timestamp, and no way to ask "did the parcel arrive?". This is not an oversight; it is what makes consensus possible. Every node must compute the same answer, so every input must already be on chain.

Therefore any fact about the real world has to be carried in by a transaction. The carrier is called an oracle. The oracle problem is: how do you get a trustworthy external fact into a system that cannot verify it, without reintroducing a single point of trust?

function shouldSettle(shipment: { status: string }): SettlementDecision {
  switch (shipment.status) {
    case "DELIVERED": return { action: "RELEASE", outcome: "DELIVERED", reason: "..." };
    case "LOST":      return { action: "REFUND",  outcome: "LOST",      reason: "..." };
    case "IN_TRANSIT":
    case "SHIPPED":   return { action: "NONE",    reason: "payment remains locked" };
    case "RETURNED":  return { action: "MANUAL_REVIEW", reason: "requires manual review" };
    case "CREATED":   return { action: "NONE",    reason: "not ready for settlement" };
    default:          return { action: "NONE",    reason: `Unknown shipment status: ${shipment.status}` };
  }
}

This function is the project's entire settlement policy, and it lives in exactly one place. The bridge has no copy of it. If an interviewer asks "where is the decision made?", point here.

Stage 2 — fetch the shipment list over HTTP, with consensus aggregation

Three things to notice. The request is wrapped in consensusIdenticalAggregation<string>(), which in a DON deployment means every node fetches and the results must be byte-identical before the workflow continues — that is how a single lying node is outvoted. In the local simulator there is one node, so the consensus wrapper is exercised but proves nothing; say that honestly. Second, failures throw, and the handler catches them and returns an error string, so a dead API results in "HTTP error" and zero settlements rather than a partial run. Stage 5 — extract the exact bytes, and prove they are the right bytes

The SDK prefixes a 109-byte metadata header to the encoded body. The receiver decodes the body only, so sending the raw report would corrupt the first field. The workflow therefore tries both candidates and accepts the one that decodes to the expected order and outcome:

const creRawReportHex = bytesToHex(report.rawReport());

return { payloadHex: creRawReportHex, payloadSource: "unverified", creRawReportHex };

In every observed run the source was body, the payload was 256 bytes, the raw report 365 bytes, and 365 − 256 = 109 exactly matches REPORT_METADATA_HEADER_LENGTH. That arithmetic is the cleanest evidence that the header was stripped correctly, and it is the kind of detail that makes an interviewer believe you built the thing.

The sequencing is the single most important repair in the project's history. In the original code the dryRun check came before runtime.report, so with dry-run enabled — the safe setting — no report object was ever produced and nothing could be captured. Moving generation above the branch is what made the entire local pipeline possible: the report exists in both modes, and only its on-chain destination is conditional.

The two log lines exist because the CRE runtime truncates user log lines at roughly one kilobyte. The payload alone is 512 hex characters, so provenance is emitted separately and the bridge rejoins the two records by order ID. That constraint, and the workaround, is a good story about reading your tools' limits instead of fighting them.

Interview checkpoint — Module 7

Q. "Why hash the tracking ID?" A. Two reasons: the hash ties the settlement to a specific courier record as evidence, and it avoids publishing the tracking number on a public ledger, which would leak shipping details. The receiver stores it only as part of the report ID.

Q. "Does consensus aggregation prove your oracle is decentralised?" A. No. The code is written for it, but in this deployment the simulator runs one node, so no independent agreement happens. Real decentralisation requires the workflow deployed to a DON with multiple operators, which was out of scope.

MODULE 8THE LOCAL EXECUTION BRIDGE

This is the component that makes the local demonstration possible, and the one most likely to be misunderstood in an interview. Learn its boundaries before its code: the bridge carries a decision, it never makes one.

8.1 Why a bridge exists at all

A CRE workflow's normal on-chain write path is evmClient.writeReport(...), which targets a chain selected by a CRE chain selector. The installed SDK (1.23.0) has no selector for a local Hardhat node on chain ID 31337. Two consequences follow: the workflow cannot deliver a report to the local escrow by itself, and no DON was available to deploy to anyway.

So the workflow runs in the official CLI simulator with dryRun: true, producing a real report but no transaction. Something must carry that report the last metre. That something is local-runner.ts, a Node/Bun script that runs the simulator, parses its structured output, validates everything it can, and submits the exact bytes through processReport.

What this architecture is, and is not

It is: genuine CRE workflow execution (real HTTP fetch, real EVM read, real decision, real ABI encoding) plus a local relay.

It is not: a Chainlink DON, decentralised consensus, or DON-signed delivery. One machine runs the simulation and one unlocked local account submits. Anyone who says this is "oracle decentralisation" is wrong, and the receiver's checks — not the bridge — are what protect the funds.

The creDryRun === false check is subtle and worth memorising: if someone flips CRE's own dry-run off, both CRE and the bridge could deliver the same report, and the second delivery would revert on replay. Rather than rely on that revert, the bridge refuses to run at all — a fail-closed design. The independent decode is the other notable choice: the bridge does not trust CRE's summary of what it produced; it decodes the bytes itself and requires them to agree with the advertised fields.

Report-ID recomputation mirrors the Solidity exactly:

const reportId = keccak256(encodePacked(
  ["bytes32", "string", "bytes32", "string", "bytes"],
  [line.orderId, line.outcome, decodedTrackingIdHash, decodedObservedAt, line.metadata]
));

Compare this with the receiver's keccak256(abi.encodePacked(orderId, outcome, trackingIdHash, observedAt, metadata)). Same fields, same order, same packing — so the two independently compute the same 32 bytes. If they diverged, the bridge's duplicate check would be useless and the contract's replay protection would still hold, but the logs would lie. Matching them is a correctness requirement, not a nicety.

8.6 Idempotency, retries and state

The state file is a JSON document listing successful submissions. On startup the bridge loads it; before submitting it checks the report ID against it, and also against the chain's processedReports and orderSettled. On success it appends a record. On failure it does not retry: a reverted submission is reported, the cause is decoded from the revert data, and the process exits non-zero. Blind retries after an ambiguous failure are exactly how duplicate settlements happen, so the bridge refuses to guess.

8.7 What would change for a real DON deployment

  1. The workflow would be deployed to a DON with dryRun: false, and the shipment API would have to be publicly reachable over HTTPS with authentication, not localhost.

Interview checkpoint — Module 8

Q. "Isn't the bridge just re-implementing the oracle?" A. No: an oracle decides what the outside world says. The bridge never looks at a shipment; it reads CRE's output, refuses anything malformed, and submits. Q. "What stops the bridge from submitting a report twice?" A. Three things: its own state file, the receiver's processedReports, and its refusal to retry after any failure. The second is the only one that matters if the bridge's disk is wiped.

9.3 One tick, in order

const due = shipments.filter(s => isDue(s, config));         // prefix + elapsed delay

  const target = nextStatus(shipment.status, shipment.trackingId);
  if (!target) continue;
  const updated = await patchStatus(config, shipment.trackingId, target);   // authenticated PATCH
  log(`[courier] ${shipment.trackingId}: ${shipment.status} -> ${updated.status}`);

  log(`[courier] ${updates} update(s); starting CRE workflow + local bridge`);
  await runBridge(config);
}

Three properties are worth naming. Updates are applied one at a time and awaited, so two shipments reaching a terminal state together cannot start two overlapping CRE executions. The bridge is started only after at least one successful update, so idle ticks cost nothing. And the bridge inherits LOCAL_BRIDGE_DRY_RUN, which defaults to true, so the scheduler cannot accidentally send money unless someone explicitly opted in.

A lock file (.courier-scheduler.lock) prevents two scheduler instances, using the same create-with-wx technique as the bridge and the same stale-pid recovery. The scheduler also logs its mode at startup: "DRY RUN - no transaction will be sent" versus "LIVE", plus the reminder that CRE's dry-run stays true and the bridge decides nothing.

9.4 The MacBook demonstration, step by step

  1. Buyer funds an escrow of 3,499 pUSD for the seller. The escrow exists and is Funded.
  2. Seller registers tracking ID PPD-MACBOOK-001 against that order. The API validates the escrow is funded and the seller matches, then stores status CREATED.
  3. Scheduler tick at t+10s: patches status to SHIPPED. An event is appended. The scheduler then starts CRE + bridge; CRE reports nothing yet because SHIPPED maps to NONE, and the bridge has no report to parse.
  4. Tick at t+20s: IN_TRANSIT. Same outcome: no report, escrow untouched.
  5. Tick at t+40s: DELIVERED, because the tracking ID does not end in -LOST. Now CRE's shouldSettle returns RELEASE, the escrow is still funded, and a 256-byte report is emitted.
  6. The scheduler's bridge run parses that report, validates it, and — if dry-run is off — submits processReport. The receiver checks authorisation, replay, duplicate and funding, calls confirmDelivery, and the seller receives 3,499 pUSD.
What was actually demonstrated

The three settlements executed on chain were 100 pUSD orders: 0x4d07…aaf3 (release, block 24), 0x0c34…1152 (refund, block 29) and 0xf694…c26434 (release, block 30). 9.5 What changes for a LOST shipment

Only the final status. A tracking ID ending in -LOST transitions IN_TRANSIT → LOST, and from there everything is symmetric: CRE maps LOST to REFUND, the report carries outcome LOST, the receiver calls confirmFailure, and the escrow pays the buyer instead of the seller. The observed refund at block 29 did exactly this for 100 pUSD, with the buyer's balance rising from 4,007 to 4,107 and the seller's unchanged.

MODULE 10THE COMPLETE WALKTHROUGH: 3,499 pUSD FOR A MACBOOK

This module is the story you will tell in an interview. Each stage is given twice: first in plain English, as you would explain it to a non-technical friend, then technically, as you would defend it to an engineer.

Stage 1 — Purchase

Plain. The buyer chooses a MacBook, connects their wallet, and pays into a locked box that neither they nor the seller can open. The seller can see that the money exists but cannot touch it.

Technical. React generates a random 32-byte orderId, validates the seller address and the amount, then sends approve(escrow, 3499e18). After that receipt, it sends createEscrow(orderId, seller, 3499e18). The escrow validates six conditions, writes a Funded struct, pulls the tokens with safeTransferFrom, and emits EscrowCreated. Two receipts, two confirmations, 156k and 46k gas respectively. The buyer's balance drops by exactly 3,499 pUSD; the escrow's balance rises by the same amount.

Stage 2 — Seller registration

Plain. The seller says "I have shipped it, here is the tracking number". This goes into the courier's system, not the blockchain, because it will change several times.

Technical. POST /api/shipments with the mutation secret. The service normalises the input, rejects duplicates by tracking ID and by order, calls getEscrow over RPC, and requires status === 1 and escrow.seller === sellerAddress. It stores the record with status CREATED and the first event, and re-runs the duplicate check after the async call to close the race.

Stage 3 — Courier progress

Plain. Over the next minute the parcel moves: dispatched, in transit, delivered. Each step is recorded with a timestamp.

Technical. The scheduler polls GET /api/shipments, filters to PPD- records with elapsed delays, and sends authenticated PATCH requests. The service validates against SHIPMENT_TRANSITIONS inside the serialised store update and appends an event per change. A manual alternative exists in the admin dashboard's simulator; both paths hit the same endpoint and the same rules.

Stage 4 — CRE evaluation

Plain. An independent program reads the courier's record and the locked box, and decides whether the delivery condition is satisfied.

Technical. The cron-triggered workflow fetches GET /api/shipments through the HTTP capability with consensus aggregation, parses defensively, and for each terminal shipment encodes getEscrow and reads it through the EVM capability at the last finalised block. It skips anything not Funded, applies shouldSettle, and builds the four-field payload. The report is generated, the payload source is verified, and two structured log records are emitted.

Stage 5 — Local relay

Plain. Because the workflow cannot post to our local test chain directly, a small relay carries its signed-off decision the last step and submits it.

Technical. The bridge runs the simulation, parses only PROOFPAY_REPORT_V1: lines, joins report and meta by order ID, validates the outcome, decodes the bytes independently, recomputes the report ID, applies the allowlist, checks the escrow is still funded, and encodes processReport(0x, report). It sends the transaction from the unlocked admin account and waits for a successful receipt, then records the submission.

Stage 6 — Settlement

Plain. The receiver checks that the report is legitimate and unused, then tells the locked box to pay. Delivered means the seller is paid; lost means the buyer is refunded.

Technical. _processReport decodes, derives the report ID, checks processedReports, orderSettled and the funding self-call, then branches on the outcome hash. confirmDelivery writes Released and transfers to the seller; confirmFailure writes Refunded and transfers to the buyer. Both emit settlement events; the receiver marks both mappings and emits ReportProcessed and SettlementExecuted.

MODULE 11SECURITY AND DESIGN DECISIONS, DEFENDED

Interviewers rarely ask "what does this function do?" — that is in the code. They ask "why is it built this way, and what did you give up?". This module answers that question thirteen times, using a fixed structure so the answers become habit: what we chose, why, what the alternatives were, why we rejected them, and what the trade-off costs.

11.2 Thirteen decisions, each defended

1. An escrow contract instead of paying the seller directly

Chosen. Buyer deposits to ProofPayEscrow; the seller is paid only on an oracle-authorised delivery. Why. The product being sold is protection; without custody there is nothing to protect. Alternatives. Direct payment with a refund process; a marketplace holding funds; a payment channel. Rejected because. Direct payment makes the buyer chase a refund from an unwilling seller; a marketplace reintroduces the trusted intermediary; channels solve streaming, not conditional sales. Trade-off. Funds can be stuck if the oracle never fires, and the buyer's capital is illiquid for the order's duration — accepted, because "stuck" is recoverable and "drained" is not.

2. A dedicated ERC-20 (pUSD) instead of ETH or a real stablecoin

Chosen. A 16-line ERC-20 with 18 decimals and owner-only mint. Why. It separates the value under protection from gas; it makes amounts exact in integers; it lets the demonstration mint balances on demand. Alternatives. Pay in ETH; integrate USDC/DAI; accept multiple tokens. Rejected because. ETH-denominated escrow conflates fees with principal and makes the demonstration's numbers unstable; integrating a real stablecoin adds external dependencies and regulatory claims the project cannot support; multi-token support multiplies accounting paths. Trade-off. pUSD is not money — no reserve, no peg, no redemption — so every claim about it must be scoped to "prototype token", which the report and this guide both do.

3. A separate receiver contract in front of the escrow

Chosen. ProofPayCREReceiver holds authorisation, decoding, replay protection and outcome mapping; the escrow only pays. Why. The receiver is the standard interface a DON calls, and isolating report handling keeps the custody contract small enough to review line by line. Alternatives. Put onReport directly on the escrow; let the escrow accept (orderId, outcome) from an EOA. Rejected because. Merging them would force the escrow to import ABI-decoding and replay logic, enlarging the attack surface of the contract that holds money; the EOA variant collapses the oracle back to a single trusted key with no provenance. Trade-off. One more deployment, one more address to configure, and about 51,000 extra gas per settlement (122,471 versus 71,186 for a direct call) — a fixed cost that buys auditable report handling.

4. Three roles: owner, forwarder, manualOracle

Chosen. Ownership configures; the forwarder is the intended automated reporter; manualOracle is a deliberate local and break-glass path. Why. Separating configuration from settlement means the key that can change addresses is not the key that moves money in normal operation. Alternatives. A single admin role; no manual path at all. Rejected because. One role concentrates risk; no manual path makes the system untestable locally and unrecoverable if the oracle dies. Trade-off. A local deployment with a zero forwarder lets the owner settle through the third branch of onlyAuthorized — a real weakening, documented in the code, the report and Module 12, and removed by setting a forwarder in production.

5. Chainlink CRE instead of a custom Node script that settles orders

Chosen. The decision lives in a CRE workflow with HTTP and EVM capabilities, report encoding and structured output. Why. The workflow is the component designed for exactly this: fetch external data, read chain state, compute, produce a report a contract can act on — and it is portable to a DON. Alternatives. A cron job holding a key and calling confirmDelivery; Chainlink Automation; Chainlink Functions. Rejected because. A key-holding script is a single trusted signer with no report artefact and no path to decentralisation; Automation triggers existing functions rather than running arbitrary multi-source logic; Functions is a request/response value fetch, not a workflow with its own decision table and report. Trade-off. CRE's chain-selector support and DON availability constrain the local deployment, which is the sole reason the bridge exists.

6. A local execution bridge instead of waiting for DON access

Chosen. Run the official simulator with dryRun: true and relay the resulting report locally. Why. It lets the whole pipeline be built, tested and measured now, while keeping CRE as the only decision-maker. Alternatives. Skip on-chain settlement entirely; fake the settlement in the UI; write a mock oracle that decides on its own. Rejected because. Skipping settlement makes the project a diagram; faking it in the UI would be dishonest; a self-deciding mock oracle would move the policy out of CRE and invalidate the architecture's central claim. Trade-off. The trust model is weaker than a DON: one machine runs the simulation and one account submits. That limitation is stated in the code header, the report and Module 8 rather than hidden.

7. The four-field report payload

Chosen. (bytes32 orderId, string outcome, bytes32 trackingIdHash, string observedAt). Why. The order identifies the escrow; the outcome selects the payout; the tracking hash ties the decision to evidence without publishing the tracking number; the timestamp distinguishes two reports and dates the observation. Alternatives. Just (orderId, outcome); include the full tracking ID; include the courier's raw JSON. Rejected because. Two fields give no provenance and make replay IDs ambiguous; the raw tracking ID leaks shipping data on a public ledger; the raw JSON is unbounded, expensive and unparseable on chain. Trade-off. The receiver cannot independently reconstruct the decision — it trusts CRE's outcome and can only check authorisation and uniqueness. That is inherent to any oracle design; the mitigation is the report's provenance record plus on-chain replay protection.

8. Two mappings: processedReports and orderSettled

Chosen. One keyed on a hash of the full report, one on the order. Why. They block different attacks: identical replay versus a fresh-looking report on an already-paid order. Alternatives. Only the order mapping; only the report mapping. Rejected because. With only the report mapping, an attacker who changes one character of the timestamp gets a new ID and a second payout attempt (stopped only by the escrow); with only the order mapping, you lose the audit record of which report settled which order. Trade-off. Two storage writes per settlement, roughly 40,000 gas — trivial against the value protected.

9. Terminal states with no exit

Chosen. Released and Refunded are final; no function reverses them; no owner rescue. Why. Reversibility is the property an attacker wants and the property a payment system must not have. Alternatives. An admin reverseSettlement; a pause function; an upgrade proxy. Rejected because. Each creates a privileged path to move money and a governance question the project cannot answer; an upgrade proxy would make "code is law" conditional. Trade-off. Mistakes are permanent. The mitigation is that mistakes are prevented upstream: preflight, allowlist, dry-run defaults and 31 tests.

10. Shipment state kept off chain

Chosen. Express + JSON persistence, read by CRE over HTTP. Why. Status changes six times per order, comes from an external process, and must be correctable. Alternatives. Store status on chain via an oracle write per update; use IPFS; use an event-sourced log on chain. Rejected because. Six paid writes per order is wasteful and every mis-scan becomes permanent; IPFS is content-addressed and awkward for mutable state; on-chain event sourcing has the same cost problem. Trade-off. The API becomes the trust boundary, mitigated by validating it against the escrow on chain before any payout.

11. The -LOST tracking-ID convention in the scheduler

Chosen. A demo scheduler derives the terminal status from the tracking ID suffix. Why. It makes a self-driving demo deterministic with no extra configuration. Alternatives. A random outcome; a config file per shipment; an admin click. Rejected because. Randomness makes demonstrations unrepeatable; per-shipment configuration is clumsy; an admin click defeats the point of automation. Trade-off. It is a courier-fact convention, not a settlement rule, and could be mistaken for one — hence the explicit comment in the file and this paragraph.

12. Dry-run defaults and the order allowlist

Chosen. LOCAL_BRIDGE_DRY_RUN=true by default; BRIDGE_ORDER_ALLOWLIST optionally restricts a run to named orders; CRE's own dryRun stays true. Why. Two independent keys before money moves, and a scope control that prevents a legitimate multi-report run from settling orders you did not intend. Alternatives. One flag; no allowlist; a confirmation prompt. Rejected because. One flag is one mistake away from an unintended transaction; without an allowlist the lost-order run would have settled two orders instead of one; a prompt cannot be used in a scheduler. Trade-off. More configuration to explain, and a user who forgets to set the flag sees a "planned" transaction instead of a real one — which the logs state plainly.

13. No private key in the repository

Chosen. The bridge sends eth_sendTransaction from Hardhat's unlocked account. Why. A settlement key on disk is the single most valuable file an attacker could find. Alternatives. A CRE_ADMIN_PRIVATE_KEY in .env; a keystore file; a hardware wallet. Rejected because. An env key is trivially leaked by a screenshot, a commit or a log; a keystore still needs a password on disk; hardware signing is impossible for an unattended scheduler. Trade-off. The design only works on a node whose accounts are unlocked, i.e. a local development chain. A production deployment would use a KMS or a dedicated signer service, and the guide says so rather than implying the local pattern is production-ready.

12.7 "I restarted Hardhat and everything vanished"

Why. The chain state lives in the node process. Restarting it produces a fresh chain at the same deterministic addresses, but with no deployments, no balances and no escrows. The backend's JSON still lists shipments that reference orders the new chain has never heard of.

Order of recovery matters. Start the node, redeploy the token and escrow, deploy the receiver, run the authorisation script, mint and distribute pUSD, then re-register shipments for the new order IDs, then run the bridge preflight. If you restore in a different order, the preflight will fail on address bytecode or on oracle wiring — which is the system telling you what is missing.

What you lose. Every transaction hash previously quoted, including the three settlement hashes. That is why the report records block numbers and hashes with their block heights, and why it says they are historical records of one chain instance rather than permanent addresses.

Interview checkpoint — Modules 11 and 12

Q. "What is the biggest security limitation?" A. The oracle path. Locally, one machine runs the simulation and one unlocked account submits; the external data source is a script with a shared secret. The contracts bound the damage — one payout per funded order, replay-blocked reports, authorised callers only — but a compromised API plus a compromised bridge could produce a wrong-but-well-formed settlement. A DON with multiple operators and a real carrier API is what removes that.

14.1 Level 1 — foundations

Q1. What is a blockchain?

Short: a database replicated across independent computers where changes are signed transactions grouped into hash-linked blocks. Reasoning: replication plus agreed validity rules means no single party can rewrite history unnoticed. In ProofPay: the escrow's state, every deposit and every settlement live in such a ledger, so neither buyer nor seller can alter the record of who was paid.

Q2. What is Ethereum?

Short: a blockchain whose nodes also run a virtual machine that executes programs called smart contracts. Reasoning: Bitcoin stores value transfers; Ethereum stores arbitrary state transitions, which is what makes conditional escrow possible. In ProofPay: the payment rules are code, not policy.

Q3. What is a smart contract?

Short: a program deployed to an address on the blockchain, with persistent public storage, executed deterministically by every node. Reasoning: determinism is what allows consensus; persistence is what makes it a record; no upgrade path is what makes it credible. In ProofPay: ProofPayEscrow holds funds and can only pay out through two functions.

Q4. What is Solidity?

Short: the main high-level language for EVM contracts, compiling to bytecode. Reasoning: it adds contract-specific constructs — modifiers, events, custom errors, storage mappings — on top of a JavaScript-like syntax. In ProofPay: all three contracts are Solidity 0.8.28, with OpenZeppelin for standard behaviour.

Q5. What is MetaMask?

Short: a browser extension wallet that stores keys, signs transactions, and injects an EIP-1193 provider at window.ethereum. Reasoning: it separates key custody from the application, so a website can request signatures without ever seeing a key. In ProofPay: every write — approve, createEscrow, processReport — is signed there.

Q6. What is an ERC-20 token?

Short: a standard interface for fungible tokens: balances, transfers, allowances and two events. Reasoning: standardisation means wallets and contracts can handle any token without custom code. In ProofPay: pUSD implements it, so the escrow can use SafeERC20 and treat it like any compliant asset.

Q7. What is gas?

Short: a unit measuring computational work, paid for in the chain's native currency. Reasoning: it prices storage and computation, preventing infinite loops and spam. In ProofPay: createEscrow costs about 156,000 gas and processReport about 122,000; the amounts were read from receipts, not estimated.

Q8. What is an escrow?

Short: a neutral hold on funds until an agreed condition is met. Reasoning: it removes the "who goes first" problem by making neither party able to spend prematurely. In ProofPay: the contract is the neutral holder, and the condition is an oracle report about delivery.

Q9. What is a transaction hash?

Short: the Keccak-256 digest of a signed transaction, used as its unique identifier. Reasoning: it is deterministic, so anyone can look it up on any node and see the same receipt. In ProofPay: the refund hash 0x835890…a5288 identifies the block-29 settlement.

Q10. What is a block number?

Short: the position of a block in the chain. Reasoning: ordering is what gives finality; a receipt's block number is when its effects became part of history. In ProofPay: settlements at blocks 24, 29 and 30, each exactly one higher than the last, which also proves no hidden extra transaction.

Q11. What is a nonce?

Short: a per-account counter that orders that account's transactions and prevents replay. Reasoning: a transaction with nonce n cannot be mined before n−1, and cannot be mined twice. In ProofPay: a stuck nonce is the usual cause of a "pending forever" transaction on the local node.

Q12. What is a chain ID?

Short: the network identifier that is signed into every transaction. Reasoning: it prevents a transaction signed for one chain from being replayed on another. In ProofPay: 31337 for Hardhat Local, and the UI refuses writes when the wallet reports anything else.

Q13. What is an RPC endpoint?

Short: an HTTP (or WebSocket) URL that a client uses to talk to a node. Reasoning: it exposes methods such as eth_call, eth_sendTransaction and eth_getLogs. In ProofPay: http://127.0.0.1:8545 is used by the wallet, the frontend, the backend verifier, the workflow and the bridge.

Q14. What is the EVM?

Short: the deterministic virtual machine that executes contract bytecode. Reasoning: determinism plus metered execution (gas) is what makes contract results agree across nodes. In ProofPay: the escrow's validations and the token's balance updates are EVM execution.

Q15. What is the difference between an address and an account?

Short: an address is the 20-byte identifier; an account is the thing it identifies, with a balance and possibly code and storage. Reasoning: every address is an account, but only EOAs can initiate transactions. In ProofPay: the receiver has an address, an account, code and two mappings, but no key — it can only act when called.

Q16. What is a private key, and who holds the project's?

Short: the 256-bit secret that signs transactions. Reasoning: possession is authority; there is no password reset. In ProofPay: no key is stored in the repository. The local Hardhat node holds test keys in memory and exposes the accounts as unlocked, so the bridge signs via eth_sendTransaction.

Q17. What is a hash function and why Keccak-256?

Short: a one-way function mapping any input to a fixed 32-byte fingerprint, with avalanche behaviour. Reasoning: Ethereum uses Keccak-256 for block linkage, addresses, selectors and event topics, so using it keeps your code consistent with the platform. In ProofPay: order IDs, tracking hashes and report IDs are all Keccak-256.

Q18. What is a digital signature?

Short: a proof, verifiable with a public key, that the holder of the matching private key approved specific bytes. Reasoning: signatures bind authorisation to content, so changing any field invalidates them. In ProofPay: that is why editing a request in the browser cannot move funds.

Q19. What does immutability actually mean here?

Short: rewriting history requires redoing all later blocks faster than honest participants extend the chain. Reasoning: immutability is economic and social, not absolute. In ProofPay: strong on chain, absent on the local node — restarting Hardhat erases everything, so no mainnet-style guarantee is claimed.

Q20. Why is the blockchain public a privacy problem, and how did you handle it?

Short: every address, amount and call is visible forever. Reasoning: payment transparency is the feature; leaking shipping details is the risk. In ProofPay: the report stores keccak256(trackingId) rather than the tracking number, so settlements are auditable without publishing parcel identifiers.

Q21. What is a testnet, and did you use one?

Short: a chain with valueless currency for development. Reasoning: it lets you rehearse without risking assets while still being public. In ProofPay: no. The project runs entirely on Hardhat Local; a Sepolia network entry exists in the config but was never used, and the report says so.

Q22. What is a wallet, if it does not hold coins?

Short: software that holds keys and signs; the coins are ledger entries. Reasoning: restoring a seed phrase restores access, not data. In ProofPay: deleting the extension changes nothing on chain; the escrow still holds the pUSD.

14.2 Level 2 — mechanics

Q23. How does MetaMask communicate with React?

Short: through the injected EIP-1193 provider's request() method and its events. Reasoning: the provider is a transport, not a library, so any framework can use it. In ProofPay: useWallet calls eth_requestAccounts, eth_chainId, eth_getBalance, and subscribes to accountsChanged and chainChanged.

Q24. What is EIP-1193?

Short: the standard describing the injected provider object and its request/response protocol. Reasoning: before it, each wallet invented its own API; after it, one code path works across wallets. In ProofPay: every chain interaction in the browser goes through it.

Q25. What is an ABI?

Short: a JSON description of a contract's functions, arguments, returns, events and errors. Reasoning: the EVM only sees bytes, so the ABI is how tooling encodes calls and decodes results. In ProofPay: the receiver's ABI has two functions in the frontend and seven entries in the bridge, including errors it decodes.

Q26. What is ABI encoding?

Short: the canonical byte layout for arguments: 32-byte words, offsets for dynamic types, lengths for strings and bytes. Reasoning: both sides must agree byte-for-byte or decoding fails. In ProofPay: the four-field report is 256 bytes, and its layout is why the receiver can decode it with one call.

Q27. What is a function selector?

Short: the first four bytes of keccak256("name(types)"), prefixed to calldata. Reasoning: it tells the contract which function to run without sending names. In ProofPay: the bridge's 388-byte transaction begins with the processReport(bytes,bytes) selector.

Q28. What is the difference between call, staticcall and delegatecall?

Short: call can change state, staticcall forbids it, and delegatecall runs another contract's code in the caller's storage. Reasoning: the distinction is what makes read-only RPC safe. In ProofPay: reads use eth_call, which is a static call; nothing in the project uses delegatecall, and no proxy pattern is used.

Q29. Why do you need approve before transferFrom?

Short: because a token contract will only debit an owner who has authorised that specific spender. Reasoning: without allowances, any contract you interact with could take everything. In ProofPay: transaction 1 sets allowance[buyer][escrow]; transaction 2 spends it inside createEscrow.

Q30. Why does the allowance get consumed?

Short: ERC-20 decrements the allowance on every transferFrom. Reasoning: an allowance is a spending limit, not a permanent grant. In ProofPay: a second purchase needs a fresh approval, which is why the checkout always runs the approve step rather than assuming it is still valid.

Q31. What is ReentrancyGuard and why is it there?

Short: a modifier that sets a storage flag so a function cannot be re-entered before it finishes. Reasoning: external calls hand control to code you do not control. In ProofPay: createEscrow and both settlement functions are nonReentrant, and a test attempts the attack.

Q32. What is SafeERC20?

Short: a wrapper that checks the return value of token calls and reverts on failure. Reasoning: some tokens return false instead of reverting, so ignoring the return value can silently lose funds. In ProofPay: all escrow transfers use it.

Q33. What is an event, and can a contract read it?

Short: a log entry stored in the transaction receipt; contracts cannot read logs. Reasoning: logs are cheap, indexable, and for off-chain consumers. In ProofPay: EscrowCreated lets the frontend discover orders, but every value shown is re-read from storage.

Q34. What is a custom error, and why use it?

Short: a typed revert with optional arguments, defined with the error keyword. Reasoning: cheaper than strings and precisely testable. In ProofPay: the tests assert revertedWithCustomError(token, "ERC20InsufficientBalance").withArgs(...).

Q35. What is an oracle?

Short: a component that delivers external facts to a blockchain. Reasoning: contracts cannot fetch, so facts must be pushed in with evidence. In ProofPay: the CRE workflow is the oracle, and the receiver is the contract that decides whether to believe its report.

Q36. Why can't a smart contract call an API directly?

Short: because execution must be deterministic and identical on every node; HTTP is neither. Reasoning: one node getting a different response would fork consensus. In ProofPay: this constraint is the reason the whole oracle pipeline exists.

Q37. What is the oracle problem?

Short: how to get a trustworthy external fact into a system that cannot verify it. Reasoning: any oracle reintroduces a trust assumption; the design question is how to bound it. In ProofPay: bounded by authorisation, replay protection, one settlement per funded order and a documented trust boundary.

Q38. What is a DON?

Short: a decentralised oracle network: independent nodes that must agree before reporting. Reasoning: agreement removes the single-reporter assumption. In ProofPay: the code is written for it, but no DON is deployed, so this is future work, not a claim.

Q39. What is Chainlink CRE?

Short: a runtime for TypeScript workflows with triggers, HTTP and EVM capabilities, and signed reports for on-chain receivers. Reasoning: it packages the whole fetch-verify-decide-report loop. In ProofPay: it holds the only settlement decision in the system.

Q40. What is a cron trigger?

Short: a schedule-based trigger, here the expression 0 */5 * * * *. Reasoning: settlement is periodic, not event-driven from the chain's perspective. In ProofPay: a deployed workflow would evaluate every five minutes; the simulator fires once per invocation.

Q41. What does the HTTP capability do in your workflow?

Short: performs GET /api/shipments and returns the body as text, with consensus aggregation available. Reasoning: this is the only place external data enters the decision. In ProofPay: a failure here ends the run with no settlement rather than a partial one.

Q42. What does the EVM capability do?

Short: performs a contract read (and, in principle, a report write) on a chain selected by a CRE chain selector. Reasoning: it lets the workflow verify on-chain state before deciding. In ProofPay: it reads getEscrow at the last finalised block and skips anything not Funded.

Q43. What is a CRE report?

Short: the SDK object holding your ABI-encoded payload plus a runtime metadata header. Reasoning: the header is provenance; the body is what the receiver decodes. In ProofPay: 109-byte header, 256-byte body, 365-byte raw report — and the extraction code proves which slice it used.

Q44. What is a receipt, and what does status 1 mean?

Short: the node's record that a transaction was included and what it did; status 1 means it succeeded. Reasoning: a hash alone proves broadcasting, not success. In ProofPay: every settlement was verified by receipt status, block number, gas used and the emitted events.

Q45. Why are reads free but writes costly?

Short: reads are executed locally against current state and change nothing; writes must be replicated and stored by every node. Reasoning: cost prices permanent storage. In ProofPay: this is why shipment status is off chain and only the escrow's essential facts are stored.

14.3 Level 3 — your architecture

Q46. Explain the ProofPay architecture in one minute.

Short: React talks to MetaMask and to an Express API; three contracts on Hardhat hold the money and the rules; a CRE workflow reads the API and the escrow, decides, and emits a report; a local bridge relays that report to the receiver, which instructs the escrow to pay. Reasoning: each layer owns one fact and one authority. Instance: the buyer's escrow, the seller's shipment record, CRE's decision, and the receiver's authorisation are four separate things that must all agree.

Q47. Why a custom token instead of ETH?

Short: to separate protected value from gas and to keep amounts exact. Reasoning: ETH-denominated escrow conflates fees with principal and makes demonstrations unstable. Trade-off: pUSD is a prototype with no reserve, and every claim must say so.

Q48. Why can't the seller access the funds immediately?

Short: because the escrow has no withdrawal function at all. Reasoning: protection requires that no one — seller, buyer, owner — can move the deposit before the condition. Instance: the only two paths are confirmDelivery and confirmFailure, both onlyOracle.

Q49. Why is there a separate receiver contract?

Short: to keep report handling out of the custody contract and to present the interface a DON expects. Reasoning: smaller money contracts are easier to audit; report policy changes more often than custody. Trade-off: one more address and ~51,000 extra gas per settlement.

Q50. What does manualOracle mean?

Short: an address the receiver will also accept reports from, intended for local testing and break-glass operation. Reasoning: without it, nothing could be settled before CRE worked, and an oracle outage would freeze funds. Trade-off: a real weakening when set to an EOA; production should use a multisig or remove it.

Q51. How does shipment registration work?

Short: the seller POSTs order ID, tracking ID, carrier and address to the API, which validates duplicates, verifies the escrow is funded on chain and that the seller matches, then stores a record with an event history. Reasoning: registration is the seller's claim; the chain verification is what makes the claim meaningful.

Q52. How does CRE read escrow data?

Short: it ABI-encodes getEscrow(orderId) with viem, sends it through EVMClient.callContract at the last finalised block, and decodes the returned struct. Reasoning: reading at a finalised block avoids deciding on a reorg-prone tip. Instance: status must be 1, otherwise the shipment is skipped and logged.

Q53. How does the local execution bridge work?

Short: it runs the CRE simulator, parses the structured report lines, validates and cross-checks them, then submits the exact bytes to processReport from an unlocked local account and verifies the receipt. Reasoning: the decision stays in CRE; the bridge only carries it. Instance: the block-29 refund.

Q54. Why does the bridge not just call confirmFailure itself?

Short: because only the oracle can, and the oracle is the receiver. Reasoning: routing through the receiver is what enforces replay and duplicate protection; a direct call would bypass the entire policy layer. Instance: the admin EOA cannot call the escrow's settlement functions at all.

Q55. What is the difference between the manual and automatic paths?

Short: manual builds a report in the browser with a zeroed tracking hash; automatic uses a CRE report with a real tracking hash and provenance. Reasoning: both pass the same receiver checks, but only the automatic path has evidence linking the decision to a courier record. Instance: the oracle panel is the manual path; the bridge is the automatic one.

Q56. Why is shipment status not stored on chain?

Short: it changes six times, comes from outside, and must be correctable. Reasoning: on-chain writes are permanent and cost gas; a mis-scan would be unfixable. Instance: the JSON store is the record; the chain stores only the settlement and its report ID.

Q57. How is a settlement prevented from happening twice?

Short: three layers: the escrow's Funded check, the receiver's two mappings, and the bridge's state file. Reasoning: each layer covers a different failure — a buggy caller, a replayed report, a retried process. Instance: blocks 24, 29 and 30 each advanced the chain by exactly one, so no duplicate was hidden.

Q58. What does the courier scheduler do, and what does it not do?

Short: it advances demo shipments through the timeline and optionally runs CRE and the bridge; it never decides settlement or touches contracts. Reasoning: separating the fact generator from the decision keeps CRE's authority intact. Instance: -LOST suffix decides the courier outcome, not the payout.

Q59. Why does the receiver store a hash of the tracking ID?

Short: to tie the settlement to a specific shipment record without publishing the tracking number. Reasoning: evidence plus privacy; it also contributes to the report ID. Instance: the manual path uses a zero hash, which is exactly why it is weaker.

Q60. What happens if CRE never runs?

Short: the escrow stays Funded; nothing is lost but nothing settles. Reasoning: the system fails safe, not open. Instance: the manual oracle path or a redeployed workflow is the recovery, and the funds remain claimable because they are still in custody.

Q61. Why does the checkout validate the seller address before prompting the wallet?

Short: to avoid wasting a signature on a call that must revert. Reasoning: the contract enforces the same rules, but failing in the UI is cheaper and clearer. Instance: zero address, self-payment and malformed addresses are blocked in handleSubmit.

Q62. How does the buyer dashboard know which orders are theirs?

Short: it discovers all order IDs from EscrowCreated logs, reads each escrow, and filters where buyer == connected address. Reasoning: chain state cannot be queried "by buyer" without an index, so filtering happens client-side. Trade-off: fine for a local demo, but a production app would index events in a database.

Q63. Why does the backend verify the escrow before accepting a shipment?

Short: a shipment for an unfunded order would have no money to settle. Reasoning: it also prevents a seller from registering an order that belongs to someone else. Instance: 404 ESCROW_NOT_FOUND, 409 ESCROW_NOT_FUNDED, 409 SELLER_MISMATCH.

Q64. What would break if you removed the allowlist from the bridge?

Short: a run intended for one order would settle every eligible order CRE reported. Reasoning: the allowlist scopes a demonstration without changing the decision. Instance: the refund run reported two shipments; without the allowlist, two settlements would have been submitted.

Short: const report = runtime.report(reportRequest).result(); placed before the dry-run branch. Reasoning: generation must happen regardless of whether the write is attempted, otherwise the safe configuration produces nothing to capture. Instance: that reordering is what made the entire local bridge possible.

14.4 Level 4 — advanced technical

Q66. Walk me through CRE report generation.

Short: encode the four fields, wrap in prepareReportRequest, call runtime.report(...).result(), then extract the body. Reasoning: the SDK adds a metadata header the receiver must not see. Instance: 256-byte payload, 365-byte raw report, source reported as body.

Q67. How exactly is the report encoded?

Short: abi.encode(bytes32, string, bytes32, string) — the order ID word, then a dynamic string, then a word, then a dynamic string. Reasoning: dynamic types use offsets, which is why the fixed part is four 32-byte words and the strings trail behind. Instance: the receiver uses one abi.decode with the same signature.

Q68. Why 109 bytes, and why does it matter?

Short: that is REPORT_METADATA_HEADER_LENGTH, the SDK's provenance prefix; the receiver decodes only the body. Reasoning: passing the raw report would shift every field by 109 bytes and fail to decode. Instance: 365 − 256 = 109, which is the arithmetic proof the strip was correct.

Q69. How does replay protection actually work?

Short: the receiver hashes the whole report and refuses a hash it has seen. Reasoning: identical bytes always produce the same digest, so a replay is detectable without storing the report. Instance: keccak256(abi.encodePacked(orderId, outcome, trackingIdHash, observedAt, metadata)).

Q70. Why do you need a second mapping for duplicate settlements?

Short: because a different report on a settled order produces a different report ID. Reasoning: without orderSettled, changing the timestamp would bypass replay protection. Instance: the escrow's Funded check would still block payment, but the receiver would waste gas and emit a misleading attempt.

Q71. Why can't the CRE SDK target local Hardhat?

Short: the installed SDK has no chain selector for chain ID 31337. Reasoning: selectors are an allow-list of supported networks, and local dev chains are not in it. Instance: the code calls getNetwork with a Sepolia selector because that is what compiles and runs; this is exactly why the bridge exists and why no CRE write is claimed.

Q72. Simulation versus DON deployment — what is the real difference?

Short: simulation runs your workflow in the CLI on one machine; deployment registers it with a DON where multiple operators execute it and agree. Reasoning: consensus, availability and signing authority all change. Instance: locally dryRun is true and a bridge relays; on a DON the workflow would write the report itself.

Q73. What exactly would you change for a DON deployment?

Short: deploy the workflow, flip dryRun to false, expose the API over HTTPS, set the receiver's forwarder, remove the owner fallback, delete the bridge. Reasoning: each change moves one responsibility from the local machine to the network. Instance: the escrow needs no change at all, because its oracle is already the receiver.

Q74. How does the receiver communicate with the escrow?

Short: it holds an immutable IEscrowSettlement reference and calls confirmDelivery or confirmFailure. Reasoning: because the receiver is the escrow's oracle, those calls satisfy onlyOracle without any EOA having that power. Instance: the escrow sees msg.sender = receiver.

Q75. What happens if report submission fails?

Short: the bridge reports the failure, decodes the revert, exits non-zero and records nothing. Reasoning: no state file entry means the submission is not falsely considered done; no retry means no duplicate risk. Instance: the operator fixes the cause (funding, wiring, authorisation) and runs again deliberately.

Q76. What if the transaction reverts after gas was spent?

Short: all state changes are undone; only gas is consumed. Reasoning: the EVM is atomic across the whole call tree. Instance: a reverted processReport leaves the escrow Funded and the mappings untouched, so a corrected retry is safe.

Q77. How would this scale to production?

Short: deploy the contracts to a public chain, run the workflow on a DON, replace the JSON store with a database, index events for the UI, use a KMS-backed signer for any manual path. Reasoning: each change addresses a specific local shortcut, not the architecture. Instance: the contract interfaces and the report format stay identical.

Q78. Where does the gas go in a settlement?

Short: mostly the token transfer, the two mapping writes, the escrow state write and the events. Reasoning: storage writes dominate; logs are cheaper. Instance: ~122,000 gas for processReport versus ~71,000 for a direct confirmDelivery; the ~51,000 difference is the policy layer's price.

Q79. Why terminal states instead of a reversible flag?

Short: because reversibility is the property an attacker needs. Reasoning: a reversible payout invites governance capture and makes balances non-final. Instance: the escrow's enum has no path back to Funded, and there is no admin rescue.

Q80. No upgradeability — is that a strength or a flaw?

Short: both, and you should say both. Reasoning: strength: no proxy admin can rewrite the rules; flaw: a bug is permanent and migration means a new deployment and manual fund movement. Instance: the project mitigates with a small surface, audited primitives and 31 tests rather than an upgrade path.

Q81. How would you add a second payment token?

Short: make the escrow's token per-order rather than immutable, or deploy one escrow per token. Reasoning: the immutable token is a deliberate simplification; multi-token support means storing the token address in the Escrow struct and validating it against a registry. Instance: the receiver would not change, because the escrow still owns payouts.

Q82. How would partial refunds work?

Short: a new settlement function that splits the amount and a report outcome that carries a basis-points field. Reasoning: the current payload has no room for an amount, and adding one changes the receiver's ABI. Instance: this is future work, listed in the report, not implemented.

Q83. What if the user switches accounts mid-checkout?

Short: accountsChanged re-runs applyAddress, the address changes, and the pending transaction is signed by the new account. Reasoning: the wallet is the authority, so the UI must follow it rather than cache an address. Instance: that is why useWallet exposes a refresh and subscribes to events.

Q84. Two orders for the same seller — any interference?

Short: none: state is keyed by order ID, and settlements are independent. Reasoning: the escrow mapping is per order, so one release cannot affect another. Instance: a test named "settles multiple escrows independently" pins exactly this.

Q85. How do you test the oracle without a real courier?

Short: with a deterministic simulated API and a scheduler that advances statuses. Reasoning: the oracle's job is to read a source, not to trust it, so a fake source exercises the same code path. Instance: the workflow's logs show it processing real records from the Express API, including skip and error branches.

Q86. What does idempotency mean in this system?

Short: running the pipeline twice has the same effect as running it once. Reasoning: settlement is the only irreversible effect, so it must be exactly-once, while report generation is safely repeatable. Instance: CRE may emit the same report again; the receiver and bridge both refuse it.

Q87. How would an auditor verify a settlement afterwards?

Short: take the transaction hash, read the receipt, decode ReportProcessed for the report ID and outcome, read getEscrow for the final state, and check token balances. Reasoning: the chain is self-describing; nothing depends on the app. Instance: that is precisely what the verification script produced for blocks 24, 29 and 30.

Q88. Why uint64 for timestamps?

Short: to pack two timestamps with an address and an enum into fewer storage slots. Reasoning: storage is charged per slot, so smaller types reduce gas when they share a slot. Instance: createdAt and settledAt are both uint64 and will not overflow for billions of years.

Q89. Why does the receiver take a metadata parameter that is always 0x?

Short: because the CRE/Chainlink receiver interface requires it, and the local path passes empty bytes. Reasoning: keeping the signature identical means a DON can call onReport without code changes. Instance: metadata still contributes to the report ID, so two otherwise identical reports with different metadata are distinct.

Q90. What happens to the allowance after settlement?

Short: it was already consumed at funding; settlement uses transfer from the escrow's own balance, not an allowance. Reasoning: the escrow owns the tokens, so it needs no permission to move them. Instance: after a purchase the buyer's allowance to the escrow returns to zero for that amount.

14.5 Level 5 — the challenging questions

Q91. Why should I trust the courier API?

Short: you should not trust it blindly — you should bound what a lie can achieve. Reasoning: a false status can cause a wrong settlement, but only for a funded, unsettled order, only once, and only through an authorised report. Instance: the design mitigations are the on-chain funding re-check, replay protection, and the audit trail that records which report justified the payout. A production system would add a real carrier's signed webhooks or multiple independent sources.

Q92. What if the seller manipulates shipment status?

Short: they can make a parcel look delivered, but they cannot make money appear. Reasoning: settlement requires a funded escrow and a valid report, and the seller cannot call the escrow or the receiver. Instance: the worst case is early release on an order the buyer actually funded — a fraud that leaves a permanent, attributable on-chain record rather than an untraceable one.

Q93. The courier says DELIVERED but the buyer never received the parcel. What then?

Short: this is the system's hardest case, and the honest answer is that it is a dispute, not a bug. Reasoning: the oracle reports what the data source says; a wrong data source yields a wrong but valid settlement. Instance: mitigation today is the manual-review path and off-chain recourse; the report lists arbitration and multi-source verification as future work. Never claim the design solves physical fraud.

Q94. What stops a seller from generating a false delivery report?

Short: the report is not produced by the seller — it is produced by CRE from the API record, and accepted only from an authorised caller. Reasoning: the seller's leverage is limited to the API's write access, which is protected by a server-side secret and validated transitions. Instance: even a forged API record still needs a funded escrow and passes the receiver's single-settlement checks.

Q95. What if Chainlink returns incorrect information?

Short: the report would be wrong, and the contracts cannot detect that — they can only enforce authorisation and uniqueness. Reasoning: an oracle is a trust boundary; a DON reduces the chance of error or collusion but does not eliminate it. Instance: locally, one simulator runs the workflow, so the trust is even more concentrated; that is stated explicitly rather than glossed.

Q96. What if the bridge is compromised?

Short: it could suppress reports or submit a forged one, and the receiver would accept the forgery because the caller is authorised. Reasoning: authority is by address, not by content signature. Instance: the damage is bounded to one payout per funded order, and every submission is recorded on chain. A DON removes the bridge entirely, which is the real fix.

Q97. What if an admin key is stolen?

Short: the thief can reconfigure the oracle, mint pUSD, and settle through the manual path — but cannot directly drain escrowed funds to an arbitrary address. Reasoning: there is no sweep function; the escrow only pays the recorded buyer or seller. Instance: the mitigations are owner separation, event logging of every configuration change, and the recommendation of a multisig in production.

Q98. Why is a local execution bridge needed at all?

Short: because the SDK cannot address Hardhat and no DON was available, yet the settlement still had to be demonstrated for real. Reasoning: the alternative was either no on-chain settlement or a fake UI claim; the bridge keeps CRE as the decision-maker and produces real transactions. Instance: three verified settlements exist because of it.

Q99. Is your system actually decentralised?

Short: no — the custody and rules are on chain, but the oracle path is centralised in this deployment. Reasoning: one simulator, one bridge machine, one authorised account, one simulated data source. Instance: the honest phrasing is "trust-minimised custody with a centralised oracle, architected for a DON". Claiming more would be false and easily challenged.

Q100. Why didn't you deploy the workflow on the DON?

Short: access to a deployed DON was not available in this environment, and the SDK lacks a local chain selector. Reasoning: both are external constraints, not design choices. Instance: the workflow was still written to DON conventions — consensus aggregation, report interface, forwarder role — so deployment is a configuration change rather than a rewrite.

Q101. How is this different from traditional escrow?

Short: custody and rules are code, decisions are evidenced, and settlement is automatic. Reasoning: a traditional agent holds money and a human judges delivery; here no one holds the money and the judgement is a report you can audit. Instance: the buyer can verify the escrowed balance and the settlement transaction without asking anyone.

Q102. What would happen if Hardhat were restarted?

Short: every deployment, balance and escrow disappears; the addresses are reusable only after redeploying. Reasoning: the chain is in memory. Instance: the recovery order is redeploy → authorise → mint → re-register shipments; the bridge's preflight reports exactly which step is missing.

Q103. What happens if the API becomes unavailable?

Short: CRE logs an HTTP error and settles nothing; the system fails safe. Reasoning: no data means no decision, which is preferable to guessing. Instance: escrows remain Funded and can be settled later or manually, so availability affects liveness, not safety.

Q104. What if a shipment is returned after delivery?

Short: if it was already released, nothing automatic happens; if it is still funded, CRE routes RETURNED to manual review and emits no settlement report. Reasoning: a return after delivery is a dispute about facts, not a courier status. Instance: shouldSettle returns MANUAL_REVIEW, and the receiver would reject such an outcome anyway.

Q105. What is the single biggest limitation?

Short: the trust boundary at the oracle: a simulated data source and a single local relay. Reasoning: every other component is either enforced by code or verified by tests; this one rests on operational honesty. Instance: the contracts bound the consequences to one payout per funded order, which is why the limitation is survivable but must be stated first, not last.

14.6 Rapid fire

Q106. msg.sender versus tx.origin?

Short: msg.sender is the immediate caller; tx.origin is the EOA that started the chain. Reasoning: authorising on tx.origin enables phishing through an intermediate contract. Instance: ProofPay uses msg.sender everywhere, which is why the escrow sees the receiver as its caller.

Q107. Why not approve an unlimited allowance?

Short: because the approved spender could take everything at any time. Reasoning: least privilege; an exact approval limits blast radius to one order. Instance: ProofPay approves the order amount and the allowance is consumed at funding.

Q108. What is front-running, and are you exposed?

Short: observing a pending transaction and submitting one that profits from it. Reasoning: on a public mempool, transaction content and ordering are visible. Instance: ProofPay's settlement is keyed to a specific order and payee, so there is no price to manipulate; on a local chain there is no mempool race at all.

Q109. Calldata, memory and storage — one line each?

Short: calldata is immutable function input, memory is temporary working space, storage is permanent chain state. Instance: the report arrives as calldata, is decoded into memory, and only the two booleans and the escrow struct reach storage.

Q110. Why is the escrow's mapping private?

Short: because a getter that reverts on unknown orders is a better API than one returning a zeroed struct. Reasoning: silent zero values are a classic source of bugs. Instance: getEscrow reverts with EscrowNotFound.

Q111. Why does the report ID include the metadata?

Short: so two reports that differ only in provenance are treated as distinct. Reasoning: the metadata is part of what the caller asserted. Instance: locally metadata is 0x, so it contributes nothing, but the interface stays DON-compatible.

Q112. What if two reports arrive with identical fields in the same second?

Short: the second is rejected — identical bytes give an identical report ID. Reasoning: the tick is part of the report only if the source's timestamp is; identical timestamps mean a true duplicate. Instance: that is the behaviour you want; a genuine second settlement attempt must fail.

Q113. What if the bridge's state file is deleted?

Short: replay protection moves entirely to the chain, which already covers it. Reasoning: the state file is a convenience for idempotent local runs, not the security boundary. Instance: a resubmission would revert with ReportAlreadyProcessed or OrderAlreadySettled.

Q114. What if two bridges run at once?

Short: the lock file prevents it; if forced, the chain prevents a double payout. Reasoning: both would compute the same report ID and only one transaction could succeed. Instance: the observed runs show one submission per order and one block of advancement.

Q115. What if CRE emits MANUAL_REVIEW as a settlement?

Short: the bridge refuses it and the receiver would revert with UnsupportedOutcome. Reasoning: the system only has two payouts, and neither means "a human should look at this". Instance: shouldSettle never produces an outcome for RETURNED, so this is belt and braces.

Q116. Why is the seller's address checked in the backend as well as the escrow?

Short: defence in depth and better errors. Reasoning: the escrow check would only fail at settlement, long after the mistake. Instance: SELLER_MISMATCH is returned at registration time.

Q117. What is the role of block.timestamp in your design?

Short: recording when an escrow was created and settled. Reasoning: it is consensus-agreed and monotonic enough for audit timestamps, but miners can nudge it slightly, so it must never gate security. Instance: no authorisation or amount logic depends on it.

Q118. Why not store the tracking ID on chain?

Short: cost and privacy. Reasoning: arbitrary-length strings cost storage and leak parcel identity. Instance: the hash gives evidence without exposure, and the receiver only needs it for the report ID.

Q119. How do you know the frontend is not lying?

Short: because it reads the chain rather than trusting a server, and every displayed value can be re-derived with an independent RPC call. Reasoning: the UI could still be malicious, but it cannot fabricate a balance that the chain disagrees with. Instance: the verification script reproduces the dashboard's numbers from getEscrow and balanceOf.

Q120. What is the point of the EscrowCreated event if the UI re-reads state?

Short: discovery and indexing. Reasoning: there is no enumerable list of mapping keys on chain, so an event is the only efficient way to learn which IDs exist. Instance: useEscrows filters logs on the event topic and the escrow address.

Q121. Why does the receiver use a self-call for the funding check?

Short: so a missing escrow becomes EscrowNotFound instead of a raw revert from the external call. Reasoning: typed errors are easier to test and to explain. Instance: try this._checkEscrowFunded(orderId) ... catch { revert EscrowNotFound(orderId); }.

Q122. Why does the bridge read the escrow again if CRE already did?

Short: because time passed and state can change between the simulation and the submission. Reasoning: the read is a preflight, not a second decision; it prevents wasting gas on an order that closed. Instance: the dry-run log prints the seller and the 100 pUSD amount from that read.

Q123. What would you do differently if you started again?

Short: design the report export before the first settlement, and keep the bridge's validation and the contract's checks generated from one schema. Reasoning: the dry-run ordering bug cost real time and was only visible once exports were attempted. Instance: a shared report schema would also have made the report ID derivation impossible to drift.

Q124. Which part of this project are you proudest of, technically?

Short: the demonstration that both outcomes can be executed and independently verified, with the decision provably outside the relay. Reasoning: the interesting engineering is the boundary design, not the contracts. Instance: the allowlist run where CRE reported two shipments and exactly one transaction resulted.

Q125. If I gave you one week, what would you add?

Short: a Sepolia deployment with a verified receiver and a DON-hosted workflow, plus one real carrier sandbox integration. Reasoning: those three changes convert the honest local caveats into production-relevant evidence. Instance: the escrow and receiver need no redesign; only addresses, configuration and the removal of the bridge.

16.2 Answers and expected reasoning

1. Connection. useWallet first calls eth_accounts (no prompt) to see whether the site is already permitted; if not, the button calls eth_requestAccounts, MetaMask prompts, and the chosen address is passed to applyAddress. That function reads eth_chainId and eth_getBalance, then writes one state object with the address, chain name, ETH balance and an isCorrectNetwork flag. A separate token hook reads balanceOf for pUSD. Nothing is stored in a database; deletion of the extension would not change any of these values on chain.

2. Approval. Transaction 1: buyer → pUSD approve(escrow, amount), which writes allowance[buyer][escrow] and emits Approval. Transaction 2: buyer → escrow createEscrow, which calls pUSD.transferFrom(buyer, escrow, amount); that decrements the allowance, moves balances, and emits Transfer. The escrow also writes its Escrow struct and emits EscrowCreated. The allowance exists so that the token, not the escrow, remains the authority over the buyer's balance.

3. Why escrow. Because the only alternative is trusting the counterparty to reverse a bad outcome. If the buyer pays directly, a lost parcel leaves them asking the seller for money; if the seller ships first, they are unsecured. Escrow makes the money conditional and the condition auditable. Removing it would also remove the thing the project sells.

4. Purchase trace. CheckoutPage.tsx validates the form and calls useEscrowActions, which uses viem to encode approve and sends it through the injected provider; MetaMask signs; ProofPayUSD.sol stores the allowance; then createEscrow is encoded and sent; ProofPayEscrow.sol validates, writes the struct, calls the token, emits the event; back in React, onCreated() triggers useEscrows to re-read state.

5. A complete transfer. The owner signs a transaction calling transfer(to, amount); the data is the 4-byte selector plus two 32-byte words; the token checks the balance, subtracts from the sender, adds to the recipient, emits Transfer(from, to, amount), and returns true. Two storage slots change; nothing else can alter them afterwards, and the receipt's logs are the permanent evidence.

6. Shipment request. React sends POST /api/shipments with the mutation secret; Express parses JSON (32 kB limit), the middleware authorises, the router calls register; validation normalises fields; duplicates are rejected; verifyEscrow performs an RPC getEscrow and requires status 1 and matching seller; the store appends the record atomically; the response is 201 with a Location header, or 400/404/409 on failure.

7. CRE fetch. HTTPClient.sendRequest with method GET against baseUrl + /api/shipments, wrapped in consensusIdenticalAggregation<string>(); ok(response) is checked, the body is read as text and parsed defensively. On a non-2xx response or a parse error the handler logs and returns an error string, so the run produces no settlements rather than a partial set.

8. Report decoding. Word 1: bytes32 orderId. Word 2: offset to the outcome string. Word 3: bytes32 trackingIdHash. Word 4: offset to the timestamp string. The two strings follow dynamically with their lengths. In the observed run, the total was 256 bytes, and the raw report was 365 because of the 109-byte SDK header.

9. processReport. onlyAuthorized → decode four fields → reject zero order ID → compute report ID → reject if processedReports → reject if orderSettled → self-call to confirm funding → hash outcome → call confirmDelivery or confirmFailure → set both mappings → emit ReportProcessed and SettlementExecuted. Any other outcome reverts with UnsupportedOutcome.

10. Refund. Shipment becomes LOST after IN_TRANSIT; CRE's shouldSettle returns REFUND with outcome LOST; the escrow is read and must be Funded; the payload is encoded and the report generated; the bridge validates the outcome and the funding, submits processReport; the receiver checks authorisation, replay, duplicate and funding, then calls confirmFailure, which writes Refunded and transfers to the buyer. Verified at block 29: buyer +100 pUSD, seller unchanged.

11. Wrong network. applyAddress compared parseChainId(eth_chainId) against 31337 and set isCorrectNetwork = false. The dashboard's write actions are gated on that flag, and the banner explains it — if the user sees nothing, the banner is above the fold or the component is reading a stale wallet object. Check the header chip and the console value of chainId.

12. UnauthorisedCaller. Possible causes: (a) the sending account is neither forwarder nor manual oracle, (b) the receiver's manual oracle was rotated and no longer matches the wallet, (c) the escrow's oracle was pointed elsewhere so the receiver's call fails downstream — but note that (c) produces UnauthorizedOracle from the escrow, not UnauthorizedCaller. Distinguish with two reads: receiver.manualOracle() and escrow.oracle(), compared against the connected address and the receiver address respectively.

13. Receipt verification. Fetch by hash, require status === 1, check to is the receiver, decode the logs for EscrowReleased(orderId, seller, amount) and SettlementExecuted(orderId, true), then read getEscrow(orderId) for status 2 and a non-zero settledAt, and finally compare the seller's balanceOf before and after — the delta must equal the escrowed amount exactly.

17.1 How to keep learning after this book

Three habits will carry you further than any tutorial. Re-derive, do not re-read: when you forget how the receiver works, write its checks from memory and compare. Change one thing in the repository and predict the failure before running it — set dryRun false on CRE while the bridge runs and see which check refuses; remove the allowlist and see two orders become eligible. And explain it to someone who does not code: the moment you can describe an oracle without the word "oracle", you understand it.

Finally, keep the honesty rule. The most impressive thing you can say about ProofPay is not that it is decentralised, but that you know exactly where it is not, why that choice was made, and what would have to change. That is what separates an engineer who used a tool from one who understands it.

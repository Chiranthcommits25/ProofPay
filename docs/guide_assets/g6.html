MODULE 11SECURITY AND DESIGN DECISIONS, DEFENDED

Interviewers rarely ask "what does this function do?" — that is in the code. They ask "why is it built this way, and what did you give up?". This module answers that question thirteen times, using a fixed structure so the answers become habit: what we chose, why, what the alternatives were, why we rejected them, and what the trade-off costs.

11.1 Threat model first

Table 11.1: Who might attack what, and which control answers it
AdversaryCapabilityControl that limits them
BuyerFunds orders, controls their own key, can call any contract function.Cannot withdraw after funding; cannot settle, because settlement is onlyOracle; cannot fund in someone else's name.
SellerRegisters shipments, controls the courier record through the API secret.Can mark a parcel delivered, but cannot move money; settlement still requires a funded escrow, one payout, and the receiver's checks.
Admin / oracle operatorOwns contracts, configures addresses, holds the manual-oracle role.Can rotate the oracle (visible via events) but has no function that transfers escrowed funds to an arbitrary address.
Bridge operatorRuns the relay, chooses which reports to submit.Cannot invent a valid report that the workflow did not produce without also forging the fields the receiver hashes; cannot replay; cannot settle twice.
Network observerReads everything on chain.Sees amounts and addresses, but only a hash of the tracking ID — a deliberate privacy choice.

11.2 Thirteen decisions, each defended

1. An escrow contract instead of paying the seller directly

Chosen. Buyer deposits to ProofPayEscrow; the seller is paid only on an oracle-authorised delivery. Why. The product being sold is protection; without custody there is nothing to protect. Alternatives. Direct payment with a refund process; a marketplace holding funds; a payment channel. Rejected because. Direct payment makes the buyer chase a refund from an unwilling seller; a marketplace reintroduces the trusted intermediary; channels solve streaming, not conditional sales. Trade-off. Funds can be stuck if the oracle never fires, and the buyer's capital is illiquid for the order's duration — accepted, because "stuck" is recoverable and "drained" is not.

2. A dedicated ERC-20 (pUSD) instead of ETH or a real stablecoin

Chosen. A 16-line ERC-20 with 18 decimals and owner-only mint. Why. It separates the value under protection from gas; it makes amounts exact in integers; it lets the demonstration mint balances on demand. Alternatives. Pay in ETH; integrate USDC/DAI; accept multiple tokens. Rejected because. ETH-denominated escrow conflates fees with principal and makes the demonstration's numbers unstable; integrating a real stablecoin adds external dependencies and regulatory claims the project cannot support; multi-token support multiplies accounting paths. Trade-off. pUSD is not money — no reserve, no peg, no redemption — so every claim about it must be scoped to "prototype token", which the report and this guide both do.

3. A separate receiver contract in front of the escrow

Chosen. ProofPayCREReceiver holds authorisation, decoding, replay protection and outcome mapping; the escrow only pays. Why. The receiver is the standard interface a DON calls, and isolating report handling keeps the custody contract small enough to review line by line. Alternatives. Put onReport directly on the escrow; let the escrow accept (orderId, outcome) from an EOA. Rejected because. Merging them would force the escrow to import ABI-decoding and replay logic, enlarging the attack surface of the contract that holds money; the EOA variant collapses the oracle back to a single trusted key with no provenance. Trade-off. One more deployment, one more address to configure, and about 51,000 extra gas per settlement (122,471 versus 71,186 for a direct call) — a fixed cost that buys auditable report handling.

4. Three roles: owner, forwarder, manualOracle

Chosen. Ownership configures; the forwarder is the intended automated reporter; manualOracle is a deliberate local and break-glass path. Why. Separating configuration from settlement means the key that can change addresses is not the key that moves money in normal operation. Alternatives. A single admin role; no manual path at all. Rejected because. One role concentrates risk; no manual path makes the system untestable locally and unrecoverable if the oracle dies. Trade-off. A local deployment with a zero forwarder lets the owner settle through the third branch of onlyAuthorized — a real weakening, documented in the code, the report and Module 12, and removed by setting a forwarder in production.

5. Chainlink CRE instead of a custom Node script that settles orders

Chosen. The decision lives in a CRE workflow with HTTP and EVM capabilities, report encoding and structured output. Why. The workflow is the component designed for exactly this: fetch external data, read chain state, compute, produce a report a contract can act on — and it is portable to a DON. Alternatives. A cron job holding a key and calling confirmDelivery; Chainlink Automation; Chainlink Functions. Rejected because. A key-holding script is a single trusted signer with no report artefact and no path to decentralisation; Automation triggers existing functions rather than running arbitrary multi-source logic; Functions is a request/response value fetch, not a workflow with its own decision table and report. Trade-off. CRE's chain-selector support and DON availability constrain the local deployment, which is the sole reason the bridge exists.

6. A local execution bridge instead of waiting for DON access

Chosen. Run the official simulator with dryRun: true and relay the resulting report locally. Why. It lets the whole pipeline be built, tested and measured now, while keeping CRE as the only decision-maker. Alternatives. Skip on-chain settlement entirely; fake the settlement in the UI; write a mock oracle that decides on its own. Rejected because. Skipping settlement makes the project a diagram; faking it in the UI would be dishonest; a self-deciding mock oracle would move the policy out of CRE and invalidate the architecture's central claim. Trade-off. The trust model is weaker than a DON: one machine runs the simulation and one account submits. That limitation is stated in the code header, the report and Module 8 rather than hidden.

7. The four-field report payload

Chosen. (bytes32 orderId, string outcome, bytes32 trackingIdHash, string observedAt). Why. The order identifies the escrow; the outcome selects the payout; the tracking hash ties the decision to evidence without publishing the tracking number; the timestamp distinguishes two reports and dates the observation. Alternatives. Just (orderId, outcome); include the full tracking ID; include the courier's raw JSON. Rejected because. Two fields give no provenance and make replay IDs ambiguous; the raw tracking ID leaks shipping data on a public ledger; the raw JSON is unbounded, expensive and unparseable on chain. Trade-off. The receiver cannot independently reconstruct the decision — it trusts CRE's outcome and can only check authorisation and uniqueness. That is inherent to any oracle design; the mitigation is the report's provenance record plus on-chain replay protection.

8. Two mappings: processedReports and orderSettled

Chosen. One keyed on a hash of the full report, one on the order. Why. They block different attacks: identical replay versus a fresh-looking report on an already-paid order. Alternatives. Only the order mapping; only the report mapping. Rejected because. With only the report mapping, an attacker who changes one character of the timestamp gets a new ID and a second payout attempt (stopped only by the escrow); with only the order mapping, you lose the audit record of which report settled which order. Trade-off. Two storage writes per settlement, roughly 40,000 gas — trivial against the value protected.

9. Terminal states with no exit

Chosen. Released and Refunded are final; no function reverses them; no owner rescue. Why. Reversibility is the property an attacker wants and the property a payment system must not have. Alternatives. An admin reverseSettlement; a pause function; an upgrade proxy. Rejected because. Each creates a privileged path to move money and a governance question the project cannot answer; an upgrade proxy would make "code is law" conditional. Trade-off. Mistakes are permanent. The mitigation is that mistakes are prevented upstream: preflight, allowlist, dry-run defaults and 31 tests.

10. Shipment state kept off chain

Chosen. Express + JSON persistence, read by CRE over HTTP. Why. Status changes six times per order, comes from an external process, and must be correctable. Alternatives. Store status on chain via an oracle write per update; use IPFS; use an event-sourced log on chain. Rejected because. Six paid writes per order is wasteful and every mis-scan becomes permanent; IPFS is content-addressed and awkward for mutable state; on-chain event sourcing has the same cost problem. Trade-off. The API becomes the trust boundary, mitigated by validating it against the escrow on chain before any payout.

11. The -LOST tracking-ID convention in the scheduler

Chosen. A demo scheduler derives the terminal status from the tracking ID suffix. Why. It makes a self-driving demo deterministic with no extra configuration. Alternatives. A random outcome; a config file per shipment; an admin click. Rejected because. Randomness makes demonstrations unrepeatable; per-shipment configuration is clumsy; an admin click defeats the point of automation. Trade-off. It is a courier-fact convention, not a settlement rule, and could be mistaken for one — hence the explicit comment in the file and this paragraph.

12. Dry-run defaults and the order allowlist

Chosen. LOCAL_BRIDGE_DRY_RUN=true by default; BRIDGE_ORDER_ALLOWLIST optionally restricts a run to named orders; CRE's own dryRun stays true. Why. Two independent keys before money moves, and a scope control that prevents a legitimate multi-report run from settling orders you did not intend. Alternatives. One flag; no allowlist; a confirmation prompt. Rejected because. One flag is one mistake away from an unintended transaction; without an allowlist the lost-order run would have settled two orders instead of one; a prompt cannot be used in a scheduler. Trade-off. More configuration to explain, and a user who forgets to set the flag sees a "planned" transaction instead of a real one — which the logs state plainly.

13. No private key in the repository

Chosen. The bridge sends eth_sendTransaction from Hardhat's unlocked account. Why. A settlement key on disk is the single most valuable file an attacker could find. Alternatives. A CRE_ADMIN_PRIVATE_KEY in .env; a keystore file; a hardware wallet. Rejected because. An env key is trivially leaked by a screenshot, a commit or a log; a keystore still needs a password on disk; hardware signing is impossible for an unattended scheduler. Trade-off. The design only works on a node whose accounts are unlocked, i.e. a local development chain. A production deployment would use a KMS or a dedicated signer service, and the guide says so rather than implying the local pattern is production-ready.

MODULE 12DEBUGGING AND TROUBLESHOOTING HANDBOOK

Every entry below is a failure you can actually hit in this project, in roughly the order you will hit them. The pattern is always the same: identify which layer owns the failure, then read the exact error rather than guessing.

12.1 How to read an error

Four sources of truth, in this order. The browser console shows the raw provider error object with a code and often a decoded revert. The MetaMask activity tab shows what was signed and its status. The node console shows the transaction and any revert reason. The receipt, fetched by hash, tells you definitively whether it succeeded (status: 1) or reverted (status: 0). Never diagnose from a toast notification.

12.7 "I restarted Hardhat and everything vanished"

Why. The chain state lives in the node process. Restarting it produces a fresh chain at the same deterministic addresses, but with no deployments, no balances and no escrows. The backend's JSON still lists shipments that reference orders the new chain has never heard of.

Order of recovery matters. Start the node, redeploy the token and escrow, deploy the receiver, run the authorisation script, mint and distribute pUSD, then re-register shipments for the new order IDs, then run the bridge preflight. If you restore in a different order, the preflight will fail on address bytecode or on oracle wiring — which is the system telling you what is missing.

What you lose. Every transaction hash previously quoted, including the three settlement hashes. That is why the report records block numbers and hashes with their block heights, and why it says they are historical records of one chain instance rather than permanent addresses.

Interview checkpoint — Modules 11 and 12

Q. "What is the biggest security limitation?" A. The oracle path. Locally, one machine runs the simulation and one unlocked account submits; the external data source is a script with a shared secret. The contracts bound the damage — one payout per funded order, replay-blocked reports, authorised callers only — but a compromised API plus a compromised bridge could produce a wrong-but-well-formed settlement. A DON with multiple operators and a real carrier API is what removes that.

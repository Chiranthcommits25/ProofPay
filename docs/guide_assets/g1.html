HOW TO USE THIS BOOK

This book has one job: after reading it, you should be able to open a blank page and explain ProofPay from the payment button to the settlement transaction, justify each design choice, name the alternatives you rejected, and admit the system's limits without being caught out. That is a different goal from writing a report. A report proves work was done; a textbook builds understanding.

Three habits make the material stick. First, read with the repository open. Every module names real files, and reading the actual source for two minutes after each section is worth more than re-reading the prose. Second, after each module, close the book and explain the module's main idea out loud in sixty seconds. If you cannot, you have read words rather than learned a mechanism. Third, do Module 16's exercises honestly before looking at the answer section; the exercises are designed to expose exactly the gaps that interviewers find.

The modules are ordered so that each one only depends on what came before. Module 10 then replays the entire system as one continuous story, which is the version you will actually tell in an interview. The honesty rule

Throughout this book, "implemented" means the code exists in this repository and was executed. "Simulated" means the mechanism is real but the data source is fake: the courier is a script, not DHL. "Not implemented" means exactly that. You will be asked about these distinctions, and the correct answer is always the precise one. MODULE 1UNDERSTANDING THE INTERNET AND BLOCKCHAIN FROM ZERO

You cannot understand escrow until you understand what it means for a program to hold money, and you cannot understand that until you understand where programs live and who can change their data. This module builds those foundations in the order a newcomer needs them: the web first, then the ledger, then the transaction, then the machine that runs contracts, then the cryptography that makes any of it trustworthy.

1.1 How the internet works, and where ProofPay sits in it

Almost every interaction in ProofPay is one of two shapes: a request to a server, or a transaction to a blockchain. Both are messages; the difference is who is allowed to change the record afterwards.

A client is a program that asks for something: your browser, or inside it, the React application. A server is a program that answers: here, the Express service on port 5001, or the Hardhat node on port 8545. Between them travel requests and responses. In the browser-to-backend case the protocol is HTTP; in the browser-to-blockchain case it is JSON-RPC, which is HTTP with a fixed message format for chain operations.

Frontend means the code running inside your browser tab: React components, TypeScript, CSS, and an injected wallet provider. Backend means code running in a separate process that the browser cannot inspect or edit: the shipment API with its JSON file. The split matters because a frontend is under the user's control. Anything the frontend decides can be changed by a determined user with developer tools. That is exactly why ProofPay's rule, "the buyer's funds may only move when the delivery condition is satisfied", is enforced in Solidity and not in React.

An API (application programming interface) is an agreed set of addresses and message shapes for talking to a program. ProofPay's shipment API, for example, defines five endpoints. A database is durable storage. Big systems use PostgreSQL or MongoDB; this project deliberately uses a single JSON file at backend/data/shipments.json, written atomically, because the teaching goal is the oracle pipeline rather than database engineering.

JSON (JavaScript Object Notation) is the text format both sides agree on. A real shipment record from this project looks like this:

{
  "trackingId": "PPD-DEMO-DELIVERED",
  "orderId": "0xf694b593b682ac612e6f5c784a6801deab4f4c0b7420272b555d8ce669c26434",

Authentication answers "who is allowed to do this?". ProofPay uses three different answers in three places, and confusing them is a classic interview mistake. The shipment API uses a shared secret header on mutating routes (requireMutationAccess), because only the seller client and the demo scheduler should write. The blockchain uses cryptographic signatures: a transaction is only valid if it is signed by the private key behind the sending address. MetaMask is where that signature happens. And the contracts use role checks (onlyOwner, onlyOracle, onlyAuthorized), which are authorisation rules layered on top of the signature.

1.2 What a blockchain is, and why it exists

Start with the problem rather than the definition. Suppose two strangers want to exchange money for goods over the internet. Somebody has to go first. If the buyer pays first, the seller may vanish. If the seller ships first, the buyer may never pay. The usual answer is an institution in the middle: a bank, a marketplace, an escrow agent. That works, but it means the rule that decides who wins a dispute lives in a private database, applied by staff, visible to nobody.

A blockchain is a distributed ledger: a database replicated across many independent computers (nodes), where every change is a signed transaction, changes are grouped into blocks, and blocks are chained together by cryptographic hashes so that altering an old block invalidates every block after it. Because many nodes hold copies and compare them, there is no single machine whose edit becomes truth. The interesting part is not "many copies"; it is that the copies agree on rules for what counts as a valid change, and that agreement (consensus) is what lets strangers rely on the record without trusting each other.

Hashing is the glue. A hash function takes any input and returns a fixed-length fingerprint: change one character and the fingerprint changes completely, but the same input always gives the same fingerprint. ProofPay uses Keccak-256, which returns 32 bytes. You will meet it in three places: block linkage (not your code), order IDs (32 random bytes, treated as an identifier), and report IDs (keccak256 of the order, outcome, tracking hash, timestamp and metadata). The report ID is what makes replay detectable: the same report hashes to the same 32 bytes, so the receiver can recognise it.

Digital signatures are the other half. A private key signs; anyone holding the matching public key can verify the signature but cannot produce a new one. An Ethereum address is derived from the public key, so "verify the signature, recover the signer's address, compare it with the sender field" is enough to prove who authorised a transaction. This is why nobody can move your pUSD by editing a request in the browser: without your key, there is no valid signature, and the node rejects the transaction before any contract runs.

Analogy, then the reality

Think of a blockchain as a shared notebook kept by a hundred people, where each page's first line is a fingerprint of the previous page. Tearing out a page changes every later fingerprint, so the forgery is visible to everyone holding a copy.

Technically: each block header commits to its parent's hash, so rewriting history requires redoing all subsequent proof-of-work or consensus participation, on the majority of the network, faster than honest nodes extend the chain. On the local Hardhat chain, this security property is absent by design — one machine mines instantly and you can restart it and erase everything. That is why this project never claims mainnet security.

Immutability, therefore, is not magic: it is the cost of rewriting history. Transparency is the consequence of replication: every participant can read every transaction. Decentralisation is the degree to which no single party can unilaterally decide what happens next. ProofPay gets strong immutability and transparency from the chain, but its oracle path is only partially decentralised, and the honest answer to "is this decentralised?" is discussed in Module 11 and rehearsed in Module 14.

1.3 How a blockchain transaction works

Here is the full path of one ProofPay action — a buyer funding a 3,499 pUSD escrow. Read it once as a story, then again as a checklist, because interviewers ask you to narrate exactly this.

  1. The user initiates an action. The buyer clicks "Fund escrow". React has already validated the form and knows the amount, the seller address and a freshly generated 32-byte order ID.
  2. The wallet prepares a transaction. The app calls eth_sendTransaction through the injected provider. MetaMask builds an unsigned transaction: from, to (the escrow contract), value (0, because pUSD is an ERC-20 not ETH), data (the encoded createEscrow call), gas parameters and the next nonce.
  3. The transaction is signed. MetaMask shows the details and asks for confirmation. On approval it signs the transaction hash with the buyer's private key. The key never leaves the extension.
  4. The transaction is broadcast. The signed bytes go to the RPC endpoint — here http://127.0.0.1:8545, the Hardhat node.
  5. A node validates it. The node checks the signature, the nonce, the balance for gas, the chain ID and the intrinsic gas; malformed or unauthorised transactions never reach a contract.
  6. It is included in a block. Hardhat mines it immediately. On a public chain this is where validators or miners compete; here it is deterministic.
  7. The contract executes. The EVM runs createEscrow: validations, struct write, then paymentToken.safeTransferFrom(buyer, escrow, 3,499e18), which calls the token contract, which checks the allowance and moves the balance.
  8. State changes. The escrow's storage now holds a Funded record; the token's balances are updated; events are queued.
  9. A receipt is returned. The app polls eth_getTransactionReceipt, sees status: 1, reads the logs, and refreshes the dashboard.

What happens when a transaction fails

Failure comes in three flavours, and telling them apart is an interview skill in itself. Rejected in the wallet: the user pressed cancel, so nothing was broadcast, no gas was spent, and the app should say "you rejected the request" rather than "transaction failed". Reverted during execution: the transaction was mined, gas was consumed, but the contract threw. In Solidity 0.8 a revert rolls back all state changes, which is why a failed settlement leaves the escrow untouched. The receipt shows status: 0, and modern tooling can decode the revert reason — ProofPay uses custom errors such as EscrowNotFunded(orderId) so the reason is precise and cheap. Never mined: the transaction sits in the mempool because the gas price is too low or a nonce gap exists; here it appears as "pending forever".

Common misconception

"A reverted transaction still transfers the tokens because the transfer happened before the revert." False. Reverts are atomic: the EVM discards every state change made by the whole call, including nested calls into the token contract. The only thing permanently consumed is gas, which is why a reverted settlement costs the sender fees but moves no pUSD.

1.4 Ethereum and the EVM

Ethereum is a network whose state is a key-value store maintained by thousands of nodes, plus a virtual machine that can modify that store according to code that users deploy. Solidity compiles to EVM bytecode; the bytecode is what actually runs. "EVM-compatible" networks (Polygon, Arbitrum, Base, BNB Chain, and your local Hardhat node) implement the same instruction set and RPC conventions, which is why the same contracts and the same frontend work on any of them — only the chain ID and addresses change.

There are two kinds of account, and ProofPay depends on both. An externally owned account (EOA) is controlled by a private key: the buyer, the seller, the admin. A contract account has code and storage and no key: the token, the escrow, the receiver. An EOA initiates transactions. A contract can only act when called, either by an EOA or by another contract — which is exactly how the receiver becomes the escrow's oracle: the admin calls the receiver, and the receiver calls confirmDelivery, so the escrow sees msg.sender = receiver, not the admin.

Events deserve one more sentence because beginners expect contracts to read them. They cannot. A log is a receipt for humans and indexers: it is stored in the transaction receipt, and only off-chain software (eth_getLogs, block explorers, your React app) consumes it. That is precisely why useEscrows uses logs to discover order IDs and then calls getEscrow to read the data: discovery is cheap and indexable; truth comes from storage.

1.5 Cryptographic foundations you will actually be asked about

Hashing. Keccak-256 maps any bytes to 32 bytes, deterministically and irreversibly. Properties that matter: the same input always yields the same output (so a report ID can be recomputed by anyone); a one-bit change scrambles the whole output (so tampering is detectable); and you cannot feasibly find two inputs with the same output (so an attacker cannot substitute a different report for the same ID). In this project, hashing appears in the block chain itself, in order IDs, in keccak256(toHex(trackingId)) inside the report, in report IDs, and in ABI function selectors.

Signatures. Ethereum uses ECDSA over secp256k1. A signature proves that the holder of a private key approved a specific 32-byte digest. The digest for a transaction covers the chain ID, nonce, gas, recipient, value and data, so a signature cannot be replayed on another chain or reused for a different call. When MetaMask shows you a scary-looking hex blob and asks you to confirm, that is the digest you are authorising.

Address derivation. Address = last 20 bytes of keccak256(publicKey) for an EOA. For a contract, the address is keccak256(rlp(sender, nonce))[12:] — which is why, on a fresh Hardhat node, deployments land at the familiar sequence 0x5FbD…, 0xe7f1… from the same account: same deployer, increasing nonce.

Why contracts cannot trust arbitrary external information. This is the seed of Module 7. A contract is deterministic: every node must compute the same result from the same inputs, or consensus breaks. If Solidity could perform an HTTP GET, two nodes could receive different responses (or none), and the chain would fork on the answer. Therefore external facts must be pushed into the chain by a transaction, and the only question that matters is who is allowed to push, and what evidence they attach. Everything in this project's oracle design — the receiver's authorisation, the report's provenance fields, the replay protection — exists because of that single constraint.

Interview checkpoint — Module 1

Q. "Why can't the escrow contract just call the courier's API when the parcel is delivered?" Model answer. Because execution must be deterministic and every node must agree on the same state transition; an HTTP call is non-deterministic and unavailable inside the EVM. So the fact has to arrive as part of a transaction, and something off chain must decide to send it. In ProofPay that something is a Chainlink CRE workflow, and the contract's protection is that it will only accept the report from an authorised caller, only once, and only while the order is still funded.

MODULE 2METAMASK, EXPLAINED COMPLETELY

MetaMask is where most beginners' understanding collapses into "the wallet thing". This module fixes that. By the end you should be able to explain what MetaMask stores, what it refuses to store, what it does when a site calls it, and why ProofPay needs two separate confirmations to fund one escrow.

2.1 What MetaMask actually is

MetaMask is a browser extension that (a) holds encrypted private keys, (b) signs transactions and messages on your behalf, and (c) injects a JavaScript object into every page at window.ethereum so that websites can request those signatures. It is also a lightweight wallet UI and a network switcher.

What it stores: an encrypted vault containing your seed phrase and derived keys, your selected network and account, and a local transaction history. What it does not store: your cryptocurrency. The tokens and ETH are entries in the blockchain's state. If you delete the extension and reinstall it with the same seed phrase, your balance reappears instantly, because the balance never lived in the extension. This is the single most useful sentence for explaining wallets to a non-technical audience.

An address is your public identifier: 0x7099…79C8. Anyone can send to it; nobody can spend from it without the key. ProofPay displays addresses shortened for readability (0x7099…79c8) but always sends full 20-byte values to the chain, because a shortened address is not a valid address.

2.2 Private keys, seed phrases, importing versus connecting

A seed phrase (12 or 24 words) is the master secret. Every account in the wallet is derived from it by a deterministic process (BIP-39 for the mnemonic, BIP-32/BIP-44 for derivation paths). Importing an account means giving the wallet either the seed phrase or a raw private key so that it can control that account. Connecting a site means granting that site permission to see your address and ask for signatures — it never gives the site your key.

Table 2.1: Connect versus import — a distinction interviewers test

MetaMask asks for approval on every transaction because a signature is irreversible. There is no "undo" for a mined transaction and no customer-support number to call. The prompt is the last line of defence, which is why ProofPay's UI always shows the amount and the recipient before triggering it, and why the escrow contract independently re-validates everything: never rely on a UI to enforce a rule.

Local accounts only

Hardhat prints twenty accounts with their private keys when you run npx hardhat node. Those keys are public, published in Hardhat's documentation, and identical every time. They exist only for local development. Never send real funds to them, never reuse them on a public network, and never paste them into a website. This guide deliberately contains no key material.

One wallet can hold many accounts (different addresses derived from the same seed) and can point at many networks (different chains). The chain ID is the crucial field: it is included in the signed transaction, so a transaction signed for chain 31337 cannot be replayed on Ethereum mainnet. Here is the actual core of the project's wallet handling, shortened but not rewritten:

frontend/src/store/useWallet.ts — silent rehydration and event subscriptions
// On mount: no popup. If the site is already authorised, adopt the account.
const rehydrate = async () => {
  if (sessionStorage.getItem(MANUAL_DISCONNECT_KEY) === '1') return;
  const accounts = await provider.request<string[]>({ method: 'eth_accounts' });
  if (cancelled || accounts.length === 0) return;
  await applyAddress(accounts[0]);
};

// Live updates: the wallet tells us, we never poll for account changes.
provider.on('accountsChanged', handleAccountsChanged);
provider.on('chainChanged', handleChainChanged);

applyAddress is the single place that turns an address into UI state: it reads the chain ID, reads the native balance, and sets isCorrectNetwork by comparing against HARDHAT_LOCAL.chainId. Everything else in the app — dashboards, checkout, oracle panel — consumes that one object. If you are asked "how does the UI know the wallet changed?", the answer is: it subscribes to the provider's events and re-runs applyAddress; there is no polling loop.

2.5 The real transaction lifecycle in ProofPay

Funding one escrow involves two transactions, and the reason is an ERC-20 design decision, not an accident. A contract cannot move tokens out of your wallet unless you have authorised it to. That authorisation is itself a state change on the token contract, so it needs its own transaction.

Table 2.4: Two transactions, one purchase
#TransactionWho executes whatWhat it means / what you see
1approve(escrow, 3499e18) on pUSDBuyer → token contract. Storage: allowance[buyer][escrow] = 3499e18.MetaMask shows a call to the token with a spending cap. After mining, the checkout shows "approved". No money has moved yet.
2createEscrow(orderId, seller, 3499e18) on escrowBuyer → escrow, which calls transferFrom(buyer, escrow, 3499e18) on the token.MetaMask shows a second confirmation. On success the allowance is consumed and the escrow holds 3,499 pUSD in the Funded state.

Why not one transaction? Because the token contract is the only thing that may debit your balance, and it will only do so for an address you have approved. Combining them would require the token to trust an arbitrary caller, which would let any contract drain any wallet. The allowance indirection is the security feature; the extra click is its cost. (EIP-2612 permit and EIP-3009 transferWithAuthorization allow signature-based single-transaction flows for tokens that implement them; pUSD, built on OpenZeppelin's plain ERC-20, does not.)

Signing a message versus signing a transaction. A message signature (EIP-191/712) proves you control an address at a point in time; it changes no state and costs no gas. A transaction signature authorises a state change, is broadcast, costs gas and produces a receipt. ProofPay's flows are all transactions; the only message-ish interaction is the wallet connection itself.

Do this once, slowly, with the three terminals running. You will understand more from ten minutes of this than from an hour of reading.

  1. Start the chain. cd ~/Desktop/Minor_2/contracts && npx hardhat node. Leave it running. Note the twenty printed accounts — those are your local identities.
  2. Deploy. In a second terminal, from contracts, run the project's deploy scripts (deploy.js, then deploy-receiver.js, then authorize-receiver.js). This writes contracts/deployments/cre-receiver-localhost.json, which is your record of what is deployed where.
  3. Install MetaMask and create a wallet. Write the seed phrase on paper. It controls only test accounts in this workflow.
  4. Add the network. Networks → Add network → Add manually. RPC http://127.0.0.1:8545, chain ID 31337, symbol ETH. Save and switch to it.
  5. Import the three roles. Account menu → Import account → paste the private key that Hardhat printed for account 0 (admin), then repeat for account 1 (buyer) and account 2 (seller). Importing is legitimate here because these keys are public test keys; you are teaching yourself role switching.
  6. Connect. Open http://localhost:5173, click Connect wallet, choose an account. The header should show "Hardhat Local" and a pUSD balance. If it shows a red network warning, you are on the wrong chain.
  7. Import the token so MetaMask can display it: Import tokens → custom address 0x5FbDB2315678afecb367f032d93F642f64180aa3, symbol pUSD, decimals 18.
  8. Act as buyer. Go to Checkout, choose a product, confirm the seller address, submit. Approve the first prompt (allowance), then the second (escrow). Watch the checkout move through "approving" → "approved" → "creating" → confirmed.
  9. Copy the transaction hashes from the UI. Paste one into a terminal: cast receipt <hash> --rpc-url http://127.0.0.1:8545 if you have Foundry, or read it via the project's viem/ethers scripts. Confirm status 1 and note the block number.
  10. Act as seller. Switch account, open Incoming Escrows, select the funded order, register a shipment with a tracking ID beginning PPD-. This writes to the Express API, not the chain.
  11. Act as admin. Switch account, open the admin dashboard, confirm that escrow.oracle() equals the receiver and that manualOracle() equals this account. That panel is your proof the wiring is correct.
If something looks wrong

A zero pUSD balance usually means the token is not imported or the admin never minted to that account. A missing "Fund escrow" button usually means the wrong network. A revert on createEscrow with ERC20InsufficientAllowance means the first transaction was replaced or never confirmed. Module 12 turns each of these into a diagnosis procedure.

Interview checkpoint — Module 2

Q. "If MetaMask doesn't store coins, what happens if I uninstall it?" A. The coins are entries in the blockchain; they remain untouched. Reinstalling and restoring the seed phrase recreates the keys and therefore access. What you lose by discarding the seed phrase is the ability to sign, not the asset.

Q. "Why does ProofPay ask for two confirmations?" A. ERC-20 separates permission (allowance) from movement (transferFrom). The first transaction grants the escrow a spending cap; the second spends it. That indirection is what stops arbitrary contracts from draining wallets.

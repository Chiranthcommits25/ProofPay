MODULE 16HANDS-ON EXERCISES AND MOCK INTERVIEW

Do these with the repository closed. If you need the code, you have not learned it yet — read the relevant module again and come back. Answers follow the exercise list; do not read them first.

16.1 The exercises

  1. Explain, in five sentences, what happens from the moment a buyer clicks "Connect wallet" to the moment the header shows a pUSD balance.
  2. Write out the token approval flow from memory, naming the two contracts, the two transactions and the storage each one changes.
  3. Explain why the escrow locks funds, and what would break if the buyer paid the seller directly.
  4. Trace one purchase from the React form to the Solidity storage write, naming every file on the way.
  5. Describe a complete ERC-20 transaction: who signs, what is encoded, what events are emitted, what changes in storage.
  6. Trace one shipment API request end to end, including validation, the chain check and the response code.
  7. Explain how CRE fetches shipment status, including which capability, which method, and what happens on failure.
  8. Decode an example settlement report by hand: given a 256-byte payload, name the four fields in order and what each contains.
  9. Explain how processReport works, in order, including every check and every revert.
  10. Explain the refund flow without looking at this guide.
  11. Diagnose an intentionally wrong network: the user is on mainnet, every button is disabled, and no error is shown. What is happening and where?
  12. Diagnose an unauthorised oracle: settlement reverts with UnauthorizedCaller. Give three possible causes and the exact read that distinguishes them.
  13. Explain how to verify a transaction receipt, and what you would check to prove a release actually paid the seller.

16.2 Answers and expected reasoning

1. Connection. useWallet first calls eth_accounts (no prompt) to see whether the site is already permitted; if not, the button calls eth_requestAccounts, MetaMask prompts, and the chosen address is passed to applyAddress. That function reads eth_chainId and eth_getBalance, then writes one state object with the address, chain name, ETH balance and an isCorrectNetwork flag. A separate token hook reads balanceOf for pUSD. Nothing is stored in a database; deletion of the extension would not change any of these values on chain.

2. Approval. Transaction 1: buyer → pUSD approve(escrow, amount), which writes allowance[buyer][escrow] and emits Approval. Transaction 2: buyer → escrow createEscrow, which calls pUSD.transferFrom(buyer, escrow, amount); that decrements the allowance, moves balances, and emits Transfer. The escrow also writes its Escrow struct and emits EscrowCreated. The allowance exists so that the token, not the escrow, remains the authority over the buyer's balance.

3. Why escrow. Because the only alternative is trusting the counterparty to reverse a bad outcome. If the buyer pays directly, a lost parcel leaves them asking the seller for money; if the seller ships first, they are unsecured. Escrow makes the money conditional and the condition auditable. Removing it would also remove the thing the project sells.

4. Purchase trace. CheckoutPage.tsx validates the form and calls useEscrowActions, which uses viem to encode approve and sends it through the injected provider; MetaMask signs; ProofPayUSD.sol stores the allowance; then createEscrow is encoded and sent; ProofPayEscrow.sol validates, writes the struct, calls the token, emits the event; back in React, onCreated() triggers useEscrows to re-read state.

5. A complete transfer. The owner signs a transaction calling transfer(to, amount); the data is the 4-byte selector plus two 32-byte words; the token checks the balance, subtracts from the sender, adds to the recipient, emits Transfer(from, to, amount), and returns true. Two storage slots change; nothing else can alter them afterwards, and the receipt's logs are the permanent evidence.

6. Shipment request. React sends POST /api/shipments with the mutation secret; Express parses JSON (32 kB limit), the middleware authorises, the router calls register; validation normalises fields; duplicates are rejected; verifyEscrow performs an RPC getEscrow and requires status 1 and matching seller; the store appends the record atomically; the response is 201 with a Location header, or 400/404/409 on failure.

7. CRE fetch. HTTPClient.sendRequest with method GET against baseUrl + /api/shipments, wrapped in consensusIdenticalAggregation<string>(); ok(response) is checked, the body is read as text and parsed defensively. On a non-2xx response or a parse error the handler logs and returns an error string, so the run produces no settlements rather than a partial set.

8. Report decoding. Word 1: bytes32 orderId. Word 2: offset to the outcome string. Word 3: bytes32 trackingIdHash. Word 4: offset to the timestamp string. The two strings follow dynamically with their lengths. In the observed run, the total was 256 bytes, and the raw report was 365 because of the 109-byte SDK header.

9. processReport. onlyAuthorized → decode four fields → reject zero order ID → compute report ID → reject if processedReports → reject if orderSettled → self-call to confirm funding → hash outcome → call confirmDelivery or confirmFailure → set both mappings → emit ReportProcessed and SettlementExecuted. Any other outcome reverts with UnsupportedOutcome.

10. Refund. Shipment becomes LOST after IN_TRANSIT; CRE's shouldSettle returns REFUND with outcome LOST; the escrow is read and must be Funded; the payload is encoded and the report generated; the bridge validates the outcome and the funding, submits processReport; the receiver checks authorisation, replay, duplicate and funding, then calls confirmFailure, which writes Refunded and transfers to the buyer. Verified at block 29: buyer +100 pUSD, seller unchanged.

11. Wrong network. applyAddress compared parseChainId(eth_chainId) against 31337 and set isCorrectNetwork = false. The dashboard's write actions are gated on that flag, and the banner explains it — if the user sees nothing, the banner is above the fold or the component is reading a stale wallet object. Check the header chip and the console value of chainId.

12. UnauthorisedCaller. Possible causes: (a) the sending account is neither forwarder nor manual oracle, (b) the receiver's manual oracle was rotated and no longer matches the wallet, (c) the escrow's oracle was pointed elsewhere so the receiver's call fails downstream — but note that (c) produces UnauthorizedOracle from the escrow, not UnauthorizedCaller. Distinguish with two reads: receiver.manualOracle() and escrow.oracle(), compared against the connected address and the receiver address respectively.

13. Receipt verification. Fetch by hash, require status === 1, check to is the receiver, decode the logs for EscrowReleased(orderId, seller, amount) and SettlementExecuted(orderId, true), then read getEscrow(orderId) for status 2 and a non-zero settledAt, and finally compare the seller's balanceOf before and after — the delta must equal the escrowed amount exactly.

17.1 How to keep learning after this book

Three habits will carry you further than any tutorial. Re-derive, do not re-read: when you forget how the receiver works, write its checks from memory and compare. Change one thing in the repository and predict the failure before running it — set dryRun false on CRE while the bridge runs and see which check refuses; remove the allowlist and see two orders become eligible. And explain it to someone who does not code: the moment you can describe an oracle without the word "oracle", you understand it.

Finally, keep the honesty rule. The most impressive thing you can say about ProofPay is not that it is decentralised, but that you know exactly where it is not, why that choice was made, and what would have to change. That is what separates an engineer who used a tool from one who understands it.

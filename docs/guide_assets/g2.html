MODULE 3SMART CONTRACTS AND SOLIDITY FROM ZERO

This module is the centre of the book. Everything else in ProofPay exists to serve the three contracts: the frontend calls them, the backend checks them, the oracle reports into them, and the tests pin their behaviour. Read this module twice — once for the language, once for the design.

3.1 What a smart contract is, precisely

A smart contract is a program deployed to a blockchain, where it receives an address, keeps its own storage, and can only be changed by sending it a transaction. Three properties distinguish it from a backend function:

  • Deterministic execution. Every node computes the same result from the same input. No randomness, no clock, no network, no filesystem. block.timestamp is the only time available, and it is the block's time, agreed by consensus.
  • Persistent, public state. Storage survives forever and anyone can read it. That is why ProofPay writes only the escrow's essentials and keeps product names, descriptions and tracking IDs off chain.
  • No owner override. Once deployed, the code cannot be patched. ProofPay's escrow deliberately has no pause, upgrade or sweep function; the only mutable configuration is the oracle address.

The practical consequence: a bug in a backend can be fixed in ten minutes; a bug in a contract that holds money is permanent. That asymmetry explains the project's conservatism — small functions, explicit checks, OpenZeppelin for anything standard, and 31 tests for 300 lines of Solidity.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract Vault {
    mapping(address => uint256) public balances;   // storage
    error NotEnough(uint256 have, uint256 want);   // custom error

    function deposit() external payable {          // payable: accepts ETH
        balances[msg.sender] += msg.value;         // state write
    }

    function withdraw(uint256 amount) external {
        uint256 have = balances[msg.sender];
        if (have < amount) revert NotEnough(have, amount);
        balances[msg.sender] = have - amount;      // write BEFORE send
        payable(msg.sender).transfer(amount);      // external call LAST
    }
}

The ordering in withdraw — check, then write, then transfer — is the "checks-effects-interactions" pattern. ProofPay's escrow follows it too, and additionally wraps each state-changing function in nonReentrant.

3.3 ERC-20, from first principles

A token is not a special kind of coin; it is a row in a contract's storage. ERC-20 is a standard interface for such rows so that wallets, exchanges and other contracts can treat every token the same way. The standard requires six functions (totalSupply, balanceOf, transfer, allowance, approve, transferFrom) and two events (Transfer, Approval).

Table 3.2: ERC-20 concepts, and exactly where ProofPay uses them

mint / burnCreate / destroy supply. Not in the standard; an extension.Only mint exists, owner-only. No burn: escrowed value must not be destroyable.

Why are approve and transferFrom separate? Because otherwise any contract you call could take everything you own. The allowance is a capability you grant deliberately, for a specific spender, up to a specific amount. ProofPay's UI approves the exact order amount rather than an unlimited allowance, so a bug in the escrow cannot drain the wallet beyond one order.

  1. Buyer calls approve(escrow, 3499e18) on pUSD. Storage: allowance[buyer][escrow] = 3499e18.
  2. Buyer calls createEscrow(orderId, seller, 3499e18) on the escrow.
  3. Escrow calls pUSD.transferFrom(buyer, escrow, 3499e18).
  4. pUSD checks allowance[buyer][escrow] >= 3499e18 and balanceOf(buyer) >= 3499e18, moves the balance, decrements the allowance, emits Transfer.
  5. Escrow emits EscrowCreated and returns. The buyer's wallet is 3,499 pUSD lighter; the escrow contract is 3,499 pUSD heavier; nobody can spend it.

Lifecycle. Deploy with owner = admin (block 1, gas 618,390). Mint 1,000,000 pUSD to the admin (block 4), then distribute to buyer and seller (blocks 5–6). Buyer approves the escrow per order. Escrow pulls funds with transferFrom. At settlement the escrow calls transfer to the seller or back to the buyer. Total supply at block 32 was 1,010,100 pUSD, which is simply the initial million plus the top-ups used to seed demonstration orders.

3.5 ProofPayEscrow.sol, the heart of the system

The escrow answers one question: who is allowed to move this money, and when? It holds pUSD, records one struct per order, and exposes exactly two terminal transitions. There is no withdraw, no admin rescue, no upgrade. If the oracle disappears, the money stays locked — a deliberate failure mode, because "stuck" is recoverable by governance while "drained" is not.

contracts/contracts/ProofPayEscrow.sol — state and types (lines 10–48)
enum EscrowStatus { None, Funded, Released, Refunded }

struct Escrow {
    bytes32 orderId;
    address buyer;
    address seller;
    uint256 amount;
    uint64 createdAt;
    uint64 settledAt;
    EscrowStatus status;
}

IERC20 public immutable paymentToken;
address public oracle;
mapping(bytes32 => Escrow) private _escrows;

Two details repay attention. paymentToken is immutable: set once in the constructor and inlined into the bytecode, so it can never be pointed at a malicious token later. The timestamps are uint64 rather than uint256: they fit comfortably until the year 584 billion, and packing two 64-bit values with an address and an enum into fewer storage slots saves gas.

function createEscrow(bytes32 orderId, address buyer, address seller, uint256 amount)
    external nonReentrant
{
    if (orderId == bytes32(0)) revert InvalidOrderId();
    if (buyer == address(0) || buyer != msg.sender) revert InvalidBuyer();
    if (seller == address(0)) revert InvalidSeller();
    if (buyer == seller) revert SameBuyerAndSeller();
    if (amount == 0) revert InvalidAmount();
    if (_escrows[orderId].status != EscrowStatus.None) revert EscrowAlreadyExists(orderId);

    _escrows[orderId] = Escrow({ orderId: orderId, buyer: buyer, seller: seller, amount: amount,
        createdAt: uint64(block.timestamp), settledAt: 0, status: EscrowStatus.Funded });

    paymentToken.safeTransferFrom(buyer, address(this), amount);
    emit EscrowCreated(orderId, buyer, seller, amount);
}

confirmDelivery and confirmFailure — the only ways out

ProofPayEscrow.sol lines 119–139
function confirmDelivery(bytes32 orderId) external onlyOracle nonReentrant {
    Escrow storage escrow = _getFundedEscrow(orderId);
    escrow.status = EscrowStatus.Released;
    escrow.settledAt = uint64(block.timestamp);
    paymentToken.safeTransfer(escrow.seller, escrow.amount);
    emit EscrowReleased(orderId, escrow.seller, escrow.amount);
}

function confirmFailure(bytes32 orderId) external onlyOracle nonReentrant {
    Escrow storage escrow = _getFundedEscrow(orderId);
    escrow.status = EscrowStatus.Refunded;
    escrow.settledAt = uint64(block.timestamp);
    paymentToken.safeTransfer(escrow.buyer, escrow.amount);
    emit EscrowRefunded(orderId, escrow.buyer, escrow.amount);
}

The private helper is where the real invariant lives:

ProofPayEscrow.sol lines 141–158 — read path and funding guard
function getEscrow(bytes32 orderId) external view returns (Escrow memory) {
    Escrow memory escrow = _escrows[orderId];
    if (escrow.status == EscrowStatus.None) revert EscrowNotFound(orderId);
    return escrow;
}

function _getFundedEscrow(bytes32 orderId) private view returns (Escrow storage escrow) {
    escrow = _escrows[orderId];
    if (escrow.status == EscrowStatus.None) revert EscrowNotFound(orderId);
    if (escrow.status != EscrowStatus.Funded) revert EscrowNotFunded(orderId);
}

Read those two functions together and you see the double-settlement defence at the custody layer: settlement requires status == Funded, and settlement immediately writes Released or Refunded. A second attempt therefore fails at _getFundedEscrow before any transfer. That is true even if a future receiver, a buggy script or a stolen key calls it again. Defence in depth: the receiver also tries to prevent the second call, but the escrow does not depend on it.

Why not send funds straight to the seller and refund from the seller if lost?

Because the seller would have to be trusted to return money. Escrow inverts the trust: the money sits in a contract that neither party controls, and the only question is who can prove the condition. That is also why the escrow has no owner-withdrawal path — an "emergency" admin function is exactly the backdoor users would criticise in an audit.

setOracle and the authority chain

function setOracle(address newOracle) external onlyOwner {
    if (newOracle == address(0)) revert InvalidOracle();
    address previousOracle = oracle;
    oracle = newOracle;
    emit OracleUpdated(previousOracle, newOracle);
}

One line of configuration decides who may settle every order. In this deployment the owner is the admin EOA and the oracle is the receiver contract, set in block 19 for 30,539 gas. That separation is deliberate: the owner key configures, the receiver executes. When the project moves to a DON, only this address changes.

3.6 ProofPayCREReceiver.sol, the policy boundary

Why does a second contract exist between the oracle and the money? Three reasons. It accepts the exact interface a Chainlink DON calls (onReport(bytes,bytes)). It centralises authorisation, decoding, replay protection and duplicate-settlement checks in one auditable place. And it lets the escrow stay dumb: the escrow knows nothing about reports, outcomes or CRE, only "pay seller" and "pay buyer".

ProofPayCREReceiver.sol — state and authorisation (lines 40–96)
IEscrowSettlement public immutable escrow;
address public forwarder;        // authorised DON forwarder
address public manualOracle;     // authorised local/backup settler
mapping(bytes32 => bool) public processedReports;
mapping(bytes32 => bool) public orderSettled;

modifier onlyAuthorized() {
    if (msg.sender == forwarder) { _; return; }
    if (manualOracle != address(0) && msg.sender == manualOracle) { _; return; }
    if (owner() == msg.sender && forwarder == address(0)) { _; return; }
    revert UnauthorizedCaller(msg.sender);
}

Read the third branch carefully, because it is the one to be honest about. When no forwarder is configured — as in this local deployment, where the forwarder is the zero address — the owner may also settle. That is a convenience for local work and a weakening of the model; a production deployment would set a forwarder and delete that branch. The report and this guide both say so rather than pretending the fallback is a feature.

function onReport(bytes calldata metadata, bytes calldata report) external override onlyAuthorized {
    _processReport(metadata, report);
}
function processReport(bytes calldata metadata, bytes calldata report) external onlyAuthorized {
    _processReport(metadata, report);
}

function _processReport(bytes calldata metadata, bytes calldata report) internal {
    (bytes32 orderId, string memory outcome, bytes32 trackingIdHash, string memory observedAt)
        = abi.decode(report, (bytes32, string, bytes32, string));

    if (orderId == bytes32(0)) revert InvalidReportData();

    bytes32 reportId = keccak256(
        abi.encodePacked(orderId, outcome, trackingIdHash, observedAt, metadata)
    );
    if (processedReports[reportId]) revert ReportAlreadyProcessed(reportId);
    if (orderSettled[orderId]) revert OrderAlreadySettled(orderId);

    try this._checkEscrowFunded(orderId) returns (bool funded) {
        if (!funded) revert EscrowNotFunded(orderId);
    } catch { revert EscrowNotFound(orderId); }

    bytes32 outcomeHash = keccak256(bytes(outcome));
    if (outcomeHash == keccak256(bytes("DELIVERED"))) {
        escrow.confirmDelivery(orderId);
        processedReports[reportId] = true;
        orderSettled[orderId] = true;
        emit ReportProcessed(orderId, outcome, reportId);
        emit SettlementExecuted(orderId, true);
    } else if (outcomeHash == keccak256(bytes("LOST"))) {
        escrow.confirmFailure(orderId);
        processedReports[reportId] = true;
        orderSettled[orderId] = true;
        emit ReportProcessed(orderId, outcome, reportId);
        emit SettlementExecuted(orderId, false);
    } else {
        revert UnsupportedOutcome(outcome);
    }
}

Note what the receiver does not do: it does not verify a signature, because authorisation comes from the caller's address; it does not re-derive the outcome from anything, because the outcome is CRE's decision; and it does not know the seller or the amount, because the escrow owns those facts. It is a policy boundary, and keeping it narrow is what makes it reviewable.

3.7 Solidity security, using your own code as the case study

Reentrancy

Reentrancy is an attack where an external call lets the callee call back into your contract before your state is final. With a token that had a malicious hook, safeTransfer could re-enter confirmDelivery and pay twice. Two defences stop it here. ReentrancyGuard sets a storage flag so a nested call reverts with ReentrancyGuardReentrantCall. And the state is already terminal before the transfer, so even without the guard a second entry would hit EscrowNotFunded. The test suite includes a reentrant createEscrow case precisely to keep both defences honest.

SafeERC20

Some tokens return false instead of reverting on failure, and some return nothing at all. A plain transfer call that ignores the return value can therefore "succeed" without moving anything. SafeERC20 checks the return data and reverts if the call failed, so the escrow's accounting cannot drift from reality. pUSD itself behaves, but the escrow is written to survive a less cooperative asset.

Integer handling

Solidity 0.8 checks arithmetic by default: overflow and underflow revert instead of wrapping. That is why ProofPay needs no SafeMath. Balances are uint256 in the token's smallest unit, so 3,499 pUSD is 3499×1018, an integer with no rounding. Comparisons such as amount == 0 are exact; there are no floating-point traps anywhere in the money path, and the UI's formatting is presentation only.

Interview checkpoint — Module 3

Q. "Where exactly do you prevent double payment?" A. In three independent places. The escrow requires status == Funded and flips it to a terminal state before transferring. The receiver keeps processedReports for identical reports and orderSettled for any second report on the same order. The bridge refuses to submit a report ID it already recorded. Any one of the three would stop the common case; all three together stop retries after crashes, two competing bridges, and a buggy new caller.

Q. "Can the owner steal the escrowed money?" A. Not directly. The owner can point the oracle at a contract that always releases, which is a governance risk, not a code-level drain — and it is logged by OracleUpdated. There is no function that transfers escrowed pUSD to an arbitrary address.

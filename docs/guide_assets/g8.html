MODULE 14 · PART AINTERVIEW AND VIVA BANK: LEVELS 1–3

Each answer follows the same rhythm: a short answer you can say in one breath, then the reasoning, then the ProofPay instance. Say the short answer first even in a viva — examiners grade clarity, then probe.

14.1 Level 1 — foundations

Q1. What is a blockchain?

Short: a database replicated across independent computers where changes are signed transactions grouped into hash-linked blocks. Reasoning: replication plus agreed validity rules means no single party can rewrite history unnoticed. In ProofPay: the escrow's state, every deposit and every settlement live in such a ledger, so neither buyer nor seller can alter the record of who was paid.

Q2. What is Ethereum?

Short: a blockchain whose nodes also run a virtual machine that executes programs called smart contracts. Reasoning: Bitcoin stores value transfers; Ethereum stores arbitrary state transitions, which is what makes conditional escrow possible. In ProofPay: the payment rules are code, not policy.

Q3. What is a smart contract?

Short: a program deployed to an address on the blockchain, with persistent public storage, executed deterministically by every node. Reasoning: determinism is what allows consensus; persistence is what makes it a record; no upgrade path is what makes it credible. In ProofPay: ProofPayEscrow holds funds and can only pay out through two functions.

Q4. What is Solidity?

Short: the main high-level language for EVM contracts, compiling to bytecode. Reasoning: it adds contract-specific constructs — modifiers, events, custom errors, storage mappings — on top of a JavaScript-like syntax. In ProofPay: all three contracts are Solidity 0.8.28, with OpenZeppelin for standard behaviour.

Q5. What is MetaMask?

Short: a browser extension wallet that stores keys, signs transactions, and injects an EIP-1193 provider at window.ethereum. Reasoning: it separates key custody from the application, so a website can request signatures without ever seeing a key. In ProofPay: every write — approve, createEscrow, processReport — is signed there.

Q6. What is an ERC-20 token?

Short: a standard interface for fungible tokens: balances, transfers, allowances and two events. Reasoning: standardisation means wallets and contracts can handle any token without custom code. In ProofPay: pUSD implements it, so the escrow can use SafeERC20 and treat it like any compliant asset.

Q7. What is gas?

Short: a unit measuring computational work, paid for in the chain's native currency. Reasoning: it prices storage and computation, preventing infinite loops and spam. In ProofPay: createEscrow costs about 156,000 gas and processReport about 122,000; the amounts were read from receipts, not estimated.

Q8. What is an escrow?

Short: a neutral hold on funds until an agreed condition is met. Reasoning: it removes the "who goes first" problem by making neither party able to spend prematurely. In ProofPay: the contract is the neutral holder, and the condition is an oracle report about delivery.

Q9. What is a transaction hash?

Short: the Keccak-256 digest of a signed transaction, used as its unique identifier. Reasoning: it is deterministic, so anyone can look it up on any node and see the same receipt. In ProofPay: the refund hash 0x835890…a5288 identifies the block-29 settlement.

Q10. What is a block number?

Short: the position of a block in the chain. Reasoning: ordering is what gives finality; a receipt's block number is when its effects became part of history. In ProofPay: settlements at blocks 24, 29 and 30, each exactly one higher than the last, which also proves no hidden extra transaction.

Q11. What is a nonce?

Short: a per-account counter that orders that account's transactions and prevents replay. Reasoning: a transaction with nonce n cannot be mined before n−1, and cannot be mined twice. In ProofPay: a stuck nonce is the usual cause of a "pending forever" transaction on the local node.

Q12. What is a chain ID?

Short: the network identifier that is signed into every transaction. Reasoning: it prevents a transaction signed for one chain from being replayed on another. In ProofPay: 31337 for Hardhat Local, and the UI refuses writes when the wallet reports anything else.

Q13. What is an RPC endpoint?

Short: an HTTP (or WebSocket) URL that a client uses to talk to a node. Reasoning: it exposes methods such as eth_call, eth_sendTransaction and eth_getLogs. In ProofPay: http://127.0.0.1:8545 is used by the wallet, the frontend, the backend verifier, the workflow and the bridge.

Q14. What is the EVM?

Short: the deterministic virtual machine that executes contract bytecode. Reasoning: determinism plus metered execution (gas) is what makes contract results agree across nodes. In ProofPay: the escrow's validations and the token's balance updates are EVM execution.

Q15. What is the difference between an address and an account?

Short: an address is the 20-byte identifier; an account is the thing it identifies, with a balance and possibly code and storage. Reasoning: every address is an account, but only EOAs can initiate transactions. In ProofPay: the receiver has an address, an account, code and two mappings, but no key — it can only act when called.

Q16. What is a private key, and who holds the project's?

Short: the 256-bit secret that signs transactions. Reasoning: possession is authority; there is no password reset. In ProofPay: no key is stored in the repository. The local Hardhat node holds test keys in memory and exposes the accounts as unlocked, so the bridge signs via eth_sendTransaction.

Q17. What is a hash function and why Keccak-256?

Short: a one-way function mapping any input to a fixed 32-byte fingerprint, with avalanche behaviour. Reasoning: Ethereum uses Keccak-256 for block linkage, addresses, selectors and event topics, so using it keeps your code consistent with the platform. In ProofPay: order IDs, tracking hashes and report IDs are all Keccak-256.

Q18. What is a digital signature?

Short: a proof, verifiable with a public key, that the holder of the matching private key approved specific bytes. Reasoning: signatures bind authorisation to content, so changing any field invalidates them. In ProofPay: that is why editing a request in the browser cannot move funds.

Q19. What does immutability actually mean here?

Short: rewriting history requires redoing all later blocks faster than honest participants extend the chain. Reasoning: immutability is economic and social, not absolute. In ProofPay: strong on chain, absent on the local node — restarting Hardhat erases everything, so no mainnet-style guarantee is claimed.

Q20. Why is the blockchain public a privacy problem, and how did you handle it?

Short: every address, amount and call is visible forever. Reasoning: payment transparency is the feature; leaking shipping details is the risk. In ProofPay: the report stores keccak256(trackingId) rather than the tracking number, so settlements are auditable without publishing parcel identifiers.

Q21. What is a testnet, and did you use one?

Short: a chain with valueless currency for development. Reasoning: it lets you rehearse without risking assets while still being public. In ProofPay: no. The project runs entirely on Hardhat Local; a Sepolia network entry exists in the config but was never used, and the report says so.

Q22. What is a wallet, if it does not hold coins?

Short: software that holds keys and signs; the coins are ledger entries. Reasoning: restoring a seed phrase restores access, not data. In ProofPay: deleting the extension changes nothing on chain; the escrow still holds the pUSD.

14.2 Level 2 — mechanics

Q23. How does MetaMask communicate with React?

Short: through the injected EIP-1193 provider's request() method and its events. Reasoning: the provider is a transport, not a library, so any framework can use it. In ProofPay: useWallet calls eth_requestAccounts, eth_chainId, eth_getBalance, and subscribes to accountsChanged and chainChanged.

Q24. What is EIP-1193?

Short: the standard describing the injected provider object and its request/response protocol. Reasoning: before it, each wallet invented its own API; after it, one code path works across wallets. In ProofPay: every chain interaction in the browser goes through it.

Q25. What is an ABI?

Short: a JSON description of a contract's functions, arguments, returns, events and errors. Reasoning: the EVM only sees bytes, so the ABI is how tooling encodes calls and decodes results. In ProofPay: the receiver's ABI has two functions in the frontend and seven entries in the bridge, including errors it decodes.

Q26. What is ABI encoding?

Short: the canonical byte layout for arguments: 32-byte words, offsets for dynamic types, lengths for strings and bytes. Reasoning: both sides must agree byte-for-byte or decoding fails. In ProofPay: the four-field report is 256 bytes, and its layout is why the receiver can decode it with one call.

Q27. What is a function selector?

Short: the first four bytes of keccak256("name(types)"), prefixed to calldata. Reasoning: it tells the contract which function to run without sending names. In ProofPay: the bridge's 388-byte transaction begins with the processReport(bytes,bytes) selector.

Q28. What is the difference between call, staticcall and delegatecall?

Short: call can change state, staticcall forbids it, and delegatecall runs another contract's code in the caller's storage. Reasoning: the distinction is what makes read-only RPC safe. In ProofPay: reads use eth_call, which is a static call; nothing in the project uses delegatecall, and no proxy pattern is used.

Q29. Why do you need approve before transferFrom?

Short: because a token contract will only debit an owner who has authorised that specific spender. Reasoning: without allowances, any contract you interact with could take everything. In ProofPay: transaction 1 sets allowance[buyer][escrow]; transaction 2 spends it inside createEscrow.

Q30. Why does the allowance get consumed?

Short: ERC-20 decrements the allowance on every transferFrom. Reasoning: an allowance is a spending limit, not a permanent grant. In ProofPay: a second purchase needs a fresh approval, which is why the checkout always runs the approve step rather than assuming it is still valid.

Q31. What is ReentrancyGuard and why is it there?

Short: a modifier that sets a storage flag so a function cannot be re-entered before it finishes. Reasoning: external calls hand control to code you do not control. In ProofPay: createEscrow and both settlement functions are nonReentrant, and a test attempts the attack.

Q32. What is SafeERC20?

Short: a wrapper that checks the return value of token calls and reverts on failure. Reasoning: some tokens return false instead of reverting, so ignoring the return value can silently lose funds. In ProofPay: all escrow transfers use it.

Q33. What is an event, and can a contract read it?

Short: a log entry stored in the transaction receipt; contracts cannot read logs. Reasoning: logs are cheap, indexable, and for off-chain consumers. In ProofPay: EscrowCreated lets the frontend discover orders, but every value shown is re-read from storage.

Q34. What is a custom error, and why use it?

Short: a typed revert with optional arguments, defined with the error keyword. Reasoning: cheaper than strings and precisely testable. In ProofPay: the tests assert revertedWithCustomError(token, "ERC20InsufficientBalance").withArgs(...).

Q35. What is an oracle?

Short: a component that delivers external facts to a blockchain. Reasoning: contracts cannot fetch, so facts must be pushed in with evidence. In ProofPay: the CRE workflow is the oracle, and the receiver is the contract that decides whether to believe its report.

Q36. Why can't a smart contract call an API directly?

Short: because execution must be deterministic and identical on every node; HTTP is neither. Reasoning: one node getting a different response would fork consensus. In ProofPay: this constraint is the reason the whole oracle pipeline exists.

Q37. What is the oracle problem?

Short: how to get a trustworthy external fact into a system that cannot verify it. Reasoning: any oracle reintroduces a trust assumption; the design question is how to bound it. In ProofPay: bounded by authorisation, replay protection, one settlement per funded order and a documented trust boundary.

Q38. What is a DON?

Short: a decentralised oracle network: independent nodes that must agree before reporting. Reasoning: agreement removes the single-reporter assumption. In ProofPay: the code is written for it, but no DON is deployed, so this is future work, not a claim.

Q39. What is Chainlink CRE?

Short: a runtime for TypeScript workflows with triggers, HTTP and EVM capabilities, and signed reports for on-chain receivers. Reasoning: it packages the whole fetch-verify-decide-report loop. In ProofPay: it holds the only settlement decision in the system.

Q40. What is a cron trigger?

Short: a schedule-based trigger, here the expression 0 */5 * * * *. Reasoning: settlement is periodic, not event-driven from the chain's perspective. In ProofPay: a deployed workflow would evaluate every five minutes; the simulator fires once per invocation.

Q41. What does the HTTP capability do in your workflow?

Short: performs GET /api/shipments and returns the body as text, with consensus aggregation available. Reasoning: this is the only place external data enters the decision. In ProofPay: a failure here ends the run with no settlement rather than a partial one.

Q42. What does the EVM capability do?

Short: performs a contract read (and, in principle, a report write) on a chain selected by a CRE chain selector. Reasoning: it lets the workflow verify on-chain state before deciding. In ProofPay: it reads getEscrow at the last finalised block and skips anything not Funded.

Q43. What is a CRE report?

Short: the SDK object holding your ABI-encoded payload plus a runtime metadata header. Reasoning: the header is provenance; the body is what the receiver decodes. In ProofPay: 109-byte header, 256-byte body, 365-byte raw report — and the extraction code proves which slice it used.

Q44. What is a receipt, and what does status 1 mean?

Short: the node's record that a transaction was included and what it did; status 1 means it succeeded. Reasoning: a hash alone proves broadcasting, not success. In ProofPay: every settlement was verified by receipt status, block number, gas used and the emitted events.

Q45. Why are reads free but writes costly?

Short: reads are executed locally against current state and change nothing; writes must be replicated and stored by every node. Reasoning: cost prices permanent storage. In ProofPay: this is why shipment status is off chain and only the escrow's essential facts are stored.

14.3 Level 3 — your architecture

Q46. Explain the ProofPay architecture in one minute.

Short: React talks to MetaMask and to an Express API; three contracts on Hardhat hold the money and the rules; a CRE workflow reads the API and the escrow, decides, and emits a report; a local bridge relays that report to the receiver, which instructs the escrow to pay. Reasoning: each layer owns one fact and one authority. Instance: the buyer's escrow, the seller's shipment record, CRE's decision, and the receiver's authorisation are four separate things that must all agree.

Q47. Why a custom token instead of ETH?

Short: to separate protected value from gas and to keep amounts exact. Reasoning: ETH-denominated escrow conflates fees with principal and makes demonstrations unstable. Trade-off: pUSD is a prototype with no reserve, and every claim must say so.

Q48. Why can't the seller access the funds immediately?

Short: because the escrow has no withdrawal function at all. Reasoning: protection requires that no one — seller, buyer, owner — can move the deposit before the condition. Instance: the only two paths are confirmDelivery and confirmFailure, both onlyOracle.

Q49. Why is there a separate receiver contract?

Short: to keep report handling out of the custody contract and to present the interface a DON expects. Reasoning: smaller money contracts are easier to audit; report policy changes more often than custody. Trade-off: one more address and ~51,000 extra gas per settlement.

Q50. What does manualOracle mean?

Short: an address the receiver will also accept reports from, intended for local testing and break-glass operation. Reasoning: without it, nothing could be settled before CRE worked, and an oracle outage would freeze funds. Trade-off: a real weakening when set to an EOA; production should use a multisig or remove it.

Q51. How does shipment registration work?

Short: the seller POSTs order ID, tracking ID, carrier and address to the API, which validates duplicates, verifies the escrow is funded on chain and that the seller matches, then stores a record with an event history. Reasoning: registration is the seller's claim; the chain verification is what makes the claim meaningful.

Q52. How does CRE read escrow data?

Short: it ABI-encodes getEscrow(orderId) with viem, sends it through EVMClient.callContract at the last finalised block, and decodes the returned struct. Reasoning: reading at a finalised block avoids deciding on a reorg-prone tip. Instance: status must be 1, otherwise the shipment is skipped and logged.

Q53. How does the local execution bridge work?

Short: it runs the CRE simulator, parses the structured report lines, validates and cross-checks them, then submits the exact bytes to processReport from an unlocked local account and verifies the receipt. Reasoning: the decision stays in CRE; the bridge only carries it. Instance: the block-29 refund.

Q54. Why does the bridge not just call confirmFailure itself?

Short: because only the oracle can, and the oracle is the receiver. Reasoning: routing through the receiver is what enforces replay and duplicate protection; a direct call would bypass the entire policy layer. Instance: the admin EOA cannot call the escrow's settlement functions at all.

Q55. What is the difference between the manual and automatic paths?

Short: manual builds a report in the browser with a zeroed tracking hash; automatic uses a CRE report with a real tracking hash and provenance. Reasoning: both pass the same receiver checks, but only the automatic path has evidence linking the decision to a courier record. Instance: the oracle panel is the manual path; the bridge is the automatic one.

Q56. Why is shipment status not stored on chain?

Short: it changes six times, comes from outside, and must be correctable. Reasoning: on-chain writes are permanent and cost gas; a mis-scan would be unfixable. Instance: the JSON store is the record; the chain stores only the settlement and its report ID.

Q57. How is a settlement prevented from happening twice?

Short: three layers: the escrow's Funded check, the receiver's two mappings, and the bridge's state file. Reasoning: each layer covers a different failure — a buggy caller, a replayed report, a retried process. Instance: blocks 24, 29 and 30 each advanced the chain by exactly one, so no duplicate was hidden.

Q58. What does the courier scheduler do, and what does it not do?

Short: it advances demo shipments through the timeline and optionally runs CRE and the bridge; it never decides settlement or touches contracts. Reasoning: separating the fact generator from the decision keeps CRE's authority intact. Instance: -LOST suffix decides the courier outcome, not the payout.

Q59. Why does the receiver store a hash of the tracking ID?

Short: to tie the settlement to a specific shipment record without publishing the tracking number. Reasoning: evidence plus privacy; it also contributes to the report ID. Instance: the manual path uses a zero hash, which is exactly why it is weaker.

Q60. What happens if CRE never runs?

Short: the escrow stays Funded; nothing is lost but nothing settles. Reasoning: the system fails safe, not open. Instance: the manual oracle path or a redeployed workflow is the recovery, and the funds remain claimable because they are still in custody.

Q61. Why does the checkout validate the seller address before prompting the wallet?

Short: to avoid wasting a signature on a call that must revert. Reasoning: the contract enforces the same rules, but failing in the UI is cheaper and clearer. Instance: zero address, self-payment and malformed addresses are blocked in handleSubmit.

Q62. How does the buyer dashboard know which orders are theirs?

Short: it discovers all order IDs from EscrowCreated logs, reads each escrow, and filters where buyer == connected address. Reasoning: chain state cannot be queried "by buyer" without an index, so filtering happens client-side. Trade-off: fine for a local demo, but a production app would index events in a database.

Q63. Why does the backend verify the escrow before accepting a shipment?

Short: a shipment for an unfunded order would have no money to settle. Reasoning: it also prevents a seller from registering an order that belongs to someone else. Instance: 404 ESCROW_NOT_FOUND, 409 ESCROW_NOT_FUNDED, 409 SELLER_MISMATCH.

Q64. What would break if you removed the allowlist from the bridge?

Short: a run intended for one order would settle every eligible order CRE reported. Reasoning: the allowlist scopes a demonstration without changing the decision. Instance: the refund run reported two shipments; without the allowlist, two settlements would have been submitted.

Q65. What is the most important line in main.ts, and why?

Short: const report = runtime.report(reportRequest).result(); placed before the dry-run branch. Reasoning: generation must happen regardless of whether the write is attempted, otherwise the safe configuration produces nothing to capture. Instance: that reordering is what made the entire local bridge possible.

MODULE 4HARDHAT AND LOCAL BLOCKCHAIN DEVELOPMENT

Hardhat is the tool that turns Solidity text into a running system: it compiles, it deploys, it tests, and it can run a complete Ethereum node on your laptop. Everything you demonstrated in this project — a funded escrow, a CRE-mediated settlement at block 30 — happened on the chain that Hardhat started.

4.1 What Hardhat does, and why this project uses it

Hardhat is a development environment for Ethereum. In this repository it provides five things: a Solidity compiler pipeline (npx hardhat compile), a test runner built on Mocha with chain-aware assertions, a scripting environment where you write JavaScript that talks to the chain, a local node (npx hardhat node) with deterministic accounts, and a network abstraction so the same scripts can target localhost or a public network by changing one flag.

contracts/hardhat.config.js (complete)
require("dotenv").config();
require("@nomicfoundation/hardhat-ethers");
require("@nomicfoundation/hardhat-chai-matchers");

const SEPOLIA_RPC_URL = process.env.SEPOLIA_RPC_URL || "https://rpc.sepolia.org";
const PRIVATE_KEY = process.env.PRIVATE_KEY;
const LOCAL_RPC_URL = process.env.LOCAL_RPC_URL || "http://127.0.0.1:8545";

module.exports = {
  solidity: { version: "0.8.28", settings: { optimizer: { enabled: true, runs: 200 } } },
  networks: {
    hardhat:   { chainId: 31337 },
    localhost: { url: LOCAL_RPC_URL, chainId: 31337, gas: 16000000 },
    sepolia:   { url: SEPOLIA_RPC_URL, accounts: PRIVATE_KEY ? [PRIVATE_KEY] : [], chainId: 11155111 },
  },
};

Three observations that interviewers like. First, the optimizer is on at 200 runs: deployment bytecode is slightly larger, runtime calls are cheaper, which is the right trade for contracts called many times. Second, the sepolia block exists but was never used; its presence is configuration, not evidence of deployment, and the report says so. Third, the private key is read from the environment and only wired into the unused network — the local workflow never needs a key at all, because Hardhat's accounts are unlocked.

Because the node holds the keys in memory and exposes them as unlocked accounts, a client can send eth_sendTransaction and the node signs. That is why the bridge needs no private key. It is also why a restart is so destructive: the chain lives in the node's memory, so stopping it erases every block, every contract and every balance, and the next start redeploys from scratch at the same deterministic addresses with a fresh history.

Never restart casually

If you restart the node mid-demonstration, the contract addresses stay the same (same deployer, same nonces) only after you redeploy; until then those addresses are empty. The frontend will show zero balances, the backend's shipment records will reference orders that no longer exist, and the bridge will fail preflight with "No bytecode at escrow". Recovery is: redeploy, re-authorise, re-mint, re-register shipments. Module 12 has the full procedure.

4.3 Compilation, artifacts, ABI and bytecode

npx hardhat compile produces two things per contract under artifacts/: bytecode, which is the deployable machine code, and the ABI (application binary interface), a JSON description of every function, argument, return value, event and error. The ABI is what lets JavaScript call a contract: it tells viem or ethers how to encode your arguments into calldata and how to decode the returned bytes.

A function's selector is the first four bytes of keccak256("name(type1,type2)"). processReport(bytes,bytes) therefore always has the same selector everywhere in the world, which is why the 388-byte calldata in the bridge log begins with that constant and why an explorer can label a transaction it has never seen before.

4.4 Deployment scripts and what they prove

Deployment order is forced by the constructors. The token must exist before the escrow, because the escrow's constructor checks that the token address has bytecode. The escrow must exist before the receiver, because the receiver stores it as IEscrowSettlement. Then two authorisation calls make the chain of authority real: escrow.setOracle(receiver), and receiver.setManualOracle(admin) with the forwarder left at zero.

// The essence of scripts/authorize-receiver.js, with read-back verification.
await escrow.setOracle(receiverAddress);
const wired = await escrow.oracle();
if (wired.toLowerCase() !== receiverAddress.toLowerCase()) throw new Error("oracle wiring failed");

// scripts/deploy-receiver.js additionally writes:
// contracts/deployments/cre-receiver-localhost.json
// { network, chainId, deployer, owner, escrow, forwarder, manualOracle, receiver, deployedAt }

That JSON file is the project's deployment record, and it is why the report can state addresses with confidence. Its forwarder field is 0x000…000: the honest marker that no DON is attached.

4.5 Testing: how 31 tests are organised, and what they actually assert

Tests are written with Mocha, Chai and @nomicfoundation/hardhat-chai-matchers, and use loadFixture from the network helpers. A fixture deploys the contracts once and snapshots the chain; every test then restores that snapshot, so tests cannot contaminate each other and the suite runs in under a second.

async function deployTokenFixture() {
  const [owner, alice, bob] = await ethers.getSigners();
  const token = await (await ethers.getContractFactory("ProofPayUSD")).deploy(owner.address);
  await token.waitForDeployment();
  return { token, owner, alice, bob };
}

it("allows only the owner to mint", async function () {
  const { token, owner, alice } = await loadFixture(deployTokenFixture);
  await expect(token.connect(alice).mint(alice.address, 1000n))
    .to.be.revertedWithCustomError(token, "OwnableUnauthorizedAccount")
    .withArgs(alice.address);
});

Two tests worth understanding in detail

"prevents duplicate settlement". The test funds an escrow, submits a valid DELIVERED report, then submits the same report again. Without the protection, the seller would be paid twice out of other users' deposits — the escrow's balance is pooled, so the second payment would silently consume someone else's money. The assertion is that the second call reverts with ReportAlreadyProcessed and that the seller's balance is unchanged. The reason this test matters more than most: it is the difference between a demo and a system.

"blocks reentrant escrow creation". A malicious token contract calls back into createEscrow during transferFrom. Without a guard, the attacker could create a second escrow that shares the same deposit, or corrupt the mapping. The nonReentrant modifier makes the inner call revert. If you removed the modifier, this test fails immediately, which is exactly what you want from a security test.

How to run and read the suite

cd contracts && npx hardhat test prints one line per test and a summary. The expected summary is 31 passing in well under a second. If a test fails, read the diff: chai-matchers show expected versus actual error names and arguments, which is usually enough to identify the broken invariant without a debugger.

5.2 TypeScript: why the types are not decoration

The project uses TypeScript 5.7 with strict settings. In a blockchain app this matters more than usual because three different representations of the same value meet in the browser: a decimal string typed by a user ("3499"), a bigint in the token's smallest unit, and a hex string for calldata. Mixing them silently is how people send 3.499 tokens instead of 3,499.

// frontend/src/lib/contracts.ts — the boundary between display and chain units
export function parseTokenAmount(input: string, decimals: number):
  { value: bigint; error: string | null } { /* digits → bigint * 10**decimals */ }

export function formatTokenAmount(value: bigint, decimals: number): string { /* reverse */ }

Every amount crossing the boundary goes through these two functions. The UI never does parseFloat on money, and the contract never sees a string. Types also catch the common mistake of passing number where bigint is required, which would otherwise throw at runtime on large amounts.

5.3 ABI, selectors and how the browser actually calls a contract

An ABI is a JSON array describing each function's name, inputs, outputs and mutability. viem uses it in two directions: encodeFunctionData turns (function, args) into calldata; decodeFunctionResult turns returned hex into typed values. A read becomes eth_call; a write becomes eth_sendTransaction followed by a receipt wait.

// frontend/src/lib/receiver.ts — building a processReport call by hand
export function encodeProcessReportCalldata(orderId, kind, observedAt) {
  const outcome = kind === 'delivery' ? 'DELIVERED' : 'LOST';
  const trackingIdHash = `0x${'0'.repeat(64)}`;           // manual path has no tracking hash
  const report = encodeAbiParameters(
    parseAbiParameters('bytes32 orderId, string outcome, bytes32 trackingIdHash, string observedAt'),
    [orderId, outcome, trackingIdHash, observedAt]
  );
  return encodeFunctionData({ abi: RECEIVER_ABI, functionName: 'processReport', args: ['0x', report] });
}

This function is worth studying because it mirrors the CRE payload exactly. The receiver decodes four fields; the manual panel must therefore produce four fields, with an empty metadata blob (0x) and a zero tracking hash. The zeroed hash is honest: the manual operator has no tracking ID, and the report ID is still unique because the timestamp and order differ. It also shows the trade-off of the manual path — no provenance — which is why automatic settlement is the project's real subject.

5.4 Discovering escrows, and why logs are not the source of truth

// frontend/src/store/useEscrows.ts (structure, not the whole file)
const logs = await provider.request({ method: 'eth_getLogs', params: [{
  address: escrowContractAddress(), fromBlock: '0x0', toBlock: 'latest',
  topics: [ESCROW_CREATED_TOPIC]                       // filter on the event signature
}]});
const ids = [...new Set(logs.map(l => l.topics[1]))];  // indexed orderId
for (const id of ids) {
  const escrow = await readEscrow(id);                 // getEscrow via eth_call
  // build the Order object from the struct, never from the log's data
}

Two subtleties. The order ID is indexed in the event, which is why it appears in topics[1] and why eth_getLogs can filter on it. And the log is used only to learn which IDs exist; every displayed field is re-read from storage. That protects the UI from stale or partial logs and from the classic bug of trusting an event that a reorg could remove.

5.5 Transaction state in the UI, and why two receipts matter

The checkout does not fire two transactions and hope. It models the sequence explicitly: approving → approved → creating → confirmed, with the buttons disabled while busy. The reason is that the second transaction is only valid after the first is mined; sending both immediately would race, and the escrow call could execute before the allowance exists, reverting with ERC20InsufficientAllowance.

const busy = tx.phase === 'approving' || tx.phase === 'approved' || tx.phase === 'creating';
// ... later, after each receipt:
//   approve  → phase 'approved', then send createEscrow
//   create   → phase 'created', call onCreated() so the app re-reads the chain

After success, the component calls onCreated(), which triggers the same discovery-and-read path described above. No local state is trusted as a record of the purchase; the chain is re-read, and if the read disagrees with the optimistic UI, the chain wins.

5.6 Error handling that users can act on

Three error layers exist. Wallet errors come back with codes: 4001 means the user rejected the prompt, 4902 means the chain is not configured. Contract errors arrive as revert data; viem decodes them into the custom error name, which the UI can translate ("Escrow already exists for this order"). Application errors are the ones the UI generates before touching the wallet, such as "The seller cannot be your own wallet", validated in handleSubmit.

Interview checkpoint — Modules 4 and 5

Q. "Why does the UI call getEscrow after reading logs instead of decoding the log's data?" A. Logs are an index, not a record: they can be missing if you start from the wrong block and they carry only the fields the event declared. Storage is authoritative, so the app uses logs to find IDs and storage to render values.

Q. "What happens if the user rejects the second MetaMask prompt?" A. The allowance transaction is already mined, so the spender is approved but no escrow exists. Nothing is lost; the UI reports the rejection and the buyer can retry the escrow call without repeating the approval.
